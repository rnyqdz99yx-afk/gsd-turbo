# gsd-turbo Stage 4 L4 — the live view for several lanes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `turbo-run view` / `view --json`, `status`, `status --watch`, the `turbo-view` pane, its band and toasts, and the owner's Telegram messages show several lanes at once: for each lane its phase, slot, step, helpers and questions, one summary line for the run (`3 lanes · 1 question · next: phase 36 waits for phase 34`), and why the next phase waits.

**Architecture:** One reader turns `supervisor.json` into a list of lanes, whether it holds Stage 4's `lanes` object or v0.3's single `lane` (`lib/sup-lanes.mjs`). `buildView` (`lib/view.mjs`) builds one lane view per entry. It reads the run files (progress, lane record, push) from the control root, and the phase files and the Claude Code transcripts from the lane's slot (`slotPath`). It also adds the next waiting phase with its reason to the view: a pure `waitReason(phase, state)` over the GSD phase list (cached), L3's lanes file and L0's slots. The view stays `v: 1`; every new field is additive. The pane (`mod/hooks/view-model.mjs`) and its text twin `formatView` (`lib/view.mjs`) draw the same lines. With one lane they draw exactly v0.3's lines. With two or more they draw a verdict line, a summary line and a block per lane. With more than two lanes, a block shrinks to one line unless that lane has a question or a warning. Telegram cards and notification bodies name the lane and carry the summary line. The readers of `supervisor.json.lane` outside the supervisor (`agent-tail`, `context`, `activePhase`, `status`) read per-lane entries.

**Tech Stack:** Node ≥ 20 (ESM `.mjs`, `node:test`, zero npm dependencies), Claude Code 2.1.29x mods (the pane), GSD 1.16 (`gsd-tools init manager` for the phase list).

**Spec:** `docs/specs/2026-10-13-stage-4-design.md` — §8 (status / pane / Telegram list the lanes: phase, slot, step, helpers, questions; the summary line; the pane's blocks, collapsed past two lanes, opened where a question or a warning is; cards show which lane) is the scope. §5 (what makes a phase ready: deps, `Areas`, `Gates`, a free trusted slot, `< max_lanes`; no `lanes.json` → one phase lane) and §6.3 (the `Areas` overlap rule) explain why a phase waits. §11 (L4 depends on L1's `supervisor.json` format) applies too. The format model is `docs/plans/2026-10-11-stage-3-s4-live-sittings.md`.

**Base:** branch `stage-4` at `d5a6ba8` with L0 (`docs/plans/2026-10-13-stage-4-l0-slots.md`) merged first. L1, L2 and L3 run in parallel with this plan. L4 imports nothing they write: it reads `supervisor.json`, and loads `lib/slots.mjs` (L0) and `lib/lanes-file.mjs` (L3) only when the file exists (D6). Existing code is referenced by function name and anchor text, never by line number. If an anchor moved, apply the same change next to the named code.

## Decisions this plan makes where the spec is open

- **D1 One reader of `supervisor.json`.** `supLanes(sup)` (`lib/sup-lanes.mjs`) returns the lanes as a list. It takes the non-empty `lanes` object, or else the v0.3 `lane`, which becomes one entry `{ key: <phase>, job: 'phase', slot: null, slotPath: null, … }`. Entries are normalized: `key` and `phase` are strings, `job` is one of `phase`/`prep`/`annotate` (anything else reads as `phase`), `slot` is a whole number ≥ 1 or null, and `slotPath` is an absolute path or null. An entry nobody can show (not an object, or a phase/prep job without a phase) is dropped. Order: phase jobs by phase (`comparePhase`), then prep, then annotate. `laneFor(sup, { phase, job, dir })` finds one entry by its slot directory (`dirKey`) or by phase. `laneDir(lane, root)` is the directory the lane works in: `slotPath`, or `root` in checkout mode. Every reader in this plan goes through these three functions.
- **D2 Where a lane's files are.** Run files (`phase-p<N>.json`, `p<N>.json`, `p<N>-push.json`, questions) are read from the control root (`root`), as L0 D3 keeps them. Phase files (`.planning/phases/<N>-*`) and Claude Code transcripts are read from `laneDir(lane, root)`. A slot is its own project for Claude Code: its sessions live under `<claude-home>/projects/<key of the slot path>`. `projectDirs`, `laneTranscript` and `laneAgents` get the slot path. `laneAgents` also uses it to show helper file paths relative to the slot.
- **D3 The view stays `v: 1`.** New fields are added and none is renamed: `lanes[].key`, `lanes[].job`, `lanes[].slot`, `next` (`{ phase, kind, other, gate } | null`) and `finished` (the milestone's finished phase ids, or null when unknown). A mod from v0.3 reads the new view and ignores what it does not know.
- **D4 The next phase and why it waits.** The next phase is the lowest unfinished phase of the run's range that no phase lane holds. A phase in prep counts: its prep lane is not its phase lane. `waitReason(phase, state)` names the first match: `deps` (its lowest unfinished dependency in the milestone), `turn` (checkout mode, no lane has a slot: one phase at a time), `marking` (no fresh lanes file while a phase lane runs: spec §5, one phase lane until the annotation lands), `gate` (a gate it shares with a running phase), `areas` (its areas meet a running phase's; a phase without marks or with `confidence: "low"` is `**`), `slots` (the lanes in use reach `max_lanes`, or no slot is free). It returns null when nothing holds the phase, and the view then says `ready`. The order goes from the most certain reason to the least: a dependency always holds; the slots question is asked last because it costs git calls.
- **D5 The phase list.** The phase list comes from GSD (`loadPhases`: `gsd-tools init manager`, normalized as the supervisor reads it), which needs the GSD core found through the view's env. It is cached in `run/view-phases.json` for 60 s, keyed by `ROADMAP.md`'s mtime and size and by the set of lane keys. A lane that leaves or arrives therefore reloads it, so `finished` is current when a cleared lane is judged (D9). Nothing is read when the supervisor has finished, there is no lane or there is no `ROADMAP.md`. Any failure gives `next: null, finished: null`. The view never fails because of it.
- **D6 Siblings that may be missing.** `lib/view.mjs` loads `lib/slots.mjs` (L0) and `lib/lanes-file.mjs` (L3) with a top-level `await import`, only when the file exists next to it. A missing sibling reads as "no slots / no lanes file". A sibling that exists but throws on load is a real error and is not hidden. `buildView` and `runPlan` take `deps: { phases, lanesFile, slots }`, which tests use as stubs. `listSlots` runs git in every slot, so it is called only when nothing else holds the next phase and some lane has a slot.
- **D7 Layout.** **One lane:** v0.3's layout, line for line. The lane's head gains ` · lane <k>` when the lane has a slot. **Two or more lanes:** first `Run — <verdict>` in the verdict's colour, then the summary line (`3 lanes · 1 question · next: …`). Then one block per lane: the lane line (`Phase 34 · lane 2 — quality checks · 2 of 4 plans done · 25m`, no verdict tail: the verdict is on top) and its rows (now, sign of life, red CI, reason, helpers). The questions follow, then **What comes next** with only the owner's needs across all lanes (no chain of steps), no **Phase steps** section, the commits and the supervisor. **More than two lanes:** a block keeps its rows only while the lane is *alert*, and is otherwise its lane line. A lane is alert when it is stopped, failed, paused or held for full mode, when its CI is red, when a question of its phase is open, or, while the supervisor runs, when it or a helper of it is silent. A prep lane reads `Phase 35 · lane 3 — getting ready ahead: discussion`, an annotate lane `Lane 2 — working out which phases can run together`.
- **D8 Band.** With up to two lanes, each lane is listed as now. With more than two, `turbo · 3 lanes · <verdict> · ❓ … · CI …`: the band stays one line.
- **D9 Toasts.** Toasts come only from phase lanes (job `phase`, or no job in an older view). A prep or annotate lane never says "Phase N done". A phase lane that leaves the view counts as done only if the view's `finished` lists it, when the view carries `finished`. Without it (a v0.3 view, no phase list), the v0.3 rule stays. A slot lane released as failed therefore never toasts "done".
- **D10 Cards show the lane.** The pane's question card adds ` · lane <k>` to where the question comes from (`(plan 34-02, task 3 · lane 2)`) when the question's phase runs in a slot. The Telegram card title adds it too (`Phase 34 · lane 2 · plan 34-02, task 3`). Without slots, nothing changes.
- **D11 "Telegram lists the lanes"** means every owner notification (desktop and Telegram) ends with the run's summary line while two or more lanes run (`withRunLine`, `runLineFor`), plus D10. The bot gets no `/status` command: it polls Telegram only while a question is open (`telegramPart` returns before `pollUpdates` otherwise), and polling all the time would change every supervisor tick. That is out of this plan's scope.
- **D12 `turbo-run status`.** One line per lane: `lane <k>: phase 32 · session … · restarts … · mode … · since …`. A prep lane reads `prep of phase 35` and an annotate lane `roadmap annotation`; a v0.3 lane keeps exactly `lane: phase 4 · …`. A lane without a session yet reads `session starting` and gets no `watch:` line. Then the next-phase line in the config's language (`next: phase 36 waits for phase 34`). `status --json` gains `next`. These lines are technical (session ids stay), as before.
- **D13 Words.** Both copies (pane and `lib/view.mjs`) gain `lane`, `laneHead`, `lanesCount`, `questionsCount`, `job.prep`, `job.annotate`, `gate.<name>` for the four spec gates (others shown as written, cut at 30), and `waits.<kind>`, in English and Russian. Russian uses the plural (`3 полосы`, `5 полос`, `21 полоса`) and the case after `ждёт` (`ждёт фазу 34`). The owner reads no gate id and no slot path.
- **D14 Lane records** follow L1's `recordKey` (L1 plan D3): a phase job and the prep of that phase both use `run/p<N>.json` (L1 never runs both at once), and the annotate job uses `run/pannotate.json`. Steps come from `readProgress(root, <phase>)` for phase and prep jobs. An annotate lane has no steps, plans, push or "now" of its own.
- **D15 `areasMeet(a, b)`** is spec §6.3, written in `lib/view.mjs` to explain a wait. Static prefixes are taken before the first `*`, `?`, `[` or `{`, after `\` → `/` and without a leading `./`. They are compared segment by segment, and the segment a metacharacter cuts matches any segment that starts with it. The answer is conservative: "meet" when in doubt.
- **D16 Readers outside the supervisor.** `agentTail` searches the transcript folders of the root and of every lane (its slot's and its session's). `measureContext` takes the lane of the phase and searches from its slot. `activePhase(root)` takes the lane whose `slotPath` is `root`, or the single slot-less lane (checkout), and otherwise falls back to the newest unfinished run as before. `laneRuns` (`lib/cli-phase.mjs`), `laneRunning` (`lib/owner-tick.mjs`) and `lib/supervisor.mjs` stay L1's.

import path from 'node:path';
import { dirKey } from './paths.mjs';
import { comparePhase } from './scheduler.mjs';

// The work a lane holds (spec §5): a phase, the prep of a phase ahead of time, the roadmap annotation.
export const LANE_JOBS = Object.freeze(['phase', 'prep', 'annotate']);

const isObj = (v) => v !== null && typeof v === 'object' && !Array.isArray(v);
const idOf = (v) => (v === null || v === undefined || String(v).trim() === '' ? null : String(v).trim());

// One entry as every reader takes it: key and phase strings, job one of LANE_JOBS, slot a whole number from 1 or
// null, slotPath an absolute path or null; every other field as written. null for an entry nobody can show (not an
// object, or a phase or prep job without a phase). An annotate job has no phase.
function normalLane(key, e) {
  if (!isObj(e)) return null;
  const job = LANE_JOBS.includes(e.job) ? e.job : 'phase';
  const phase = job === 'annotate' ? null : idOf(e.phase);
  if (job !== 'annotate' && phase === null) return null;
  return {
    ...e,
    key: idOf(e.key) ?? String(key),
    job,
    phase,
    slot: Number.isInteger(e.slot) && e.slot >= 1 ? e.slot : null,
    slotPath: typeof e.slotPath === 'string' && path.isAbsolute(e.slotPath) ? e.slotPath : null,
  };
}

const rank = (l) => LANE_JOBS.indexOf(l.job);
const byLane = (a, b) => rank(a) - rank(b) || comparePhase(a.phase ?? '', b.phase ?? '') || (a.slot ?? Infinity) - (b.slot ?? Infinity) || a.key.localeCompare(b.key);

// supervisor.json's lanes as a list (Stage 4 L1 writes `lanes`, keyed <N>, prep-<N>, annotate; v0.3 and checkout mode
// write one `lane`): the non-empty `lanes`, else the one `lane` as a phase lane without a slot. Phases first (in phase
// order), then prep, then the annotation.
export function supLanes(sup) {
  if (!isObj(sup)) return [];
  const lanes = isObj(sup.lanes) ? Object.entries(sup.lanes).map(([k, e]) => normalLane(k, e)).filter(Boolean) : [];
  if (lanes.length) return lanes.sort(byLane);
  const legacy = isObj(sup.lane) ? normalLane(sup.lane.phase, { ...sup.lane, job: 'phase', slot: null, slotPath: null }) : null;
  return legacy ? [legacy] : [];
}

// The lane that works in dir (its slot path, compared by dirKey), else the lane of this job and phase; null for none.
export function laneFor(sup, { phase = null, job = 'phase', dir = null } = {}) {
  const lanes = supLanes(sup);
  if (dir) {
    const k = dirKey(dir);
    const own = lanes.find((l) => l.slotPath && dirKey(l.slotPath) === k);
    if (own) return own;
  }
  const p = idOf(phase);
  return p === null ? null : lanes.find((l) => l.job === job && l.phase === p) ?? null;
}

// The directory a lane works in: its slot, or root for a lane without one (checkout mode, v0.3). Its phase files and
// its Claude Code transcripts are there; its run files stay in the control root.
export const laneDir = (lane, root) => lane?.slotPath ?? root;

// Stage 4 (L4): why the next phase waits (spec §5). The supervisor decides; the view only explains, from the same
// inputs: GSD's phases, L3's lanes file (Areas, Gates), the lanes running and L0's slots.
export const WAIT_KINDS = Object.freeze(['deps', 'turn', 'marking', 'gate', 'areas', 'slots', 'ready']);
const arr = (v) => (Array.isArray(v) ? v : []);
const AREA_META = /[*?[{]/;

// A mask's static part: its path segments before the first metacharacter, and whether one cut the last segment.
function staticPart(mask) {
  const s = String(mask ?? '').replace(/\\/g, '/').replace(/^\.\//, '').replace(/^\/+/, '');
  const i = s.search(AREA_META);
  return { segs: (i < 0 ? s : s.slice(0, i)).split('/'), open: i >= 0 };
}

// Spec §6.3: two masks meet when one may match a path the other matches. The static prefixes are compared segment by
// segment; a segment a metacharacter cuts matches any segment that starts with it; a prefix that runs out first meets.
// Conservative: a false "meet" costs only parallelism.
export function areasMeet(a, b) {
  const A = staticPart(a);
  const B = staticPart(b);
  const n = Math.min(A.segs.length, B.segs.length);
  for (let i = 0; i < n; i++) {
    const x = A.segs[i];
    const y = B.segs[i];
    if (x === y) continue;
    const xOpen = A.open && i === A.segs.length - 1;
    const yOpen = B.open && i === B.segs.length - 1;
    return (xOpen && y.startsWith(x)) || (yOpen && x.startsWith(y));
  }
  return true;
}

// A phase's areas as the scheduler counts them: none, no marks or confidence low is ** (meets everything).
const areasOf = (m) => (m && m.confidence !== 'low' && arr(m.areas).length ? arr(m.areas).map(String) : ['**']);

// Why phase waits, first match: its lowest unfinished dependency in the milestone (deps); checkout mode, one phase at
// a time (turn); no fresh lanes file while a phase lane runs (marking); a gate a running phase holds (gate); areas that
// meet a running phase's (areas); every lane in use or no free slot (slots). null when nothing holds it.
// state: { phases, range, lanes (supLanes), lanesFile (readLanesFile), maxLanes, freeSlots (null: not looked at) }.
export function waitReason(phase, state = {}) {
  const n = String(phase);
  const st = isObj(state) ? state : {};
  const byNum = new Map(arr(st.phases).map((p) => [String(p.number), p]));
  const dep = arr(byNum.get(n)?.deps).map(String).filter((d) => byNum.has(d) && !isFinished(byNum.get(d))).sort(comparePhase)[0];
  if (dep !== undefined) return { kind: 'deps', other: dep };
  const lanes = arr(st.lanes).filter(isObj);
  const running = lanes.filter((l) => l.job === 'phase' && l.phase != null && String(l.phase) !== n);
  if (running.length && lanes.every((l) => !l.slot)) return { kind: 'turn', other: String(running[0].phase) };
  const file = st.lanesFile;
  const marks = isObj(file) && file.fresh === true && isObj(file.phases) ? file.phases : null;
  if (!marks && running.length) return { kind: 'marking' };
  const mark = (p) => (marks && Object.hasOwn(marks, p) && isObj(marks[p]) ? marks[p] : null);
  const mine = mark(n);
  const gates = new Set(arr(mine?.gates).map(String));
  for (const l of running) {
    const gate = arr(mark(String(l.phase))?.gates).map(String).find((g) => gates.has(g));
    if (gate !== undefined) return { kind: 'gate', other: String(l.phase), gate };
  }
  const areas = areasOf(mine);
  for (const l of running) {
    const theirs = areasOf(mark(String(l.phase)));
    if (areas.some((a) => theirs.some((b) => areasMeet(a, b)))) return { kind: 'areas', other: String(l.phase) };
  }
  const max = Number.isInteger(st.maxLanes) && st.maxLanes >= 1 ? st.maxLanes : 1;
  if (lanes.length >= max || st.freeSlots === 0) return { kind: 'slots' };
  return null;
}

// The next phase: the lowest unfinished phase of the range that no phase lane holds (a phase in prep counts), with
// why it waits, or kind ready; null when none is left.
export function nextWaiting(state = {}) {
  const st = isObj(state) ? state : {};
  const busy = new Set(arr(st.lanes).filter((l) => isObj(l) && l.job === 'phase' && l.phase != null).map((l) => String(l.phase)));
  const next = arr(st.phases)
    .filter((p) => isObj(p) && !isFinished(p) && inRange(String(p.number), st.range ?? null) && !busy.has(String(p.number)))
    .sort((a, b) => comparePhase(a.number, b.number))[0];
  if (!next) return null;
  const n = String(next.number);
  return { phase: n, ...(waitReason(n, st) ?? { kind: 'ready' }) };
}

export function cachedPhases(root, lanes, { env = process.env, now = Date.now(), load = loadRoadmapPhases } = {}) {
  let st;
  try {
    st = fs.statSync(path.join(root, '.planning', 'ROADMAP.md'));
  } catch {
    return null;
  }
  const file = path.join(runDir(root), PHASES_FILE);
  const key = { roadmap: [st.mtimeMs, st.size], lanes: arr(lanes).map((l) => String(l?.key)).join(',') };

// The run's next phase and why it waits, and the milestone's finished phases, for a run that goes on with lanes:
// { next: { phase, kind, other, gate } | null, finished: string[] | null }. Nothing is read for a finished run or one
// without lanes; anything that fails reads as unknown. listSlots runs git in every slot: it is asked only when nothing
// else holds the next phase and a lane has a slot.
export function runPlan({ root, sup, config = {}, env = process.env, deps = {} }) {
  const none = { next: null, finished: null };
  const lanes = supLanes(sup);
  if (!isObj(sup) || sup.finished || !lanes.length) return none;
  const phases = tryRead(deps.phases ?? ((r, l) => cachedPhases(r, l, { env })), root, lanes);
  if (!Array.isArray(phases)) return none;
  const state = { phases, range: isObj(sup.range) ? sup.range : null, lanes, lanesFile: tryRead(deps.lanesFile ?? LANES_FILE?.readLanesFile, root), maxLanes: maxLanesOf(config), freeSlots: null };
  let next = nextWaiting(state);
  if (next?.kind === 'ready' && lanes.some((l) => l.slot)) {
    const slots = tryRead(deps.slots ?? SLOTS?.listSlots, root, config);
    if (Array.isArray(slots)) next = { phase: next.phase, ...(waitReason(next.phase, { ...state, freeSlots: slots.filter((s) => s?.state === 'free').length }) ?? { kind: 'ready' }) };
  }
  const txt = (v) => (v === undefined || v === null ? null : clean(String(v)));
  return {
    next: next ? { phase: txt(next.phase), kind: next.kind, other: txt(next.other), gate: txt(next.gate) } : null,
    finished: phases.filter((p) => isObj(p) && isFinished(p)).map((p) => txt(p.number)),
  };
}

## Interfaces for L1–L3

L4 only reads. It writes nothing that L1–L3 read (its one file is its own cache, `run/view-phases.json`). Keep the following stable; any change goes through the Stage 4 controller so that `lib/sup-lanes.mjs` and `runPlan` follow.

**L1 — `supervisor.json`** (`<control root>/.planning/turbo/run/supervisor.json`)
- `lanes: { [key]: { key, job, phase, slot, slotPath, branch, sessionId, launchedAt, restarts, notified, mode } }` as L0 documents it, with key `<N>`, `prep-<N>` or `annotate`. L4 relies on these fields:
  - `job`: `'phase' | 'prep' | 'annotate'`; anything else reads as `phase`.
  - `phase`: the normalized phase id as a string; `null` only for `annotate`.
  - `slot`: a whole number ≥ 1.
  - `slotPath`: the absolute path the lane's session was launched in, exactly `slotPath(root, config, k)`. L4 finds the lane's transcripts under the Claude projects folder of this path and its plans under `<slotPath>/.planning/phases`.
  - `sessionId`: the job id that `claude --bg` printed, or `null` before the launch.
  - `launchedAt` (ISO), `restarts` (integer), `mode` (`'full' | 'safe'`).
  - `notified.downgraded` (truthy: held for full mode) and `forceRelaunch` (a resume pending), per entry, with the meaning they have on v0.3's `lane`.
- Checkout mode (`lanes.mode: "checkout"`) may keep v0.3's single `lane` (no `lanes`), or write `lanes` with `slot: null, slotPath: null`. Both read the same. A non-empty `lanes` wins over `lane`: write one of them.
- The top-level `pid`, `updatedAt`, `finished`, `halted`, `failingSince` and `range: { from, to }` keep their v0.3 meaning.
- An entry leaves `lanes` when its job ends. L4 calls a phase lane that left "done" only when GSD lists its phase as finished (`isFinished` on `gsd-tools init manager`). The order must therefore be: L2's `phase.complete` committed in `main`, then the entry dropped. A lane released as `failed` or `abandoned` may leave at any time.
- Lane records follow L1's `recordKey`: `run/p<N>.json` for a phase job and for the prep of phase N, `run/pannotate.json` for the annotate job. A record is fresh when written at or after the entry's `launchedAt`. A prep job's steps go through `phase-step <N>` (`run/phase-p<N>.json`), like `/turbo-phase`'s.
- `deps.notify(key, vars)` in `bin/turbo-run.mjs` `makeCtx` keeps that signature. L4 wraps its note with `withRunLine(…, runLineFor(root, config))` at the anchor `notify: (key, vars) =>`. Rewording the `phaseDone` body ("Moving on to the next phase.") for lanes stays L1's.
- `printStatus` in `bin/turbo-run.mjs`: L4 replaces its `sup.lane` branches with a loop over `supLanes(sup)` and adds the `next:` line; `status --json` gains `next`. L1 adds no lane lines there; on a merge conflict, L4's loop wins and keeps the per-entry `forceRelaunch` line.
- L1 owns the other readers of `supervisor.json.lane`: `lib/supervisor.mjs`, `laneRuns` in `lib/cli-phase.mjs` and `laneRunning` in `lib/owner-tick.mjs`. L4 updates `lib/view.mjs`, `lib/agent-tail.mjs`, `lib/context.mjs` (`measureContext`), `lib/phase-progress.mjs` (`activePhase`), `lib/telegram.mjs` (card titles) and `bin/turbo-run.mjs` (`printStatus`, `status`, the `notify:` line). L1 may import `supLanes`, `laneFor` and `laneDir` from `lib/sup-lanes.mjs` (pure, read-only) instead of writing its own.
- `waitReason` explains the scheduler's readiness rule (spec §5), in this order: deps → one phase at a time in checkout mode → annotation pending → gate → areas → no free slot. If L1's scheduler keeps its own overlap test, it must give the same answer as `areasMeet` (§6.3: static prefixes by path segments; a phase without marks or with `confidence: "low"` is `**`), or else export one function both use from a module that does not import `lib/view.mjs`.
