# gsd-turbo reference

## What it is

gsd-turbo is an overlay for [GSD](https://github.com/open-gsd/gsd-core) on Claude Code that runs a milestone faster with background Claude Code sessions. A small supervisor process (no LLM of its own) starts each remaining phase of the current milestone as an unattended background session, starts a fresh one when a session stops at its context limit, replaces full test runs with targeted ones where that is safe, and notifies you when a phase finishes or needs you. It does not modify GSD: it talks to GSD only through `gsd-tools` and GSD's own skills, agents and workflows, and it writes only a few documented GSD settings (see [GSD settings turbo writes](#gsd-settings-turbo-writes)).

This is v0.4.0 (stage 4 of the [roadmap](#roadmap)). Each phase runs as `/turbo-phase`: a freshness check, discuss in assumptions mode, a parallel planning prologue, GSD planning and execution, gates in parallel, fixes, a full test run, automated UAT and a done record. When a phase needs you, its checkpoints become clickable [owner questions](#owner-questions) you can answer ahead or at the stop (in your session, the [live view](#live-view) or [Telegram](#telegram-optional)), and the answer reaches the same waiting agent; any other stop of a phase reaches you as a question in plain words with options, and your answer wakes the phase. Lanes can [push and watch CI](#push-and-ci-optional), and you can [sit with a phase](#live-sittings) in your own session. Independent phases run at the same time, each in its own [lane slot](#lane-slots) (see [Several lanes](#several-lanes)); future phases are [prepared ahead](#prep-and-lane-markup), and the supervisor [merges](#merging-lanes-slots) each finished lane into your main branch.

## Requirements

- Node.js ≥ 20 and git.
- Claude Code ≥ 2.1.234 (background sessions: `claude --bg`, `claude agents --json --all`).
- For the live view in Claude Code (the `turbo-view` mod): Claude Code ≥ 2.1.290. With an older version the installer leaves the mod out, and `turbo-run status --watch` shows the run in any terminal.
- GSD core 1.16.x or 1.17.x, installed with `npx @opengsd/gsd-core@latest` (or `npx @opengsd/gsd-core@1.17` to stay inside the tested range). `turbo-run doctor` is tested against `>=1.16.0 <1.18.0`. A different GSD version, including newer minor and major releases, runs in safe mode if the other checks pass: doctor prints `FAIL gsd-version …` and then `mode: safe`. If `gsd-tools init manager` changed incompatibly, doctor reports `mode: unsupported` and the run does not start. `/turbo-phase` (whether the supervisor or you start it) needs full mode, which also needs the tested GSD range (see [Full and safe mode](#full-and-safe-mode)).
- Windows, macOS or Linux.
- Claude Code must trust the project folder: run `claude` in it once and accept the trust prompt. In a folder it does not trust, every background session fails to start; the supervisor then stops at the first attempt and notifies you.
- For automated browser checks (`turbo-uat`): Playwright (`playwright` or `@playwright/test`) installed in the project, with its Chromium browser. turbo never installs packages or browsers; without them, the items that need a browser go on your checklist.

## Install

```sh
git clone https://github.com/rnyqdz99yx-afk/gsd-turbo && cd gsd-turbo && node install.mjs
```

The installer copies files into your Claude Code config directory (`~/.claude`, or `$CLAUDE_CONFIG_DIR` when it is set):

- `turbo/`: the `turbo-run` CLI, its library and an install manifest;
- `skills/turbo-autonomous/`: the `/turbo-autonomous` skill;
- `skills/turbo-phase/`: the `/turbo-phase` skill, which a full-mode background session runs for its phase;
- `agents/turbo-uat.md`: the `turbo-uat` agent, which `/turbo-phase` starts for automated UAT.
- `skills/turbo-view/`: the `turbo-view` mod, the live view in your Claude Code sessions (see [Live view](#live-view)); only with Claude Code ≥ 2.1.290, otherwise the installer prints `turbo-view mod not installed: …`.

It never writes `gsd-*` paths. `node install.mjs --dry-run` shows only how many files would be installed and where, without writing anything.

To upgrade, first stop the supervisor in every project where one runs (`/turbo-autonomous stop` there): a running supervisor keeps the old code in memory, and its background sessions call the files the upgrade replaces. Then run `git pull && node install.mjs` in the gsd-turbo clone (a new install first removes the previous one) and start again with `/turbo-autonomous`.

## Uninstall

First stop the supervisor in every project where one runs (`/turbo-autonomous stop` there). Otherwise it keeps running from memory, its background sessions call a `turbo-run` that no longer exists, and GSD's test gates fail with `Cannot find module`.

Next, while `turbo-run` is still installed, put GSD's gates back in any project where a phase was interrupted with them off: run, from the project root, for each `p<N>.json` in `.planning/turbo/gates/` (nothing to do when that directory is empty or absent):

```sh
node "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/turbo/bin/turbo-run.mjs" gates restore <N>
```

and `gates docs-restore <N>` the same way for each `docs-p<N>.json` in `.planning/turbo/run/`.

Then run, from the gsd-turbo clone (the installer itself is not copied into your config directory):

```sh
node install.mjs --uninstall
```

`node install.mjs --uninstall --dry-run` shows how many files would be removed. Only files listed in the install manifest are removed, plus the whole `skills/turbo-view/` directory of the mod (with any files Claude Code wrote into it; a link there is left alone). Without a manifest in the config directory, the uninstaller prints `no gsd-turbo install manifest in <directory>` and exits with code 1 (check `CLAUDE_CONFIG_DIR`).

Projects keep their turbo files: `.planning/turbo/`, the last-green marker of the targeted tests (`turbo-last-green` in the git directory, usually `.git/turbo-last-green`; you can delete it) and, where `init` set it, the GSD setting `workflow.test_command`. In each project, from the project root, in a bash-compatible shell (Git Bash on Windows), check the setting:

```sh
node "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/gsd-core/bin/gsd-tools.cjs" config-get workflow.test_command
```

If it still calls `turbo-run`, restore it:

- If `turbo-run init` printed `kept previous workflow.test_command as test.full: <command>`, set it back to that command:

  ```sh
  node "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/gsd-core/bin/gsd-tools.cjs" config-set workflow.test_command "<command>"
  ```

- Otherwise, if `test.full` in `.planning/turbo/config.json` is the default `npm test`, clear the setting, so that GSD detects the test runner itself again instead of being pinned to `npm test`:

  ```sh
  node "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/gsd-core/bin/gsd-tools.cjs" config-set workflow.test_command ""
  ```

- Otherwise (you set `test.full` yourself), set it to the value of `test.full` with the first command. When `test.full` is a list, `workflow.test_command` takes one command: join the entries, for example `npm test && (cd server && npm test)`.

If GSD is installed inside the project, use `.claude/gsd-core/bin/gsd-tools.cjs` instead.

`planning.chunked_parallel: true`, which turbo sets when the key is absent, stays as well. It only affects GSD's chunked planning (`--chunked`); to remove it, run `config-set planning.chunked_parallel null` with the same `gsd-tools` call.

## Use

Inside a GSD project (a directory with `.planning/`), open Claude Code and run:

```text
/turbo-autonomous
```

If a run is already going, the skill shows its status and changes nothing. Otherwise it checks compatibility (`turbo-run doctor`), creates `.planning/turbo/config.json` on the first run (`turbo-run init`), commits only the setup files (`.planning/turbo/config.json`, `.planning/turbo/.gitignore`, `.planning/config.json`) and asks you what to do with any other uncommitted changes, so that the working tree is clean, and starts the supervisor. You can then close the session: the supervisor and the background sessions keep running. (Checked on Windows: the supervisor outlives the Claude Code process that started it.)

```text
/turbo-autonomous status          # supervisor state, current phase, session id, lane mode, range, owner requests
/turbo-autonomous stop            # stop the supervisor and this project's turbo background sessions
/turbo-autonomous resume <phase>  # after you handled an owner-only step or a halt: clear the phase and start again
/turbo-autonomous attend <phase>  # run the rest of a phase's plans in this session with you, then give it back to its lane
/turbo-autonomous answer          # answer the open owner questions (the plans' checkpoints), up to four at a time
```

A milestone that is already running on plain GSD moves onto turbo with `/turbo-adopt`, once, before the first `/turbo-autonomous`: it shows where every phase stands, asks its questions at once, applies its changes in one commit after one confirmation, and ends with a report and the `/turbo-autonomous` command; it never starts the run itself. See [Adopting a running milestone](#adopting-a-running-milestone).

`resume <phase>` counts as your answer to that phase's owner request: it removes `.planning/turbo/run/p<N>-owner.md`, and the phase writes it again only when something is still open for you. Until the supervisor's next check, status shows the resumed lane as `relaunch pending (resume)` with the session it replaces, not as a session to watch. With several lanes (`lanes.mode` `slots`) and the supervisor running, `resume <phase>` (with or without `--start`) never stops the supervisor: it hands the phase to it (`phase <N>: handed to the running supervisor …`), status shows `resume asked: the running supervisor relaunches it at its next check`, and at that check the supervisor clears the phase and relaunches its lane while the other lanes go on. Otherwise `resume` stops a running supervisor first and you start it again (`turbo-run start`, or `resume <phase> --start` in one command).

To run only part of the milestone, give a phase range when you start:

```text
/turbo-autonomous --only <N>           # phase N only
/turbo-autonomous --from <N> --to <M>  # phases N to M; either flag alone leaves that end open
/turbo-autonomous --all                # every remaining phase again, clearing a kept range
```

The range is inclusive and ordered the way GSD orders phases (`2` < `2.1` < `2A` < `3`), so `--only 2` does not include `2.1`. Only phases inside it are started. A dependency on a phase outside the range counts as met only when that phase is complete or closed; a dependency on a phase outside the milestone always counts as met. When nothing in the range can start because a phase waits on an unfinished phase outside it, the supervisor stops, logs one line and notifies you ("Phases 4–6 are waiting": phase 4 depends on phase 3 outside the range); run that phase first (`--only 3`) or widen the range. `--only` together with `--from` or `--to`, `--all` together with any of them, or `--from` after `--to` is a usage error, and nothing starts. `start` prints the range it uses once (`range: phases 3–5`, with `(kept from the previous run)` when it carried over), and status shows it. A run that was stopped or halted keeps its range for the next start (`resume <phase> --start` included); the range of a finished run is dropped. When every phase of the range is finished, the supervisor stops and notifies you. If the recorded running phase lies outside a new range, it is not resumed and its session is left alone. If no phase of the milestone falls in the range, the supervisor waits and says so in its log.

Range changes never touch a run that is going:

- `start` with `--from`, `--to`, `--only` or `--all` while the supervisor runs exits with code 1, names the running range (`a run of phases 4–5 is going (supervisor pid …)`, or `the whole milestone`) and changes nothing: run `turbo-run stop` first. `start` without range flags still just reports the running supervisor.
- `resume <N> --start` for a phase outside the range the next start would keep exits with code 1, names that range and how to change it (`turbo-run start --only <N>`, or `--from`, or `--all`; with `turbo-run stop` first when the supervisor runs). Nothing is stopped, removed or started.
- Two starts at the same moment: the one that loses says which supervisor runs and its range (`another start launched supervisor pid … first (phases 4–5)`); it exits with code 1 only when it was given range flags for a different range.

To watch a phase live, run `claude attach <session id>` (the id is in the status output); detaching leaves the session running. The supervisor log is `.planning/turbo/logs/supervisor.log`.

The same commands work without the skill, in a bash-compatible shell (Git Bash on Windows):

```sh
node "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/turbo/bin/turbo-run.mjs" doctor   # also: init, start [--from <N>] [--to <N>], start --only <N>, start --all, status [--watch], view [--json], stop, resume <phase> [--start], autostart on|off|status, context [<phase>] [--json], adopt scan|plan|reverify|apply
```

Below, `turbo-run` stands for this `node …/turbo-run.mjs` call; the installer does not put it on your PATH. Its other subcommands, such as `phase-step`, `staleness`, `gates`, `jobs`, `uat`, `lane-status`, `integrate`, `state-sync`, `context` and `test-changed`, are the deterministic steps the supervisor and the sessions call. You need them only for recovery: `turbo-run gates restore <N>` ([GSD settings turbo writes](#gsd-settings-turbo-writes)), `turbo-run lane-status <N> done` ([Full and safe mode](#full-and-safe-mode)) and `turbo-run state-sync <N>` ([Context and the resume position](#context-and-the-resume-position)).

To see a run at a glance, run `turbo-run view`. It shows the supervisor and its range; for each lane, its phase, its current `/turbo-phase` step, its status, session id and running time; the lane's subagents with their type, plan, current action, time and context tokens; open owner questions; and the last five commits. A subagent counts as `completed`, `stopped` or `failed` only once Claude Code has reported this to the lane session. Until then it is `running` while its transcript keeps being written or a command it runs (Bash, PowerShell) is within its timeout (the call's `timeout`, else 10 minutes, plus 2 minutes for Claude Code to write the result: a transcript gets nothing while a call runs), and `quiet` after `stall_minutes` without a write, or once such a command ran past its timeout with nothing written since. A lane is silent by the same rule over its whole session tree, its own transcript and every subagent's at any depth; a lane busy with a command that has run for a minute or more shows `a long command is running · 6m` instead of its last activity. `quiet` itself is only a mark: nothing is stopped or restarted because of it. `turbo-run view --json` prints the same information as one JSON object. The command reads Claude Code's transcripts and job state under `${CLAUDE_CONFIG_DIR:-~/.claude}` and turbo's run files, and changes none of them. It keeps a cache in `.planning/turbo/run/view-cache.json` and masks secrets in everything it prints. With several lanes (v0.4) it lists every lane with its phase, its slot (lane 1, 2, …), its step and helpers, read from the lane's slot, and says which phase comes next and why it waits, as the supervisor decided it (`supervisor.json` `next`): for a phase it depends on, for a phase that changes the same files or uses the same shared resource, for a free lane, until turbo has worked out which phases can run together, or for a phase whose merge waits. For a phase you attend (see [Live sittings](#live-sittings)) it reads your sitting instead of the stopped lane: the lane's last activity and subagents are those of the session the attend mark names (its subagents since the mark; the first read of its transcript looks at its last 2 MB only), `sitting` in `--json` holds that session's id (null when turbo does not know it), its own tool call in flight (`action`, else null) and how many of the phase's open questions it holds (`questions`): they are left out of `questions` until the hand-back. turbo-run keeps the transcript it found for the session in its view cache.

To run a single phase without the supervisor, run `/turbo-phase <N>` in Claude Code, in a clean checkout. It needs `turbo-run doctor` to report `mode: full`; otherwise it stops at once.

The background sessions work in your checkout. Each lane runs with `worktree.bgIsolation: "none"` passed to its session, so it edits the project folder directly, as GSD expects; your own settings are not changed. Do not run GSD phase commands in the same checkout while the supervisor is running.

Each lane also gets its own temporary directory under turbo's own directory, outside the checkout and its git directory: `~/.claude/turbo/tmp/<project key>/p<N>/` (`CLAUDE_CONFIG_DIR` moves it with the rest of `~/.claude`, and when that directory lies inside the project the lane gets `<system temp>/gsd-turbo/tmp/<project key>/p<N>/` instead, noted in the supervisor log; the key is a 16-hex hash of the project root, so two GSD projects never share it), so linters and type checkers that glob the tree never see it, nothing in it can be committed, and a project test that checks that the system temp directory lies outside its checkout passes inside a lane too. The supervisor creates it before the launch, after removing what an earlier session of the phase left there; the same `--settings` set `TMP`, `TEMP` and `TMPDIR` of the session to it, and the lane's rules say that temporary files, stands and copies of data go there, never to `/tmp` or the system temp directory (in Git Bash on Windows `/tmp` stays the system temp directory whatever `TMP` says), and that nothing else of the session's goes outside the checkout: not the home directory, not next to the checkout, not in a folder above it. GSD's TDD RED evidence record, which GSD reads only from inside the project, goes under `.planning/turbo/run/tdd/` in the checkout, which git ignores. Subagents never see the lane's rules, so the lane adds that rule, unchanged, to every subagent prompt (GSD's executors, planners and the others), and each passes it on. The supervisor removes it once it has finished the phase and removed the session; `lane-status <N> done` does not, because the session may still use it (Claude Code's own scratch files and GSD's hook files can live there). Only that one directory is ever removed: a `p<N>` that is a link or resolves elsewhere, and a `turbo/tmp` or `turbo/tmp/<project key>` that is a link, are refused and logged.

The rule has a mechanical half, the lane's write guard (`lanes.write_guard`, on by default). The same `--settings` give the lane session a `PreToolUse` hook (`node …/lib/lane-guard-hook.mjs`, no dependencies, about as fast as `node` starts) that Claude Code runs before every `Write`, `Edit`, `MultiEdit` and `NotebookEdit` of the lane and of all its subagents. It denies a write to any path outside the lane's checkout (its slot, or your checkout for a `checkout`-mode lane), its temporary directory and, for a lane in a slot, your checkout's `.planning/turbo`, where the slot's turbo state lives; the denial tells the agent to write temporary files to its temporary directory instead. Paths are compared by their real location: a link or junction is followed, an 8.3 short name and a Git Bash path (`/c/Users/…`) mean the same folder as the long one, and on Windows case does not matter. A call the hook cannot read is allowed, so a broken guard never stops a lane. Claude Code's own auto-memory writes from a lane (under `~/.claude`) are denied too, which is harmless: a lane needs no memory of its own. A project or user setting `disableAllHooks: true` turns the guard off along with every other hook. The guard does not see Bash: a redirect or a script that writes a file passes it. For that, while lanes run, the supervisor looks at the folders right around the project after every check: the folder above it and, with slots, the slots folder and the folder above that. A new entry there since the first running lane started whose name looks like a lane's scratch file (GSD's executor folders `exec-<phase>-<plan>`, and `capture*`, `red-*` or `mut-*` files with a script, data, log or text extension such as `capture-red.mjs` or `red-t1.json`; a `Capture.PNG` is not one) is written to the supervisor log once, and you get one notification, «Files appeared next to the project». Other new entries there (most likely your own files) are only counted in the log, never named. turbo never moves or deletes them: the folder is yours (on a Desktop, say), the file may be yours or still in use, and the lane's temporary directory, the only place to move it to, is deleted when the lane ends.

### Live view

With Claude Code 2.1.290 or newer, the installer adds the `turbo-view` mod to `skills/turbo-view/` in your config directory. Claude Code loads it in every session as `turbo-view@skills-dir`, without a marketplace or a settings change. Outside a project with `.planning/turbo/` it does nothing. In such a project it runs `turbo-run view --json` every `view.refresh_seconds` seconds (every 15 seconds in a background session no terminal is attached to; never in `claude -p` runs), starting when a session starts or resumes (in a folder Claude Code trusts), at the first draw of the prompt or at `/turbo-view`, and shows (a session no terminal is attached to gets no pane and no toasts):

Everything is in plain words, in `lang` (English or Russian), with the verdict first and coloured by it (your theme's colours: green when all is fine, amber when an answer waits or a phase is silent, red when CI is red or a phase or the supervisor stopped):

- a band above the prompt, for example `turbo · phase 32: running plans 5/9 · ❓ 1 question waits for you · CI ✓`;
- a pane in sections. First the verdict line, for example `Phase 32 — running plans · 5 of 9 plans done · 1h 12m · needs your answer (1)`: the phase, its `/turbo-phase` step in words, its plans done and how long it runs, then one verdict that says whether you have to step in (all fine; needs your answer; CI red that the phase fixes itself, attempt 1 of 2, nothing needed from you; CI red that needs you; a silent phase or helper; the supervisor failing, stopped or not running; a phase in your own session). A phase that is not running says what happened first, for example `Phase 32 stopped — waits for your answer · step: plan execution · 5 of 9 plans done · 1h 12m`, `Phase 32 paused: needs a fresh context` or `Phase 32 done · took 1h 12m`; while the supervisor does not run, the phase reads `stopped at step: …`, its time stops at its last activity and nothing is called stuck. A phase you attend (`turbo-run attend <N>`) reads `Phase 32 is running in your session · 5 of 9 plans done`, neutral, and it is never counted as needing you: what its stopped lane left (its stop, its step, its last activity, its helpers) is not shown. Under it the pane reads your sitting, the session that ran `attend` (the mark names it): what it does now (`Now: writing code for a plan`, or its own call in flight: `Now: waits for your answer in the session` while it asks you, `Now: working` for a tool without words), its last activity over its transcript and its helpers' (dim, never a silence: you may be thinking or away), and its helpers at work; no phase steps (they would be the stopped lane's). A sitting whose session turbo does not know shows the line alone. Its questions are the sitting's, asked in your session: the pane, the band and Telegram leave them out, nothing answers them automatically, and they come back with `attend <N> --done`. While any wait, a dim line under the phase counts them and says how to go on (`2 questions of the phase in your session · go on: /turbo-autonomous attend 32 · give the phase back: turbo-run attend 32 --done`; a sitting paused or cut off keeps them), and **What comes next** says they wait in your session (or that your session waits for your answer) instead of `Nothing needed from you now`. While attend has stopped the supervisor and nothing else runs, its line reads `Supervisor paused: phase 32 is running in your session`. A phase past its planning whose planner works again reads `planning gap fixes` (`Now: writing plans to close the gaps the checks found`). Under it, indented: what the phase does now, in words (`Now: fixing the red CI — attempt 1 of 2`, `Now: reviewing the code`, `Now: writing code for 2 plans at once`, `Now: waiting for CI`, or its step, `Now: running the final tests`), the last activity (`last activity 20s ago`), a red CI that needs you and the verdict does not mention (one the phase fixes itself is said by `Now`, and only while the supervisor runs), the reason a phase stopped, the helpers at work and what each does (`Executor · plan 32-07, task 2 · editing lib/export.mjs · 6m`, `running tests`, `a long command is running · 6m` while a command runs within its timeout; one silent for `stall_minutes` reads `⚠️ Verifier silent for 16m`), and the finished ones as one count. A silent phase says what turbo did about it, never that it may be stuck: `silent for 17m — turbo is waking the session`, `— woke the session, waking it again` (or `restarted the session`, `could not wake the session`), and, once two wakes brought no answer, `— waking the session did not help: needs you` with what to do under **What comes next**. Then **Needs your answer**: each open question in its own card, the one the phase waits for first and red (`The phase waits for this answer`), the others marked that you can answer them ahead; the question in bold with its plan and task, its context, a row of buttons, one per option with its number and text (`[1. Yes, by the gate ★]`, the recommended option marked), and **Your own answer…** on a row of its own; an option too long for its button is cut there and listed in full above the buttons, with its description when it has one. Then **What comes next**: the steps ahead (`fixes → final check → acceptance → wrap-up → next phase`, or `end of the run` for the last phase of the range, or for the last unfinished phase of a run without one) and when you are needed, from what turbo knows: the question the phase waits for, a stop for your decision or by a failure, full mode, questions you can answer ahead, the last CI attempt (it asks you next); otherwise `Nothing needed from you now`, in green. Then **Phase steps**, the `/turbo-phase` steps done (`✓`), now (`▶ quality checks — now`, also `▶ merge into main — now` while the supervisor merges a finished lane, or where a stopped phase stopped, `■ acceptance — stopped here`) and ahead. Then the latest commits counted by kind, never their subjects, which are the project's own text and jargon (`Latest changes: 2 fixes, 1 new feature · latest 12m ago`; `turbo-run view --json` keeps the subjects), and the supervisor. The pane opens by itself while the supervisor runs, a question is open or a lane is recorded and not done (after a crash or a reboot, the supervisor that died with the machine left its lanes behind; a run you stopped with `turbo-run stop` opens it only for a question), also right when a session starts or resumes in the project (`claude --resume`, `claude -r`), not only at the first draw of the prompt. Claude Code places a pane a mod opens by itself only in a terminal at least 144 columns wide (110 once you have opened it); in a narrower one the band ends with `open the pane: /turbo-view`, and your next message typed in the session opens the pane at any width, once (docked beside the transcript from 110 columns, else above the prompt), as `/turbo-view` does. A pane you close by hand stays closed until you run `/turbo-view`;
- toasts for a new question, a finished phase, red CI (and whether the phase fixes it itself), a phase that stopped, a stopped supervisor, and what became of your answer: `Answer recorded: “Stop” · 08:18` (your local time; `not committed to git: …` when it could not be committed), already answered elsewhere (where and when), the question changed, or not recorded and why (it looked like a secret, it was too long).

A button runs `turbo-run answer --project <project> <phase> <id> --option <n> --by pane --rev <r>`, where `<r>` is the question's revision as the pane showed it; **Your own answer…** opens a field whose text goes last, as `--text <your answer>`, so a text that reads like a flag stays text. The mod runs turbo-run with the `node` it finds in an absolute `PATH` directory and in turbo's install directory, never in the project. The first answer from any channel counts, and the toast says in words what the command did. If the question changed since the pane showed it, nothing is recorded: the toast says so, the pane reads the run again, and **Your own answer…** brings back what you typed. The mod runs nothing but these two `turbo-run` commands and writes no files.

**Several lanes (v0.4).** While two or more lanes run, the pane starts with the verdict (`Run — needs your answer (1)`) and one line for the whole run: `3 lanes · 1 question · next: phase 36 waits for phase 34`. The next phase can wait for a phase it depends on, for a phase that changes the same files (`— they change the same files`) or needs the same shared resource (`— both need the deploy`), for a free lane, until turbo knows which phases can run together, or for another phase to be merged. Then each lane gets a block: `Phase 34 · lane 2 — quality checks · 2 of 4 plans done · 25m`, with what it does now and its helpers under it; a lane that prepares a phase ahead reads `Phase 35 · lane 3 — getting ready ahead: discussion`, and the lane that marks the roadmap `Lane 2 — working out which phases can run together`. A lane the supervisor stopped alone reads `Phase 34 · lane 2 stopped — the other lanes go on` (resume it with `turbo-run resume 34`), and one whose work is done while it is merged into `main` reads `done — being merged into the main branch`. With more than two lanes a calm lane is one line, and a lane opens when a question of its phase waits, it stopped, its CI is red, or it or a helper is silent. The question of the lane markup (which dependencies to relax) is titled `lane markup` in the pane and `Lane markup` in Telegram. **What comes next** then says only when you are needed, and the phase steps are left out (each lane line names its step). A question card says which lane its phase runs in (`plan 34-02, task 3 · lane 2`), and so does its Telegram message (`Phase 34 · lane 2 · plan 34-02, task 3`). The band lists up to two lanes and counts them beyond (`turbo · 3 lanes · …`). Toasts come from phase lanes only; a phase in a lane says `Phase 34 done` once it is merged into `main`, never when its lane is released after a failure. Every notification (desktop and Telegram) ends with the run's line while two or more lanes run. To see it without a run: `node scripts/turbo-view-demo.mjs --lanes 3`.

To turn the mod off, set `"turbo-view@skills-dir": false` under `enabledPlugins` in your Claude Code settings. Without the mod, `turbo-run status --watch` shows what `turbo-run view` shows (the pane's words, verdict and sections in `lang`, each question with its options listed), in any terminal, coloured by state like the pane (green, amber, red, dim) when it writes to a terminal and `NO_COLOR` is not set, and redraws it every `view.refresh_seconds` seconds until you press Ctrl+C; its footer follows `lang` too. In a terminal it redraws in place; into a pipe or a file it prints a new frame only when the view changed. Git Bash's mintty is not a terminal to Node without ConPTY, so there it prints like into a pipe: for a live redraw run it through `winpty` or use PowerShell or Windows Terminal.

To see the mod without a real run, run `node scripts/turbo-view-demo.mjs` (or `node scripts/turbo-view-demo.mjs --lang ru`) in the gsd-turbo clone. It builds a demo project with a scripted run in a new temporary folder and prints the command that opens it in Claude Code, and what to check: the pane, the band and the toasts as the mod draws them. The script repeats every 16 reads; from the second round on its questions say so (`Demo, round 2: …`), so a question you answered and see again is no lost answer.

## What happens

- **One background session per phase.** The supervisor picks the next phase (inside the range, when one is set) whose dependencies are complete and starts it with `claude --bg`. A phase checked off in the ROADMAP and fully implemented counts as complete here even when GSD reports it unfinished, for example because a later phase changed files its verification covers and GSD now marks that verification stale: it is never started again, and the phases that depend on it can start. The supervisor log names such phases once per set (`skipped phases 3, 4: checked off in the roadmap, GSD reports them unfinished (verification stale); …`); you are not notified. A phase that GSD checks off while its session runs keeps running to its usual end. In full mode the session runs `/turbo-phase` for that phase (see [Inside a phase](#inside-a-phase-turbo-phase)); in safe mode it runs GSD's `gsd-autonomous` skill for that phase only, as in v0.1 (see [Full and safe mode](#full-and-safe-mode)). In safe mode the next phase starts when GSD marks the phase complete; in full mode, when the session has also written its own done record at the end of `/turbo-phase`. With `lanes.mode: "checkout"` phases run one at a time; with slots, see [Several lanes](#several-lanes).
- **Automatic continuation after context limits.** Each session runs `turbo-run context <N>` before each step and, when it reports `context_stop_pct` percent or more, commits, runs `gsd-pause-work`, records its position in STATE.md (`turbo-run state-sync <N>`) and ends; the supervisor then starts a fresh session that resumes from the state on disk. Sessions never estimate their context by hand (see [Context and the resume position](#context-and-the-resume-position)). In full mode `/turbo-phase` checks this before each of its steps, and the fresh session resumes at the next unfinished step, recorded in `.planning/turbo/run/phase-p<N>.json`. A session that has finished its turn counts as ended, also while Claude Code still lists it as `blocked`. If it ended its turn without recording what comes next (no lane record of its own, and GSD shows the phase neither complete nor, in safe mode, waiting for human verification), it waits, and you are notified after `blocked_minutes_before_notify`. A session that is gone, or that Claude Code lists as ended (`done`, `idle`, `stopped`), before the phase is complete and without failing is resumed the same way. A failed session stops the run and notifies you, except when a supervisor starts: a lane session that ended or is gone before it started (a reboot or a crash took both down, or the run halted on it) is relaunched as a continuation, as `resume <phase> --start` does, with a fresh count of restarts (see [After a crash or a reboot](#after-a-crash-or-a-reboot)). After `max_restarts_without_progress` restarts in a row with no new commit and no new plan summary, the supervisor stops and notifies you.
- **When a session cannot start or looks unfamiliar.** A failed `claude --bg` launch is retried at the next check; after 10 failed launches in a row the supervisor stops and notifies you. The count starts again with every supervisor start (`start`, or `resume <phase> --start` when it starts one). A session in a state the supervisor does not recognize counts as waiting: it is neither replaced nor relaunched, and you are notified after `blocked_minutes_before_notify`. If the running phase disappears from the roadmap, the supervisor stops once its session has ended or finished its turn, and keeps that session for inspection; if no remaining phase can start because they all wait on each other (a dependency cycle), it notifies you once and keeps checking; if no phase of the run's range can start because one waits on an unfinished phase outside the range, it stops and notifies you. A folder Claude Code does not trust stops the run at the first attempt.
- **Targeted tests.** `turbo-run init` points GSD's `workflow.test_command` to `turbo-run test-changed` only when a full test command is known: your previous `workflow.test_command` (kept as `test.full`), a `test.full` you set yourself (other than the default `npm test`), or `npm test` where GSD would pick it itself (a root `package.json` with a `test` script, and no Xcode project, no Makefile with a `test:` target and no Justfile, which GSD prefers). Otherwise init leaves `workflow.test_command` alone, GSD keeps detecting the test runner, and init prints how to enable targeted tests. Wherever GSD runs its test command (after each wave and in the phase's regression gate), turbo runs only the tests related to the files changed since the last full green run. With `test.import_graph: true`, a targeted run also includes the tests that loaded a changed JavaScript module in the last full green run, through other modules or import aliases; the graph never turns a full run into a targeted one. It falls back to the full suite whenever the selection could be unsafe, for example: not a git repository or no commit yet, no full green run yet, uncommitted or untracked files, changed dependency or config files, changes in a nested package that no `test.full` entry runs or outside the project root, a test command it cannot mirror exactly (`test.full`, or each entry of a `test.full` list, must be its package's test script, and that script a plain `node --test`, `jest` or `vitest` call without `pretest`/`posttest` hooks; pytest projects always run in full), a selected test outside the runner's default test match, a changed file with no related test, or `test.max_targeted` targeted runs since the last full run. `TURBO_FULL=1` forces a full run. When nested packages have their own test scripts, list them in `test.full`, so that the full run covers them too; each is then planned on its own (see [Several packages in `test.full`](#several-packages-in-testfull)). Every full-mode phase also ends with a full run (see [Inside a phase](#inside-a-phase-turbo-phase)). To enable targeted tests where init did not, set `test.full` to your full test command (see [Config](#config)) and run `turbo-run init` again. Running `turbo-run init` again is safe: it keeps `.planning/turbo/config.json`, including `test.full`, unless `workflow.test_command` was changed to another command: that command becomes `test.full`. If `workflow.test_command` already calls `turbo-run`, init keeps it: it sets it again when a full command is known and, when none is, warns instead of changing it.
- **Notifications.** A desktop notification (and optionally Telegram) when a phase is done, the milestone is complete, every phase of the range is done ("Phases N–M done", when the run has a range), a phase needs you, a phase leaves you a checklist of live checks (once per phase, and again only when the checklist changes), a full-mode phase waits because doctor now reports safe mode, a session waits for input or fails, a phase stops making progress, a session cannot be started (10 failed launches in a row), the running phase is no longer in the roadmap, no phase can start because the remaining ones wait on each other, no phase of the range can start because one waits on an unfinished phase outside it ("Phases N–M are waiting"), the project folder is not trusted by Claude Code, or the supervisor itself keeps failing or stops on an error. When the run stops for a phase, the notification ends with the command that continues it: `/turbo-autonomous resume <phase>`.

### Context and the resume position

`turbo-run context [<N>] [--json]` measures a session's context from its Claude Code transcript (`projects/<folder>/<session id>.jsonl` under `${CLAUDE_CONFIG_DIR:-~/.claude}`): the prompt side of the last main-session assistant message, `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, against `context_window` from `.planning/turbo/config.json` (default 1000000). It measures the calling session: the transcript named by `CLAUDE_CODE_SESSION_ID` (set in a Claude Code session's Bash tool); else the one the calling background job writes now (`CLAUDE_JOB_DIR`'s `state.json`: a job woken again writes into a transcript with a new id); else, with a phase whose lane `supervisor.json` records, that lane's job; else the most recently modified transcript whose entries carry a `cwd` inside this project's root (subfolders and Git Bash's `/c/…` form included). Only the end of the file is read. It prints `context: 270000 of 1000000 tokens (27%)`, or `context: unknown (<why>)`, and exits 0 either way; `--json` gives `used`, `window`, `pct`, `sessionId`, `transcript` and `source` (`session`, `job`, `lane` or `newest`), or `unknown`. A session stops at `context_stop_pct` by this number only, never by its own estimate and never by GSD's `context_window`; `unknown` means go on. Wherever GSD's execute-phase runs inside a step (`execute`, and its re-runs in `final-gate` and the `uat` gap round) it checks before each wave or plan as well, and at the stop percentage finishes the current plan or wave and pauses without marking the step done. The output names the window it assumed: when `lane_model` (or your default model) has a smaller context window than 1000000 tokens, set `context_window` to it.

GSD sizes some prompts by its own `context_window` (at 500000 or more its executors also get the phase's context, research and earlier summaries), 200000 when `.planning/config.json` sets none. `turbo-run init` sets it to turbo's `context_window` when it is absent and says so; a value you set stays. `turbo-run doctor` prints a `warn context-window` line when the two differ.

GSD's execute-phase starts with `state.begin-phase`, which on a phase already in progress resets STATE.md's plan to 1 unless STATE.md's `Status` contains `Executing Phase <N>`; plan-phase's `planned-phase` turns the phase line into `READY TO EXECUTE`. Every lane resume runs execute-phase again, so after every stop (the context pause, `needs-owner`, `failed`) and at the end of the `execute` step, a session runs `turbo-run state-sync <N>`. It writes the real position with GSD's own commands (`phase-plan-index`, `state patch`, `state record-session`, `commit`, which follows `commit_docs`): the phase line `<N> (<name>) — EXECUTING`, `Plan: <next> of <total>` (and `Current Plan` / `Total Plans in Phase` where STATE.md has them), the `Executing Phase <N>` marker in `Status`, `Stopped at`, and `Resume file` (the `.continue-here.md` that `gsd-pause-work` wrote when it is newer than the phase's newest SUMMARY, by commit time or else modification time; otherwise the next plan). The next plan is the plan without a SUMMARY in the lowest wave (GSD's waves follow `depends_on`; the lowest number on a tie), and `Plan` counts the plans done plus one.

- Your words in STATE.md stay. state-sync never writes `Last activity`. A `Status` that GSD wrote (`Ready to execute`, `Paused`, for example) becomes `Executing Phase <N>`; a `Status` with your own text keeps it and gets the marker at its end, `<your text> (Executing Phase <N>)` (a marker at its start, `Executing Phase <N> — <your text>`, moves to the end): there begin-phase still finds it, and GSD's `advance-plan` and `planned-phase` leave your text alone. A `Status` that already reads so is not touched. GSD copies a `Status` with your text into the frontmatter's `status:` as it is, instead of a word like `executing`.
- begin-phase itself writes `Status: Executing Phase <N>` and `Last activity: <date> — Phase <N> execution started` (or `… execution resumed (wave continue)`) over whatever was there, on every run. When STATE.md shows those lines (or the `… stopped; next plan <id>` that state-sync wrote up to 0.3.1), state-sync takes each of them back from the newest of the last 50 commits of STATE.md (`HEAD` first) where that line is not begin-phase's, when it holds your words (a value GSD wrote itself, such as `Ready to execute` or `<date> — Phase <N> marked complete`, is nothing to put back). Its output names the fields it changed.
- GSD's `state patch` rewrites the first bold `**Field:**` line anywhere in STATE.md, else the first `Field:` line, else a two-cell table row. state-sync sends a field only when that first match lies inside the Current Position section, and names the fields it left out (an archive's `**Phase:**`, for example).
- With every plan summarized there is nothing to resume, but a re-run of execute-phase (final-gate's, for example) still runs begin-phase, which sets the plan back to 1. When begin-phase's `Status` line is there, state-sync puts back `Plan: <total> of <total>` (and `Current Plan`), `Status` (your words as above, else GSD's `Phase complete — ready for verification`) and `Last activity` (your words as above); the phase line stays as begin-phase wrote it (the phase, executing). It records no session, and commits `docs(phase-<N>): put back the STATE.md position that begin-phase reset`. Without that line it changes nothing.
- It changes nothing with no plans yet, or before execution started (no SUMMARY yet and step `gates-off` not done): then `begin-phase` must take its first-run branch.
- It is best effort: a failing GSD command or commit (a held `index.lock`, for example) prints a `warn:` line, puts STATE.md back to the bytes it had before (a clean STATE.md stays clean; one that already had uncommitted changes keeps them, so it stays dirty), and exits 0. The callers never stop on it.

turbo never calls `begin-phase` itself, and `planned-phase` only where GSD's plan-phase would have: after the plan step's checker pass that follows an interrupted planning, before execution starts (see [Inside a phase](#inside-a-phase-turbo-phase)).

### Full and safe mode

`turbo-run doctor` prints one line per check, a `warn` line per warning (see [Several packages in `test.full`](#several-packages-in-testfull); warnings do not change the mode), then the mode. `start` runs the supervisor in that mode, and the `lane:` line of `/turbo-autonomous status` shows the mode of the running phase.

- `mode: full`: GSD core in the tested range (`>=1.16.0 <1.18.0`), the installed `turbo-phase` skill (check `turbo-phase-skill`) and `turbo-uat` agent (`turbo-uat-agent`), and a working `gsd-tools loop render-hooks` (`gsd-render-hooks`). Each phase runs as `/turbo-phase`.
- `mode: safe`: one or more of those checks prints `FAIL`, and every other check passes. Each phase runs `gsd-autonomous --only <N>` as in v0.1. Before that, the session runs `turbo-run gates restore <N>` and `turbo-run gates docs-restore <N>`, which put back what an interrupted `/turbo-phase` run left switched off (they do nothing otherwise).
- `mode: unsupported`: node, git, Claude Code, the project, GSD core or `gsd-tools init manager` fails; the run does not start.

If doctor (which runs when the supervisor starts) drops from full to safe while a phase that GSD already marked complete has not finished turbo's gates and UAT, the supervisor does not relaunch that phase: `gsd-autonomous` would end at once on the completed phase and skip them. You get one notification ("Phase N waits for full mode") with two ways out: fix what `turbo-run doctor` reports, then run `/turbo-autonomous resume <N>`; or do the remaining `/turbo-phase` steps (restore, fanout, fix, final-gate, uat) by hand (the skill itself stops in safe mode), then `turbo-run lane-status <N> done`. A session the supervisor adopts (one that is already running for the phase) keeps the stricter mode: a full-mode phase stays full.

### Inside a phase (`/turbo-phase`)

A full-mode session runs these steps in order. `turbo-run phase-step <N>` shows the next one, and each step is safe to run again from its start:

1. `freshness`: `turbo-run staleness <N>` checks the phase's existing planning artifacts (CONTEXT.md, RESEARCH.md, PATTERNS.md, plans) against the files they reference, since the commit each was recorded at; only the stale ones are rebuilt or re-grounded.
2. `discuss`: when the phase has no CONTEXT.md yet, GSD's discuss workflow in assumptions mode, with the recommended answers and no questions.
3. `prologue`: research, the UI and AI design contracts and codebase intel run in parallel, where GSD's planning would run them (`turbo-run jobs <N> prologue`); GSD's per-plan planners are set to run in parallel (`planning.chunked_parallel`).
4. `plan`: `gsd-plan-phase <N> --chunked`, which reuses the prologue's artifacts. Chunked planning writes GSD's outline (`<padded N>-PLAN-OUTLINE.md`, for example `03-PLAN-OUTLINE.md`) first and then commits the plans one by one, and GSD reports the phase as planned from the first plan on; so the step counts as done only when the outline is finished and every plan it lists is written (`turbo-run phase-step <N> --check plan`; `--done plan` refuses otherwise). A session interrupted between two plans runs the chunked planning again, which resumes from the outline. GSD's plan-checker (and the planner's revisions it asks for) runs after the last plan's commit; only after it does GSD record the planning (STATE.md "Ready to execute", the ROADMAP's wave notes and, with `commit_docs`, a `docs(<padded N>): create phase plan` commit). turbo also keeps its own record: once gsd-plan-phase returns, the session records `turbo-run phase-step <N> --plan-checked` (in `.planning/turbo/run/phase-p<N>.json`, with the plan files it covers). `--done plan` refuses until the set counts as checked: that record covers every plan file, or GSD's create-phase-plan commit comes at or after the last commit of a plan file changes STATE.md and adds no plan file (a gsd-planner's own commit with the same subject adds its plan, or holds ROADMAP.md alone, before the checker ran: it does not count). A session cut between the last plan's commit and both leaves `--check plan` printing `plan set unchecked: …`; the next session runs only the checker pass (the plan-checker, at most one planner revision and a second check, then GSD's own planning record and commit), never the planning again. A plan written after the record makes the set unchecked again. A phase whose execution has begun (a plan with its SUMMARY), planned before turbo kept this record, and GSD's plan check switched off (`plan_checker`, else `workflow.plan_check`, `false`) count as checked. An outline that does not match the phase's plans (another phase's number, or one an earlier planning run left beside plans it does not list) is ignored, and a plan GSD wrote but had not committed yet is committed before the step counts as done. A phase with a long chain of plans drafts its later Waves alongside the first (see [Plan drafts](#plan-drafts)), and the step ends with a planning-time line in the supervisor log.
5. `gates-off`: `turbo-run gates off <N>` switches GSD's four built-in gates off for its execution only.
6. `execute`: `turbo-run gates off <N>` again first (a stop inside this step restores the gates, so a resumed step would otherwise run GSD's gates serially and then the fan-out again), then `gsd-execute-phase <N> --no-transition`, with GSD's waves, test gates and verifier, and up to `gap_rounds` gap-closure rounds (default 1) when the verifier finds gaps; it ends with `turbo-run state-sync <N>`.
7. `restore`: `turbo-run gates restore <N>` switches the gates back on.
8. `fanout`: the gates that were on (security, UI review, code review, Nyquist validation) run in parallel; Nyquist validation writes its tests in its own git worktree, merged afterwards and then removed with `turbo-run worktrees prune <path>` (see [Safety](#safety)). `turbo-run jobs <N> outcome` reads their reports; a report that cannot be read counts as a finding.
9. `fix`: code-review findings are fixed one per commit (at most 3 review rounds) and open security threats are mitigated, with targeted tests after every iteration; a fix that turns the tests red is fixed forward or reverted.
10. `final-gate`: re-verification first (GSD's verifier runs again when the fixes changed covered code, with one gap-closure round when it finds gaps), and the phase's full test run last: `TURBO_FULL=1 turbo-run test-changed`, with at most 2 rounds of fixes when it is red.
11. `uat`: when GSD's verification is `human_needed`, the `turbo-uat` agent checks the items (see [Automated UAT](#automated-uat-turbo-uat)); then GSD's `gsd-verify-work` completes the UAT session and marks the phase complete. Every UAT write makes the verification report stale; when nothing outside `.planning/` changed since the report's commit (`turbo-run staleness <N> --verification`), only GSD's verifier runs again, and the last code review and green test and CI runs still count. When code changed, GSD's whole verification chain runs. When nothing but the UAT file (and STATE.md, turbo's run files or your answers) changed, all UAT writes of the step come first and the report is refreshed once after them, so a step that changed no code runs the verifier once; a changed plan, context or roadmap refreshes it first, since the human items may change. Before GSD's `uat.complete-session`, `turbo-run uat settle <N>` gives the UAT file the line endings of its committed version (it never touches git's index, so `git status` may still list the file while `git diff` shows nothing): complete-session compares the two byte for byte, so in a checkout with `core.autocrlf=true` it would otherwise commit a new `updated:` line on every call and make the report stale again. An edit to a file the report covers (a doc fix under `.planning/`) is never reverted only to keep the report fresh: it costs one verifier run.
12. `close`: writes the lane's done record only when verification passed, GSD marked the phase complete, no security threat is open, and, when the phase has a UAT file, GSD's own `phase uat-passed` check passes; otherwise it stops for you.

When only you can continue (for example verification gaps left after the gap-closure rounds, tests still red after the fixes, or UAT items that need your signature), the session stops the phase as `needs-owner` and asks you with a question card (see [A phase's own question](#owner-questions)); on an error it stops it as `failed`. Either way it first switches GSD's gates back on and records the position in STATE.md (`turbo-run state-sync <N>`). `/turbo-autonomous resume <N>` runs the stopped step again.

The bounded rounds (up to `gap_rounds` gap-closure rounds in `execute` and in `uat`, default 1 each; 3 code-review fix iterations; 2 red rounds in `final-gate`) are counted across sessions: a session that restarts a step after a context pause or a crash goes on from the earlier count, and the phase stops for you when a budget is used up. Your `/turbo-autonomous resume <N>` starts a fresh budget. A gap-closure round after the first runs only when the previous one brought new evidence: the verification report's failing must-haves and score (`execute`), or the UAT rows that do not pass (`uat`), changed; other words for the same failures do not count. A round that left them as they were stops the phase for you, whatever budget is left. A gap plan re-runs only the checks of the failed items, never the phase's whole live run. A round that a context pause or a stop interrupted before its gap plans ran is resumed, not counted again; it is resumed once more only after another of its gap plans finished, so a gap plan that never finishes stops the phase for you.

turbo keeps a phase's progress (the steps done, their notes and those counts) in `.planning/turbo/run/phase-p<N>.json`. When a new milestone reuses phase numbers (`/gsd-new-milestone --reset-phase-numbers`), run `turbo-run phase-step <N> --reset` for each reused number before that phase starts; otherwise the new phase N inherits the old phase N's finished steps.

GSD may mark a phase complete before turbo's gates and UAT finish: its execute-phase does that as soon as its verifier passes. The supervisor therefore waits for the lane's own done record (`turbo-run lane-status <N> done`, written by the close step), and `human_needed` alone never stops a full-mode phase.

A full test run ends every phase. From the moment every plan of the phase has a summary until the `execute` step is marked done, `turbo-run test-changed` runs the full suite (the phase-end rule, unless only Markdown, `docs/` or `.planning/` files changed since the last full green run), so GSD's regression gate sees all of it. The fan-out and the fixes in between run targeted tests, and the final gate runs the full suite again with `TURBO_FULL=1`.

### After a crash or a reboot

- **Your chat.** Come back to the session that started the run with `claude -r` (pick it by its title) or `claude --resume <id>`. `turbo-run status` run in that session prints the line with its id (`back to this chat: …`, in `lang`), and `/turbo-autonomous` passes it on when it starts a run. A bare `claude -c` opens the latest conversation in the folder, which in checkout mode may be a lane's own.
- **The live view** comes back by itself when that session resumes (or any session starts in the project) while a run is recorded, under the width rule of the [Live view](#live-view).
- **The supervisor** does not come back by itself unless autostart is on (below): run `/turbo-autonomous` (or `turbo-run start`). The supervisor that starts relaunches every lane whose session ended or is gone before it started as a continuation, as `resume <phase> --start` does, with a fresh count of restarts; a lane that recorded its own state before (a question for you, a pause, its own failure, its end) is handled as usual.
- **A supervisor that died without a word.** The supervisor keeps its pid in `.planning/turbo/run/supervisor.json` until it exits, or you stop, resume or attend the run. When that pid no longer runs, or has not checked in for ten minutes (five of its polls when that is longer), the machine crashed or restarted, or its process was killed or hung. Then the first to notice tells you once, on the desktop and in Telegram as `notify` says, with the command that starts the run again, and writes `watchdog:` lines into the supervisor log: the turbo pane's clock in your session, or a lane at its `inbox`, `ask` or `lane-status`, which also prints `warn: the supervisor is not running …` to the lane and goes on. A pid that still runs is told only two of its polls later (two minutes at least): a machine that slept checks in again first. A channel that fails is tried again after 5 minutes, three times at most; a lane without the Telegram token leaves that channel to your session. `.planning/turbo/run/supervisor-down.json` remembers what was told. Nothing restarts the supervisor by itself: run `/turbo-autonomous` (`/turbo-plan-milestone` for a plan-only run), or turn autostart on (below); `turbo-run start` and `resume` refuse to run inside a lane.
- **Claude Code's background service.** The service that runs the lane sessions (`claude --bg`) stops by itself when no session is its client, and a crash or a reboot takes it down too. While it is down, `claude stop` and `claude rm` fail with `the background service may be restarting`, and `claude agents` still lists its sessions from disk, a dead one as `blocked` or `working`. turbo handles it: a session listed without a pid whose turn ended is not running, so its stop counts as done; for any other one turbo first looks whether the service of your Claude Code config directory (`CLAUDE_CONFIG_DIR`, else `~/.claude`) is there at all (on Windows its control pipe `\\.\pipe\cc-daemon-<key>-control`, the key in `daemon/pipe.key` of that directory; elsewhere its `control.sock` under `/tmp/cc-daemon-<uid>/`; another config directory's service does not count) and whether any process still carries the session (its id in a command line, or the pid listed for it). With neither, nothing runs the session: `turbo-run stop` and `turbo-run attend` count it as stopped and say so in one line (`Claude Code's background service is not running and no process carries lane session <id>: counted as stopped`, in `lang`), and go on; the supervisor logs the same and wakes the session's own conversation, starting the service for it with a no-op background session. When either is there, or cannot be checked, turbo starts the service that way and tries once more, and only then reports the session as not stopped. On Windows the session's own pipe (`…-pty-<id>`) counts like the control pipe. On macOS and Linux a `control.sock`, or a session's pty socket, left by a crash counts as the service, so there the stop waits for that retry.
- **A damaged supervisor.json.** A crash right after a write can leave `supervisor.json` empty, full of zero bytes or cut short (seen after a Windows bugcheck: 526 NUL bytes). turbo never reads such a file as a project that never ran: `turbo-run status` prints `supervisor: state damaged (…)`, `status --json` carries `damaged`, `doctor` warns `supervisor-state`, the pane, the band and `turbo-run view` say «supervisor state damaged (likely a machine crash) — run turbo-run start, it rebuilds the lanes», and the watchdog tells you once per damaged file (desktop and Telegram, `watchdog:` lines in the log; a lane gets `warn: the supervisor's state file is damaged …` and goes on). Nothing rebuilds it by itself, a start at logon (autostart) included. Your `turbo-run start` (or `/turbo-autonomous`) keeps the file as `supervisor.json.damaged-<UTC time>` next to it, never deleting it, and rebuilds what lives outside it: in slots mode each slot whose own record holds an active job of this project becomes its lane again (key, phase, slot, branch), with its lane session found by name and slot (a running one is adopted, an ended one resumed in a new session); in checkout mode the lane of this checkout is a running lane session here, else the newest lane record (`run/p<N>.json`) of a phase GSD has not completed, else the newest lane session or `/turbo-phase` progress of such a phase. It prints one summary (in `lang`; English in the log as `recovery:` lines): what it recovered, each phase's next step, a slot whose own record is damaged too (repair or remove that slot by hand), and what is lost: the run's range and plan-only mark (give the range flags again), restart counts and sent-notification marks. With nothing to recover it says so and starts fresh. `turbo-run resume <N>` rebuilds the same way before it clears the phase; `attend` refuses until a start has rebuilt it; `stop` leaves the file as it is. A start also refuses while `daemon.lock` names a daemon that still runs since this machine started (`turbo-run stop` first). The pane opens by itself for a damaged state unless you stopped the run. A file that cannot be read at all (an error code that stays after a few quick tries, not damaged content) is never moved: start refuses and names it, `status` says it cannot be read now, the pane shows nothing for it, and the watchdog tells you in its own words (check the file and the disk). The owner's stop mark (`run/owner-stop.json`) left damaged still counts as a stop, so autostart never brings back a run you stopped; the other run files read a damaged file as missing, which is the safe side for each (no attend mark is lost: a mark counts by its existence; a damaged `away.json` means you are here, so nothing is answered for you).
- **State files and crashes.** turbo's JSON state (`supervisor.json` and the rest of `.planning/turbo/run/`), the UAT file it records into, the answers' `.gitignore` and the trust entries it writes into Claude Code's config are flushed to the disk before they replace the old file, so a crash leaves either the old content or the new one. Logs and appended lists (`supervisor.log`, a lane's inbox) are not flushed.
- **Autostart (optional, per project).** `turbo-run autostart on` makes the supervisor of this project start at logon; `turbo-run autostart status` says whether it is set, `turbo-run autostart off` removes everything `on` made. `on` and `off` print each file they write or remove and each command they run. What it sets up:
  - Windows: a value `gsd-turbo <project key>` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (your user only, no administrator) that runs `wscript.exe` on a small launcher, `turbo/autostart/<project key>.js` in your Claude Code config directory, which starts `node turbo-run.mjs start --autostart --project <dir>` without a console window, with the `CLAUDE_CONFIG_DIR` you had when you turned it on, when one was set (the rest of the environment is your logon's). Not a Task Scheduler task: a logon task needs an administrator, and Task Scheduler ends every process a task started when the task's own process exits, the supervisor included. Windows Script Host must be enabled (it is by default); some security software flags a Run entry that starts a script, so check `turbo-run autostart status` after `on`. A path (the project, `node`, `turbo-run.mjs` or the config directory) with `%` or a control character is refused.
  - macOS: a LaunchAgent, `~/Library/LaunchAgents/gsd-turbo.<project key>.plist`, run at login with the `PATH` (and `CLAUDE_CONFIG_DIR`) you had when you turned it on; it loads from your next login.
  - Linux: a systemd user unit, `~/.config/systemd/user/gsd-turbo-<project key>.service`, enabled for your login. Without a systemd user session `on` says it is not supported and prints the command to add to your session's autostart yourself.

  The project key is the one the lane sessions are named with: the folder name and a short hash of its path. At logon `start --autostart` starts the supervisor only for a run that was going when the machine went down, or that halted because its lane's session failed. It starts nothing for a run that finished, that halted for you, or that you stopped with `turbo-run stop` (it leaves `.planning/turbo/run/owner-stop.json`, which your next `start` or `resume` removes), and copies what it prints into the supervisor log. In slots mode a lane stopped for you stays stopped at logon, while one stopped by its session's failure is tried again. It runs the `node` and the `turbo-run.mjs` of the call that turned it on: if either moves (a Node.js version manager may move `node`), run `turbo-run autostart on` again. Turn autostart off before you delete the project or uninstall turbo.

## Several lanes

With `lanes.mode: "slots"` (the default) and doctor's full mode, the supervisor runs up to `max_lanes` phases at once, each in its own slot (see [Lane slots](#lane-slots)), and prep and annotate jobs in the slots the phases leave (at most `max_prep`).

- **Which phases run together.** A phase starts when every phase it depends on is finished, its `Areas` (the ROADMAP annotation) do not overlap the `Areas` of a running phase, none of its `Gates` is held by a running phase or a lock, and a free slot that Claude Code trusts exists. A phase without annotation, or with low confidence, may touch any path, so it runs alone. Without a fresh annotation (`.planning/turbo/lanes.json`) only one phase lane runs. Among the ready phases, the one with the longest chain of phases waiting on it goes first.
- **Shared resources.** Before a deploy, a packaged build or a live check, a lane takes a lock: `turbo-run lock <gate> <N> [--wait-seconds <s>]` (default 540; exit 0 taken, 3 still held after the wait and you are notified, 2 usage or an unknown gate) and `turbo-run unlock <gate> <N>`. The gates are `prod-deploy`, `owner-live`, `owner-signature`, `packaged-build` and your `lanes.gates`. A lane's locks are released when it ends; a lock nobody holds a lane for stays until you unlock it.
- **When a lane fails.** Only that lane stops: you get one notification with the reason and `cd "<slot>" && claude` to look inside. Its slot keeps the work, and the phases that depend on it wait; the other lanes go on. `/turbo-autonomous resume <N>` tries it again in the same slot, and so does a new start. When every lane has stopped and nothing else can start, the supervisor halts. A slot Claude Code does not trust is never used: you get its trust line once.
- **attend.** `turbo-run attend <N>` stops only lane N and prints `open: cd "<slot>" && claude`: the sitting runs there. The supervisor and the other lanes keep running. `turbo-run attend <N> --done` gives the phase back to the running supervisor the same way, without stopping it.
- **stop and status.** `stop` stops every lane, prep and annotate session; the slots and their branches stay for review. `status` prints `lanes: <n> · questions: <n> · next: <what the next phase waits for>` and one block per lane.
- **Plan only.** `turbo-run start --plan-only` (with the usual range flags; `/turbo-plan-milestone` runs it) starts no phase: only prep and lane markup jobs run in the slots, and the supervisor ends with one notification, «Milestone prepared», once none is due and none runs. A later `start` without the flag runs the phases. It needs `lanes.mode: "slots"` and full mode.
- `lanes.mode: "checkout"` runs one lane in this checkout, exactly as v0.3 (also what a safe-mode supervisor does).

## Merging lanes (slots)

With `lanes.mode: "slots"`, a phase ends with the step `integrate`. Its lane, in its slot, runs `turbo-run integrate <N>`: it fetches the main branch, merges it into `turbo/p<N>`, and always takes the main branch's `STATE.md`, `ROADMAP.md` and `REQUIREMENTS.md`. The lane then runs the full test suite, re-verifies when the merge staled the verification, and reports `turbo-run lane-status <N> ready --base <sha>`. The supervisor merges under one lock (`.planning/turbo/locks/merge`), and only when the main checkout is clean, on its branch, and its `HEAD` is still that base: `Merge phase <N> (turbo lane <k>)`, exactly the tree the lane tested. When the main branch moved first, the lane gets a `reintegrate` message and integrates again. After `merge_rounds` (default 3) such rounds in a row, you get a question: wait (turbo starts no new phase meanwhile) or merge it yourself. After the merge, the supervisor re-stamps the verification fingerprint (the main checkout may write other line endings), runs GSD's `phase.complete`, commits `docs(phase-<N>): complete phase (turbo merge)` (GSD's untracked `.planning/state.json`, which `phase.complete` writes, is removed again when the main checkout had none before; your own stays, updated, and a tracked one is committed with the rest), and pushes the main branch when `push.mode` is set. Red CI goes to the lane's inbox, and the lane fixes it and integrates again. The slot is freed after green CI, or at once with `push.mode: off`. Lanes in slots never push: `push-request` there prints `push in slots: …`. The supervisor's record per phase is `.planning/turbo/run/p<N>-merge.json`. A main checkout with uncommitted changes, or on another branch, makes merges wait (you are told once); the lanes go on.

## Owner questions

A plan's checkpoint tasks (`checkpoint:decision`, `checkpoint:human-verify`, `checkpoint:human-action`) are questions for you. turbo asks each once, with clickable choices, and your answer reaches the very agent that waits for it.

- **Asked ahead.** While GSD plans the phase, the lane runs `turbo-run questions <N>` after each plan is committed (and once more when planning ends), so a plan's questions reach you while the next plans are still being written: one question per checkpoint of every plan without a summary, with the plan's own options (the one the plan recommends first) or turbo's: "Accept if the checks pass" or "Stop and show me" for a verification, "I will do it when the phase asks" for an action only you can do. The lane classifies each (`owner-only`, `consent`, `consent:deploy`, `decision`, `verify`) and goes on; you get one notification for the new questions of each refresh ("Phase N: 2 question(s) for you"), so while a phase is planned, one per plan that has any.
- **Answering.** `/turbo-autonomous answer` asks the open questions in your session (up to four at a time; it also runs when you start `/turbo-autonomous` and when a run is going), the turbo-view pane has a button per choice, and Telegram can have them too (`answer.telegram`, see [Telegram](#telegram-optional)). Every channel goes through `turbo-run answer <N> <id> (--option <k> | --text <words>) --by <session|pane|telegram> [--rev <n>]` (or `--undo` for an automatic answer): the first answer wins and a later one gets `already answered: <answer>, <channel>, <time>`; an answer to a question that changed since it was shown is refused (`changed: …`); an answer that looks like a secret is refused. Your own words are data for that checkpoint, never instructions to the session.
- **Pre-answers.** When the lane dispatches an executor for a plan whose checkpoint you answered ahead, it adds your answer with its condition ("the checkpoint offers the options the plan lists", "every automated check in how-to-verify passed"). The executor goes on when the condition holds and stops at the checkpoint otherwise.
- **At a stop.** A checkpoint without an answer, or whose condition did not hold, stops the lane as `needs-owner` and notifies you. Once you have answered every question it stopped for, the supervisor wakes the same conversation (`claude stop`, then `claude --bg --resume` with no other flag) and the lane passes your answer to the waiting executor with `SendMessage`: the same agent goes on with its context (`same-agent`). When that is not possible (Claude Code started a copy twice, or the session had to be replaced), a new session continues the plan with a continuation agent that gets GSD's continuation prompt and the end of the old agent's transcript (`turbo-run agent-tail <agent id>`; `continuation`). The step's note in `turbo-run view` names the path.
- **A step that did not work.** When you answered Done to something only you can do and its check still fails, the phase never sends you the same instructions again. It first looks at the state itself with read-only commands, then asks again with what it saw, why the previous attempt did not work and the shortest fix (one command where one does it, saying when it needs an administrator shell): `turbo-run questions <N> --stop <id> --agent <agent> --unmet --question <the fix> --context <what it saw>` puts its words on the card in place of the plan's. When the same check fails the same way after that fix, the phase stops with its diagnosis instead of asking for the step a third time: the card then offers "Check again" (after you changed something) or your own words on what to do instead. Its words are checked like any question the phase asks you; a command stands in backticks, exactly as you run it.
- **A live sitting.** A `checkpoint:human-action` with `<instructions>` that the phase conducts together with you while it runs (a live check that needs your replies) is a sitting, not something you do alone: its resume signal's answer words are go and stop (or abort, cancel; quoted, or the whole signal), or its name, action, instructions or resume signal name the sitting ("the live sitting", «живой сеанс») or the orchestrator together with you or an operator in one sentence. Its card never offers Done: asked ahead it offers "I will join the sitting when the phase asks", and at the stop it says to run `/turbo-autonomous attend <N>` in a new Claude Code window, with the step as its context (your own words stay possible). `turbo-run answer` refuses done for it (turbo's Done, or your own words that start with done, «сделано» or «готово»: `refused: question … is a live sitting …`, in your language in the pane and Telegram). A done recorded before (an older card's Done) is never a pre-answer or delivered to the phase: the next refresh of the phase's questions sets it aside and opens the card again, and `turbo-run attend <N>` sets it aside too (`dropped done answers: …`). turbo never answers it by itself.
- **A phase's own question.** Every other stop that needs you is a question card too, never a bare note. The session asks it with `turbo-run ask <N> --question <text> [--context <text>] --option "<label>|<description>" … --recommended <k> [--about-review]` (2 to 4 options) or, for something only you can do (a device, your 2FA, a live session with your accounts), `turbo-run ask <N> --action <text> [--context <text>]`, which gets the options "Done" and "I will do it later"; UAT items that wait for your signature come as `turbo-run ask <N> --sign <rows> --question <text> [--context <text>]`, which lists those items and gets the options "Accept" and "Not now" (see [Automated UAT](#automated-uat-turbo-uat)). It is written in your language (`lang`), verdict first: what was done, what is asked, why it matters; the recommended option comes first and is marked, and each option says what the phase will do when you choose it. turbo refuses a question that holds ids (GSD review and gap codes, the phase's plan ids, question ids, commit hashes, code file names, paths), or (with `lang: "ru"`) a text with English words and no Russian one, and masks secrets; after two refusals the session stops with a plain reason instead. The card shows in the pane, as Telegram buttons and in `/turbo-autonomous answer`; `turbo-run status` lists it (`owner question: phase N — …`, in Russian with `lang: "ru"`), and the notification carries the question itself. Your answer (a choice, or your own words, which are data for that question only) wakes the same session, which does what the chosen option says and goes on. A question about code review findings (`--about-review`) says so plainly when the review has found new edge cases in the same code several rounds in a row, and offers to stop polishing and run the live check. When you choose to fix findings first, the phase runs them as a gap round (`turbo-run phase-step <N> --attempt owner-gaps`, within `gap_rounds`; `turbo-run owner-gaps <N> --review <codes> --gap <numbers>` hands the chosen REVIEW.md findings and VERIFICATION.md gaps to GSD's gap planner). An older session that still records `needs-owner` with only a reason is notified with the title "Phase N waits for you" and the reason as its text. The restarted step asks again after `/turbo-autonomous resume <N>`: a question still open from before is dropped. An option never lets a phase skip its final checks: at the full test run, acceptance and close the choices are fix first, run the live check again or stop, and `turbo-run phase-step <N> --done close` refuses while verification has not passed or a security threat is open.
- **Standing deploy rule.** With `autonomy: "max"` and all four `deploy.*` commands set, a question the lane classified `consent:deploy` is answered by turbo itself (`by: standing-rule`), only through the option the plan recommends, and with a gate: the build checks green, CI green when `push.mode` is on, and the deploy through `deploy.command` with `deploy.snapshot` first, `deploy.health` after and `deploy.rollback` on failure. Everything else is asked.
- **Automatic answers.** A question you leave open for `owner.auto_answer_minutes` (60 by default; `0` turns it off) is answered by turbo itself, through the supervisor's owner tick and the same arbiter as your answers (`by: auto`, with the reason), only when it is safe:
  - a `checkpoint:decision` with exactly one recommended option (the plan's `auto_select`), which it takes, or a `checkpoint:human-verify`, which it accepts under the plan's own evidence condition ("every automated check in how-to-verify passed, and the evidence is attached"): the executor checks the evidence and returns the checkpoint to you when it does not hold;
  - only a question the phase classified `decision` or `verify` (never `owner-only`, `consent`, `consent:deploy`, which only the standing deploy rule answers, or a question no phase has classified yet, such as one `away` built ahead); never a `checkpoint:human-action` (something only you can do), never a checkpoint with `gate="blocking-human"` (checkpoints a phase names at a stop are that too), never a question without a single recommended option, never a card that could only say "see the plan", never a phase's own question (`turbo-run ask`) unless it was asked with `--auto-ok` (the lane-markup dependency card is: its decision record undoes it; the merge card is not), never a question answered before (a stop that reopened your answer, an undone automatic answer), never in a phase you attend, and never a question that speaks of money or payment, accounts, logins or tokens, a deploy, a release or production, deleting or dropping data, signing, passwords or secrets, or a live check (in English or Russian, their word forms included; a safety net over the rules above). For a checkpoint of a plan the check reads the plan's own text (every field of the checkpoint and its options, in the lane's slot when one runs the phase), not the shorter card; a checkpoint that cannot be found there is left to you.
  - The executor and the lane get it as turbo's automatic answer, never as yours ("turbo's automatic answer (the owner did not answer in time; it is the recommended option, not the owner's own check or choice)"), so no summary records a check nobody made; its commit says `automatic answer`.
  - The clock starts when the question is asked, again when a phase stops at it, and again when its options change. A bad value of `owner.auto_answer_minutes` is logged and answers nothing.
  - Every automatic answer is notified (desktop and Telegram): «Accepted automatically while you were away: <question> → <option>. Undo: turbo-run answer N <id> --undo». The pane, `turbo-run view` and `turbo-run status` list them until you come back (`turbo-run back`).
  - **Undo.** `turbo-run answer N <id> --undo` takes back an automatic answer. An answer given ahead (or the lane-markup card not applied yet) reopens: the question opens again (a new revision, notified anew) and waits for you; turbo never answers it again. An answer at a stop is not reopened (the supervisor wakes the phase with it in the same check), nor one the phase already took or whose plan is finished: `noted`. Either way but for the markup the phase gets your correction in its inbox (an executor may already hold an answer given ahead); a phase that holds it asks you whether to keep that result or redo that part, and one that no lane runs now reads it at its next run. The markup card, once applied, is undone by reverting its decision record's commit.
- **Away mode.** `/turbo-autonomous away` (`turbo-run away --json` builds the questions of the run's remaining phases that no lane runs yet and that have none, and lists every open one) asks them all in one batch, four at a time, then `turbo-run away --set` records when you left. While you are away the automatic answers work as above. `turbo-run back` (and any `/turbo-autonomous` call) prints the morning summary: phases moved on, commits, the automatic answers with their undo commands, the questions still waiting and the failures, and turns the mode off; the pane shows the mode until then. The state is `.planning/turbo/run/away.json`. Telegram has no away buttons: use the commands.
- **A silent lane.** A session that writes nothing, neither itself nor its subagents, for `stall_minutes` (for example after Claude Code or the PC restarted and the session came back idle) is woken the same way, with the request to resume its unfinished subagents; after two such wakes without progress you are notified (`Phase 32 is silent — waking it did not help`). A command in flight anywhere in the session's tree (Bash or PowerShell, not one run in the background) keeps the lane busy while it is within its timeout and 2 minutes: Claude Code writes nothing while a call runs, and a wake stops the session and the command with it, so a long build is never woken. A command past that with nothing written since makes the lane silent at once, without waiting for `stall_minutes`. A session waiting for its own running subagents does not count as waiting for you, and sessions never stop for a context limit while their subagents still run.
- **Storage.** Answers are kept in git, in `.planning/turbo/answers/p<N>.json`: while a lane runs, it commits the whole directory (every phase's answers) at its next step; when no lane runs, `turbo-run answer` commits it itself. The questions live in `.planning/turbo/run/p<N>-questions.json`. Sessions never answer: `turbo-run answer` refuses to run inside a lane.

## Live sittings

Some plans need you while they run: a device to connect, a login, an app to quit. `/turbo-autonomous attend <N>` runs the rest of phase N's plans in your own session, with you, and then gives the phase back to its lane:

1. `turbo-run attend <N>` takes the lane over. It refuses, changing nothing, unless phase N is the supervisor's lane, still has plans without a summary and, in a full-mode lane, has reached its `gates-off` step (before it, the plans are not checked yet). It stops the supervisor and the lane's session (`claude stop`: the conversation is kept; a session that Claude Code's stopped background service still lists, with no process of it left, counts as stopped, see [After a crash or a reboot](#after-a-crash-or-a-reboot)) and marks the phase attended in `.planning/turbo/run/p<N>-attend.json`, with the session `attend` runs in (`CLAUDE_CODE_SESSION_ID`, set by Claude Code in a session's Bash tool; none when it is absent or `attend` runs outside the sitting's checkout, as the first `attend` of a slots-mode lane does): the pane reads the sitting's progress there. A later `attend <N>` from another session names that one: after `/clear` (a new session) run `/turbo-autonomous attend <N>` again so the pane follows the sitting. While any phase is attended, no supervisor starts, relaunches or wakes a lane, also one started by hand; `turbo-run status` and `turbo-run start` name the mark, and the held lane shows no session to watch. Meanwhile you answer in your session: `turbo-run answer` commits each answer itself, and presses and replies in Telegram wait there until the hand-back. The phase's questions are not sent to Telegram, notified or answered automatically while it is attended (a message already in the chat stays as it is); they go out after the hand-back. The checkpoints the lane had stopped at become questions asked ahead again: the agents that waited there belonged to the stopped session. A stop you had answered before it came back to the lane keeps your answer for the sitting (`released stops with your answer: …` lists it, with any answer you gave at a stop the lane had not delivered yet: the answer, where you gave it and when; `turbo-run questions <N>` lists it the same way), unless its condition changed: the answer did not hold, the phase reworded the card after a failed action, you had asked to be asked at the stop, or the plan changed the checkpoint. A done answer to a live sitting (see [Owner questions](#owner-questions)) is set aside and named on a `dropped done answers: …` line: the sitting runs in your session.
2. The skill shows the plans left and all their questions and asks you the questions up front (the `/turbo-autonomous answer` flow, phase N only); physical actions are left for when the run reaches them.
3. It runs GSD's `execute-phase <N>` in your checkout, one plan at a time and without worktrees (`dispatch-isolation --force-isolation none` right before each executor, as GSD's isolation guard needs), with GSD's own gates off only while the lane's restore and fan-out still lie ahead, so the lane runs them after the hand-back (`attend` prints `gates: turn off`), and on otherwise, so GSD runs them in your session (`gates: keep on`: a lane at `fix`, `final-gate` or `uat`, or in safe mode), your answers as conditional pre-answers in the executor prompts, and the release rule (see [Safety](#safety)). A checkpoint without an answer is shown to you there.
4. `turbo-run attend <N> --done` clears the mark and runs `resume <N> --start` (without a mark on phase N it refuses and changes nothing): the lane goes on with verification, the gates, UAT and close. With several lanes and the supervisor running, it hands the phase to the supervisor instead, which clears the mark and relaunches the lane at its next check; an `attend <N>` before that check cancels the hand-back. `turbo-run resume <N>` clears the mark too.

`turbo-run attend` refuses to run inside a lane.

## Prep and lane markup

In `lanes.mode: "slots"` the supervisor prepares future phases while others run, and marks up the ROADMAP so that independent phases can run at the same time (spec §6).

- **Prep.** Every unfinished phase of the run's range without a `CONTEXT.md` gets a prep job: a background session `/turbo-prep <N>` in a free slot on `turbo/prep-<N>`. It runs `/turbo-phase`'s freshness, discuss (assumptions mode, recommended answers) and prologue steps and stops before plan; `turbo-run lane-status <N> prepped --job prep` refuses anything outside `.planning/phases/<N>-*`. The supervisor merges the branch without tests. At most `max_prep` run at once (default `max_lanes`), and phase lanes always come first. A failed prep is not retried: the phase's lane does the same work itself.
- **Markup.** After prep, one annotate job runs the `turbo-lane-analyst` agent over the ROADMAP, each unfinished phase's CONTEXT, RESEARCH and plans, and the code, then `turbo-run annotate apply` writes, right after each phase's `**Depends on**:` line, `**Areas**:` (path masks the phase may touch), `**Gates**:` (`prod-deploy`, `owner-live`, `owner-signature`, `packaged-build`, plus `lanes.gates`) and `**Parallel with**:` (informative), and `.planning/turbo/lanes.json`, which the scheduler reads. A phase without markup, or with `confidence: low`, counts as touching everything. Each phase's entry in `lanes.json` records whether its CONTEXT.md existed when it was marked up (`context`); a phase marked up with `confidence: low` before its CONTEXT.md existed is marked up again once its prep wrote one (an entry from v0.4, without `context`, is not).
- **Freshness.** `lanes.json` keeps a digest of the ROADMAP's scheduling text (each phase's heading, Goal, Depends on and Requirements). Completing a phase does not change it; adding or removing a phase or editing a dependency does, and only the phases whose section changed are marked up again.
- **Dependencies.** GSD reads every `Phase <N>` in a `Depends on` line as a dependency, even in `Nothing (independent of Phase 1)`: for a phase with no dependency write `Nothing` alone. The analyst may propose to drop a `Depends on` that is only wording or imaginary. With `autonomy: max` turbo applies it (`Depends on` rewritten as `Phase 3, Phase 4`) and writes a decision record to `.planning/decisions/` (when that directory exists) or `.planning/turbo/DECISIONS.md`: what was, what is, why, how to roll back. With `standard` you get one question card (remove all / leave as is / your own words for some); nothing waits for it.
- **Commands.** `/turbo-plan-milestone [range]` prepares and marks up the milestone without running any phase (`turbo-run start --plan-only`), and ends by itself. `/turbo-new-milestone` runs `/gsd-new-milestone`, then `/turbo-plan-milestone`. `/turbo-autonomous` does the same first steps by itself when a milestone has no markup.

## Plan drafts

GSD's chunked planning plans one Wave of its outline at a time, because a planner reads the plans written before its own: a phase whose plans form a long chain (ten plans in eight Waves, say) plans for hours, one Wave after the other. With plan drafts, the lane's step `plan` writes the plans of the later Waves as drafts at the same time as the first Wave, and at each later Wave checks every draft against the plans before it, now written, with a short planner revision (a reconcile pass). Only a reconciled draft becomes a plan. GSD's outline, its commits (`docs(<padded N>): plan <id> (chunked)`), its plan checker and its revision loop run as before, and your questions from each plan come after that plan's commit, as without drafts.

**When.** In the plan step only (never for gap plans, `--reviews` or a freshness revision), once GSD's outline is finished, when `plan_drafts.enabled` is on (off by default until their live check on a long plan chain; turn it on in `.planning/turbo/config.json`), GSD's plan checker is on, and the outline has a `Wave` and a `Depends On` column, a plan id in every row, whole-number waves (blank is 1, as GSD reads it), dependencies on plans of earlier waves only, and at least `plan_drafts.min_waves` (default 3) waves of plans not written yet. Otherwise the phase plans exactly as without drafts, and `turbo-run plan-drafts <N> --plan` says why (`drafts off: …`). The plans of the waves after the one GSD plans now are drafted, at most `plan_drafts.max_parallel` (default 8), once; GSD plans the rest at their waves.

**Where.** A draft is `<id>-PLAN.md` in `.planning/turbo/run/drafts-p<N>/` of the lane's own checkout (its slot), with the record `drafts.json`; git ignores both, and a slot prepared anew starts without them. A draft is never written into the phase directory: GSD would take it for a written plan. The draft agent gets GSD's own single-plan prompt plus a paragraph that names the draft file and tells it not to touch the phase directory, ROADMAP.md or STATE.md and not to commit.

**Checks.** Each step of a draft is a `turbo-run plan-drafts` command the lane runs; a refusal sends that plan down GSD's own path at its wave.
- `--drafted <id>`: the draft file exists, starts with frontmatter, its `wave` and `depends_on` match its outline row (quoted, long-form or bare ids read as the outline's), it ends with a `## Draft assumptions` section (what it takes from each earlier plan), and the agent wrote no plan file into the phase directory: its own `<id>-PLAN.md`, or any new plan file that is no plan of the outline (`33-02-auth-PLAN.md`, `plans/…`). turbo removes such files (with a commit when the agent committed them) and refuses. ROADMAP.md, STATE.md and commits are not looked at: GSD's own chunked planners update ROADMAP.md and commit `docs(<padded N>): create phase plan` on their own. The draft's blob is recorded even when refused.
- `--reconcile <id>`: the plans the draft builds on (its dependencies, the earlier plans its assumptions name, the earlier plans that change a file it changes or cites) are committed; the draft is the one checked. It records each of those plans' committed blob and prints what the reconcile prompt needs.
- `--reconciled <id> --verdict passed|failed`: none of those plans changed since, and the reconcile agent wrote no plan file into the phase directory (removed as for `--drafted`).
- `--promote <id>`: the draft is the reconciled one (the blob of the very bytes it reads and writes), matches its row, changes no file a written plan of its own wave changes, and `<id>-PLAN.md` does not exist; then turbo writes it into the phase directory without its assumptions section, and the lane commits it with GSD's message.
- Any `use: gsd` answer and `--replan <id>` mark the plan as GSD's. A file a draft agent wrote into the phase directory is removed by turbo (with a commit when the agent committed it); `--plan` also removes such leftovers on a resume, and names promoted plans a stopped session did not commit (`commit first: …`).

**The guard.** `phase-step <N> --check plan`, `--done plan` and `--plan-checked` refuse while a plan file of the phase came from a draft without a passed reconcile: a plan of a drafts record that is not GSD's whose newest adding commit (its working copy while uncommitted) is not the promoted file, or any plan file of the phase, under any name, that is byte for byte a recorded draft. A new plan file no outline row names is not refused: GSD's revision loop may split a plan into new ones; turbo removes an agent's own plan files while it knows the agent's window (`--drafted`, `--reconciled`, a lost agent's `--reconcile`, a lost agent's re-draft (`--drafting`), `--replan` of an entry still at work). When drafts turn off in a resumed session (disabled, or GSD's checker off), `--plan` hands every draft not promoted yet to GSD. Later revisions by GSD's plan checker are GSD's normal work and pass.

**Measuring.** When the plan step is marked done, `.planning/turbo/logs/supervisor.log` gets one line, `phase 33 plan: 1h12m wall clock · drafts on: 10 plans in 8 waves, 9 drafted, 8 reconciled, 1 replanned` (or `drafts off: <why>`); the same text starts the step's note. The wall clock runs from the first time `phase-step <N>` named `plan` as the next step (kept across sessions, context pauses included; `.planning/turbo/run/plan-clock-p<N>.json`) to `--done plan`; `phase-step <N> --json` shows it as `timings.plan`. To compare, plan one phase with `plan_drafts.enabled` `true` and another of similar length with `false`, and compare the two lines.

**Cost.** Each drafted plan is written once as a draft (as it would have been once anyway) plus a reconcile pass (about a quarter to two fifths of a plan), plus GSD's own plan for a draft that fails: expect 30–50 % more tokens in the plan step.

## Lean mode

### What changes in a phase

`/turbo-phase` keeps its steps; in a lean phase some of them do less. With lean off every command, prompt and output stays as before.

- **Which phase.** `turbo-run phase-step <N>` prints `lean: on` before its `phase N: next …` line when the phase runs lean (`--prep` too; `--json` is unchanged). The choice is pinned when step `gates-off` is done (`.planning/turbo/run/lean-p<N>.json`, removed by `--reset`): a phase whose execution began before lean (gates-off done, or a plan SUMMARY, with no pin) finishes without it, and a later change of `lean.enabled` leaves a running phase alone.
- **Research** runs only when the phase calls for it: `turbo-run jobs <N> research` prints `research: yes|no (<why>)` from the phase's signals (topics the assumptions analyzer flagged, an external API, a dependency upgrade or a security subject in the goal, requirements or success criteria) or an existing RESEARCH.md. On `no` the prologue has no research job and the plan step runs `gsd-plan-phase <N> --chunked --skip-research`.
- **Prompt inserts.** The researcher builds on CONTEXT.md's Existing Code Insights instead of scanning the code again and ends RESEARCH.md with a table of pitfalls, each answered by a plan task or a spike. The planner keeps each PLAN.md under 25 KB, cites RESEARCH.md and CONTEXT.md instead of restating them, writes no code block over 10 lines, and keeps every field the checker needs. The checker reports `research_resolution` and `scope_sanity` issues as info only and asks for a revision only for a real gap. A lean lane hands each executor `checkpoints.md` only for a plan with a checkpoint task, never `executor-examples.md`.
- **Security audit.** Lean turns GSD's security gate off; turbo's fan-out adds its own `gsd-secure-phase` job (`direct: true`, GSD's secure-phase workflow without its enforcement check) when the phase touches authentication, private data or data routed between users, or plans files on such paths. It blocks like GSD's gate: `outcome` retries while its SECURITY.md is missing.
- **Fix loop.** `turbo-run jobs <N> review [--json]` reads the loop from git's commit order of REVIEW.md and REVIEW-FIX.md and from the code committed since the review: `fixer` (one pass of `gsd-code-review <N> --fix`), then `review-diff` (a review of the fix diff only, `--files` and a paragraph that also re-checks every critical or warning finding the pass skipped, closed without a code change, fixed only outside its files (critical) or left out of its report; at most three, counted by `phase-step <N> --attempt review-diff`), then `done`; a second fixer pass only for new critical findings, two passes at most. A critical finding left at `done` stops for you: only a code change or your decision closes it, never a note. An uncommitted or edited report makes it print `fallback`, and the step runs as before.
- **Re-gate.** After the fixes, final-gate (and a stale report with code changes) no longer re-runs `gsd-execute-phase` with every gate on: `turbo-run jobs <N> regate [--json]` lists the gates whose inputs changed since their report's commit (code for all, except files step integrate took in from the main branch and the phase left unchanged; also the phase's PLAN and SUMMARY files for the security audit, its PLAN files for Nyquist, its UI-SPEC for the UI review; a gate without a committed report runs again), the code review only over the changed files; then the verifier runs alone when the report is stale.
- **Tests.** Before final-gate is done, `turbo-run test-changed` in a lean phase never runs the full suite: a run it cannot target prints `skip: lean: no full run before final-gate of phase <N> (<reason>)`, passes and writes no green marker; `max_targeted` and the phase-end rule are off in that window. Outside a lane session the window closes once the phase's progress has not moved for 24 hours (an abandoned run). final-gate's `TURBO_FULL=1` run is the phase's one full run, plus CI; the UAT gap round and integrate keep theirs, and `TURBO_FULL=1` or a hand run outside a phase run full as before.
- **Records.** One `docs(phase-<N>): <step> records` commit per step (the owner's answers, STATE.md, `.planning/STATE-ARCHIVE.md`, the phase's `turbo-base.json`), also at a stop (`stop records`) and a context pause (`pause records`); `turbo-run state-sync <N> --no-commit` writes STATE.md and leaves its commit to it.

## What-if: plans as a graph

GSD executes a phase wave by wave: a wave starts only when every plan of the wave before it is done and merged, so one long plan holds back every plan of the next wave, including those that do not need it. turbo's next step (Stage 6) starts each plan as soon as the plans it needs are merged. Before that is built, `turbo-run exec-whatif <N>` measures what it would have saved on a phase that has already run. It only reads: the phase's plans, git and Claude Code's transcripts; it writes nothing.

```text
turbo-run exec-whatif 32                 # in the project
node <gsd-turbo checkout>/bin/turbo-run.mjs exec-whatif 32 --project <path to the project>
```

- **Graph.** A plan needs the plans in its `depends_on`, every earlier plan that changes or deletes a file it changes or deletes (`files_modified`, `files_deleted`), and every earlier plan that changes a file its `must_haves.key_links` name (the planner's own rules). Earlier means GSD's wave, then the declared wave, then the plan id.
- **Minutes per plan.** From the executor transcripts (each executor subagent of the plan from its first to its last entry; a continuation after a checkpoint counts, the time waiting for you between them does not), else from git (from the commit of the phase's orchestration before the plan's first commit to its summary commit; a start more than `--max-lead` minutes, default 20, before the first commit becomes the median of the others, marked `start estimated`), else `--minutes 32-07=12,…`, which wins over both. Gap-closure plans are left out.
- **GSD's waves** as GSD computes them (the longest `depends_on` chain; a wave whose plans share a file runs one plan at a time), with the wave tail (merges, test gate, tracking commit, next dispatch) measured at each wave boundary (median), else 5 minutes (`--tail-minutes`).
- **The ready queue** for 1 executor up to `max_executors` (`--max-executors`): the longest remaining chain first, one merge at a time after each plan, each merge costing one wave tail unless `--merge-minutes` says otherwise (a merge plus targeted tests is usually shorter: the line also shows half a tail).
- **Output.** The measured span, the assumptions, GSD's waves, the ready queue by executors, the gain, the critical path, the edges that cost most (what the queue would save without each), and per plan its minutes, source and start in both schedules. `--json` prints all of it; `--edges depends,files` or `--edges depends` leaves edge kinds out; `--no-transcripts` uses git only.

## Adopting a running milestone

`/turbo-adopt` moves a milestone that is already running on plain GSD onto turbo. It never starts the supervisor, a lane, a prep or markup job, makes no slots, writes no trust, removes no agent worktree and turns no gates back on: the report names each of these with its command, and the first `/turbo-autonomous` does the rest. It runs `turbo-run adopt …` in this order:

1. **Check** (`turbo-run adopt scan`). Refused, with one `refused:` line per reason and nothing changed: no `.planning/ROADMAP.md`; `turbo-run doctor` says `unsupported`; the supervisor runs; a lane of the last run still works; a phase is attended; a git merge is in progress; uncommitted changes (adopt commits nothing of yours; the skill shows the list and asks you); GSD branches per phase or milestone (`git.branching_strategy` `phase` or `milestone`) and HEAD is not on the default branch (origin's HEAD, else git's `init.defaultBranch`, else GSD's `git.base_branch`): `refused: HEAD is on GSD's branch <b>; merge it into <default> and switch back`; when only `main` or `master` suggests the default branch, a `warn:` line instead. Nothing unfinished: `nothing to adopt: every phase is done`. Otherwise the overview: one line per state with its phases, the current phase (GSD's state contract `.planning/state.json`, else `gsd-tools state json`; never `init manager`'s `is_active`, which only says that a file of the phase changed in the last five minutes), the branch, `markup: needed|fresh|off`, and what is open for you (turbo's open questions, phases whose verification needs a person or whose UAT has open items, agent worktrees left, GSD gates left off).

   | State | Meaning | What turbo does with it |
   |---|---|---|
   | done | GSD counts it complete | nothing |
   | closed, verification stale | checked off in the ROADMAP and every plan has its SUMMARY, but the verification is stale, missing, has gaps or needs a person (code it covered changed later) | turbo does not run it (plain GSD's `/gsd-autonomous` would run it again); adopt asks you about it |
   | built, waiting for verification | every plan has its SUMMARY, not checked off | its lane starts with verification and UAT |
   | being built | some plans have their SUMMARY | its lane goes on with the next plan |
   | planned | plans, no SUMMARY (or GSD's chunked plan outline is not finished: `planning not finished`) | its lane starts with freshness |
   | discussed | CONTEXT.md, no plans | no prep needed |
   | not started | no CONTEXT.md | the first run preps it in a slot |

2. **Markup** (slots mode, when `lanes.json` is missing or stale): the skill runs `turbo-run annotate brief` and the `turbo-lane-analyst` agent in your session; `adopt plan` checks its analysis. Refused twice: adopt goes on without markup and the first run marks the phases up.
3. **Questions, all at once** (`turbo-run adopt plan --json`, at most two, in one AskUserQuestion): `stale-closed` when there are closed phases with a stale verification (Keep closed, recommended; or Re-check: one pass of GSD's verifier per phase over the code as it is now, no tests or review again, the phase stays closed); `relax` when the analyst proposed to drop dependencies (the markup's card: remove all, recommended; leave as is; or your own words for some; none with `autonomy: max`, where they are applied with a decision record). A question is asked again only for phases its last answer did not cover. Answers: `--answers stale-closed=keep|reverify,relax=all|none|r1+r2`.
4. **Changes and one confirmation** (`turbo-run adopt plan --answers …`): the list of changes in plain words, the forecast and `plan: <sha256>`, the digest of the answers and the changes. Each change is listed only when it is not done yet: turbo's config and its `.gitignore`, `workflow.test_command` → `turbo-run test-changed` (the previous command kept as `test.full`) and `context_window` (the same as `turbo-run init`), `planning.chunked_parallel` `true` when the key is absent (an explicit `false` stays), `git.branching_strategy` `none` (slots mode, from `phase` or `milestone`), the markup (ROADMAP, `lanes.json`, a decision record for removed waits), the re-checks, and adopt's record `.planning/turbo/adopt.json`. Cancel changes nothing.
5. **Re-check** (only when you chose it): for each phase on the plan's `reverify pending:` line, `gsd-tools query init.execute-phase <N>` and only the Agent call of step `verifier_dispatch` of GSD's `verify-phase-goal.md`, without its hooks, code review and regression gate; one at a time on Windows (verifiers may run tests that lock files or take ports), up to three at a time elsewhere. Then `turbo-run adopt reverify <N>`: GSD's `verification status` `passed` keeps the fresh report for the commit (`phase N: re-verified: passed`); anything else moves the new report to `.planning/turbo/adopt/reverify-p<N>.md` and puts the committed report back byte for byte (the phase stays closed; the differences were most likely made by later phases). A report GSD cannot read (a status outside its set) is moved aside the same way before anything else, since it would stop GSD from listing any phase. A verifier that wrote nothing moves nothing. Files a verifier left elsewhere are listed (`left by the verifier: …`) and apply refuses until you commit or remove them. The outcomes wait in `.planning/turbo/run/adopt-reverify.json`; a phase listed there still counts as closed, so the digest you confirmed holds.
6. **Apply** (`turbo-run adopt apply --answers … --plan-sha <sha256>`): the plan is computed again, every refusal of point 1 runs again right before anything is written, and a digest other than the one you confirmed refuses (`refused: the plan changed since it was shown …`). Then `adopt.json` is written with `state: applying` and the paths it will touch, the changes are made, the record becomes `applied`, and exactly these paths go into one commit `chore(turbo): adopt`. `git revert` of that commit gives the project's files back (and removes `adopt.json`: the next `/turbo-adopt` starts afresh). Re-check reports of phases you then chose to keep closed are put back first.

The report (in `lang`, or the language the skill passes before a config exists) has six parts: where the project is; the closed phases without a fresh verification and the outcome of each re-check; lanes and the critical path before and after (plain GSD: the unfinished phases one after another; turbo: an event simulation with the scheduler itself — `max_lanes` slots, or one in `checkout` mode, the markup's areas and gates, the dependencies with the removed waits — every phase as long as the median of the milestone's last five done phases from the first to the last commit in its directory, or in phase lengths without such history), the speed-up from lanes alone and with turbo's speed-up inside a phase (an estimate: ×0.45); what changed, with the commit and `git revert <sha>`; what is left for you (phases with `owner-live` or `owner-signature` gates, open questions, verification or UAT items that need a person, agent worktrees with `turbo-run worktrees prune <path> --dry-run`, gates left off with `turbo-run gates restore <N>`, the slots and preps the first run makes); and the command that starts the run, `/turbo-autonomous`.

The first adopt of a project turbo already runs in still writes its record (`turbo is already set up; adopt's record written`). Run again with nothing new, `/turbo-adopt` asks nothing and commits nothing (`no changes: already adopted`). A commit that fails (a hook, signing, a held `index.lock`) is refused with `refused: git commit failed: …; run /turbo-adopt again to finish`, and the next adopt finishes it. An adopt cut after `state: applying` is accepted by the next one (its dirty paths are adopt's own), which lists `finish the adopt that stopped before its commit: …` first and commits once.

Outside adopt, `turbo-run start` (which `/turbo-autonomous` shows) and `turbo-run status` name the closed phases with a stale verification that turbo skips: `closed phases not re-verified: 24–31 (checked off, verification stale; turbo skips them) · /turbo-adopt` (`закрытые фазы без свежей проверки: …` in Russian). Without an adopt it names every such phase except those a turbo lane finished. Once `/turbo-adopt` ran, it records every phase finished at that time as decided, and a phase that finishes later is never named (its verification going stale as later phases change its files is the run's normal life); a second `/turbo-adopt` does not ask about it either. `status` leaves the line out while the supervisor runs, and keeps it in `.planning/turbo/run/closed-phases.json`, read again from GSD only after the ROADMAP, `adopt.json`, a phase's files or a lane's record changed.

## GSD settings turbo writes

turbo writes only these documented keys to `.planning/config.json`, always through `gsd-tools config-set` (a restore may then check out the file's committed bytes when they mean the same configuration):

| Setting | When | What |
|---|---|---|
| `workflow.test_command` | `turbo-run init` | `turbo-run test-changed`, only when a full test command is known (see Targeted tests above). It stays after an uninstall; see [Uninstall](#uninstall). |
| `context_window` | `turbo-run init` | turbo's `context_window`, only when `.planning/config.json` sets none (GSD's default is 200000). A value already there stays; `doctor` warns when it differs from turbo's. |
| `planning.chunked_parallel` | the prologue (`turbo-run gates chunked`) | Set to `true` once, only when the key is absent; an explicit `false` is kept. Committed when git tracks `.planning/config.json`. |
| `workflow.nyquist_validation`, `workflow.security_enforcement`, `workflow.ui_review`, `workflow.code_review` | only while GSD's execute-phase runs (`turbo-run gates off <N>`, then `gates restore <N>`) | Set to `false`. The old values are saved in `.planning/turbo/gates/p<N>.json`, and both files are committed when git tracks `.planning/config.json`. They are restored right after execute, before turbo runs these gates itself in parallel, because GSD's gate skills do nothing while their key is off. The four keys always get their old values back; when git tracks `.planning/config.json` and nothing else in it changed meanwhile (GSD's own `workflow._auto_chain_active: false` counts as no change), the file also gets back the exact bytes it had before `gates off`. |
| `phase_commit_docs.<N>` | only while the parallel workers of the prologue and the fan-out run (`turbo-run gates docs-off <N>`, then `gates docs-restore <N>`) | Set to `false` and put back right after; never committed. For a decimal phase such as `3.1` GSD cannot key this setting: `gates docs-off` answers `not done`, and that phase's workers run one at a time. |

Safeguards:

- `turbo-run gates off <N>` refuses while another phase's gates state is left over in `.planning/turbo/gates/`, and names `turbo-run gates restore <that phase>`.
- `turbo-run jobs <N> fanout` and `jobs <N> outcome` refuse while phase N's gates are still off.
- Every early stop of a phase (`needs-owner`, `failed`) restores the gates first.

If a phase was interrupted with its gates off (`.planning/turbo/gates/p<N>.json` exists), `turbo-run gates restore <N>` puts them back, and `turbo-run gates docs-restore <N>` does the same for `phase_commit_docs.<N>` (left over as `.planning/turbo/run/docs-p<N>.json`). Both print `nothing to do` when nothing is off. A safe-mode lane runs both by itself. `turbo-run status` and `turbo-run stop` list every such leftover with its command (`status --json`: `gatesOff`, the phases whose gates are off); neither restores anything.

## Automated UAT (`turbo-uat`)

When GSD's verifier ends with `human_needed`, GSD writes the phase's UAT file with pending items. The `uat` step of `/turbo-phase` then starts the `turbo-uat` agent, which checks what it can on a local stand and leaves the rest to you.

`turbo-run uat plan <N>` gives each pending item a class floor from a fixed rule list; the first match wins, from D down to A. The agent may raise a class (C to D included), never lower it, and `turbo-run uat record` refuses a lowered class. An item with a hermetic and a live part is split in two: the hermetic part is checked, and the live part becomes a new row.

| Class | Items | What happens |
|---|---|---|
| D (owner) | signatures, legal review, owner decisions, private or offline keys, 2FA, money; with `autonomy: "standard"` also deploys | Left `[pending]`, marked `class: D`. The phase stops before GSD's verify-work and asks you to sign them (below). |
| C (live) | third-party platforms, physical devices, desktop or mobile apps, production (read-only checks included; deploys with `autonomy: "max"`), live accounts, email, SMS and push delivery | Recorded as a deferred follow-up (`result: skipped`, `reason: "Deferred follow-up: …"`), which does not block the phase, and put on your checklist. |
| B (seeded) | needs a signed-in or seeded state: logins, sessions, roles, admin, accounts | Checked on the local stand with a one-time test account. |
| A (observable) | visible in a browser, over HTTP or a socket; or a property of the code itself: a plan's MUST NOT prohibition, which files a change touched | Checked on the local stand; a code property with `git grep` or `git diff` over the tracked code (`harness: static`), with no stand booted. |

An A or B check is recorded `pass` with evidence, or `issue` with what was seen and a severity; GSD's verify-work turns issues into a gap closure, which the phase runs up to `gap_rounds` times (default 1). The agent classes an item no rule matches itself, C when unsure. GSD's review wording on a plan's prohibition ("judgment-tier, unverified-prohibition: human review recommended") is no owner decision: such an item is a static code check (unless it asks what the running app shows, which is checked on the stand), recorded `pass` or `issue` with the search or diff as its evidence, and deferred to your checklist as C only when no search or diff can settle it. Without a usable local stand, A and B items are deferred to you as C, never recorded `pass`. Every row turbo-uat writes carries `source: turbo-uat`, `class` and `head`, plus `checks`, `harness` and the evidence hashes where it has them.

Stand rules:

- **Loopback only.** `uat.base_url` must be a loopback URL without credentials and not one of `uat.forbidden_hosts`; otherwise the stand is refused. Every URL a check requests is logged and checked with `turbo-run uat net-check`: a request that leaves loopback or reaches a host in `uat.forbidden_hosts` fails the item closed (it is deferred to you).
- **Temporary data.** `turbo-run uat stand <N> prepare` creates a temporary `DATA_DIR` under `.planning/turbo/run/uat-p<N>/`. A stand boots only when the app takes its data directory from `DATA_DIR`; otherwise its A and B items go on your checklist.
- **One-time credentials.** `prepare` also writes a random test account to a credentials file, which the agent reads only inside its scripts. The values are never printed and never written to evidence or the UAT file.
- **Isolated browser.** Browser checks run only from a Node script in a fresh Playwright context, never through a browser MCP tool or your browser profile. The project must have Playwright installed; turbo never installs packages or browsers. Items that cannot run that way go on your checklist.
- **Secret-scan.** `turbo-run uat record` scans the text evidence and the new UAT lines for the one-time password and common token formats. A finding refuses the whole record and names file, line and rule, never the value.
- **Cleanup.** `turbo-run uat stand <N> cleanup` removes the data directory, the credentials and the results file after every run, once the results are recorded.

Evidence: screenshots (PNG) and text logs go to `.planning/turbo/run/evidence/p<N>/`, which is git-ignored; the UAT file gets only their sha256 hashes.

What is left for you goes into one file per phase, `.planning/turbo/run/p<N>-owner.md`, in the `lang` language: what passed, what failed, your checklist and what needs your signature. `/turbo-autonomous status` lists these files (`turbo-run status --json`: `ownerRequests`).

- **C items only:** a checklist; it does not block the phase. You are notified once per phase, and again only when the checklist changes.
- **Anything else open:** the phase waits for you on every open UAT row, whoever wrote it: pending, missing, blocked, or skipped without a deferral reason (GSD's own rule). These include D items, the live part of a split item that turbo-uat left pending, and rows it could not record. The phase stops before GSD's verify-work as `needs-owner` and asks you on a question card to accept the items that wait for your signature, with the options Accept and Not now; turbo never answers that card by itself, and `turbo-run answer` and `uat sign` refuse an answer given from a lane's own session. Accept signs exactly those rows (`turbo-run uat sign <N> --answer <question>` writes `result: pass`, `source: owner` and your answer on each) and the phase goes on; Not now keeps it waiting. You can also sign them with `/gsd-verify-work <N>`, then run `/turbo-autonomous resume <N>`.
- **Skipped or blocked rows:** a row whose reason holds your dated ruling and a deferral to a numbered phase in one clause ("owner ruling 2026-01-08: defer to Phase 9", "owner ruling 2026-01-08 DEFERRED → Phase 9", "решение владельца 2026-01-08: отложить на фазу 9") becomes a deferred follow-up by itself (`turbo-run uat defer <N> --rulings`: GSD's `Deferred follow-up:` reason and a `## Deferred Follow-Ups` entry); nobody is asked to test it again. Only that form counts: a ruling without a date or without a phase number, or one with a question mark or a word that awaits, negates, limits or revokes it ("owner ruling pending", "only if", "draft", "cancelled", "нельзя", "отменено"), is none, and the row comes to you. Any other skipped or blocked row still makes the phase wait, and the request says plainly that it was not tested: confirm that it stays for later with `turbo-run uat defer <N> <numbers>` (for example `8,9`), save the UAT file in git (commit), then run `/turbo-autonomous resume <N>`; or test it with `/gsd-verify-work <N>`.
- Delete the file once you have handled it. A later `uat` step also removes it when nothing is left for you, and `/turbo-autonomous resume <N>` removes it (the phase writes it again while something is still open; a checklist already sent is not sent again).

## Lane slots

From v0.4 each lane works in a slot: a lasting local clone of your repository next to it, `<parent>/<repo>.turbo/lane-<k>` (`k` from 1 to `max_lanes`; `lanes.dir` moves them). `turbo-run lanes setup` creates the missing slots (`git clone --local`; a slot's `origin` is your checkout), gives each your checkout's local git identity, signing and line-ending settings, copies into it the git-ignored files that `lanes.copy` names (the `.env` files by default) and your `.claude/settings.local.json` with `worktree.baseRef: "head"` added (so GSD runs a wave's plans in parallel there), and lists those copies in the slot's `.git/info/exclude`, so they never show in its `git status` and are never committed. A file `lanes.copy` names that git does not ignore stops the setup before anything is created. A directory in a slot's place that is not a slot of this project is never touched.

Claude Code starts a background session only in a folder it trusts. `lanes setup` and `turbo-run lanes trust` write that trust for each slot into Claude Code's global config (`~/.claude.json`, or `.claude.json` in `CLAUDE_CONFIG_DIR`): one value, `projects["<slot>"].hasTrustDialogAccepted`, after a backup next to the file (`.claude.json.turbo-bak-<UTC time>`, one per command; only the 5 newest of that name are kept). When `.claude.json` is a link (dotfiles kept elsewhere), its target is written and the link stays. Nothing else in the file changes. When its format is not one turbo knows, or Claude Code keeps the file busy, turbo prints `open claude in <slot> once and accept the trust dialog` and exits with code 3. `lanes.trust_write: false`, or `--no-trust-write`, never writes the file.

Before each job a slot goes to a fresh branch at your main branch (`turbo/p<N>` for a phase, `turbo/prep-<N>`, `turbo/annotate`), and git removes what the last job left, except the copied files and `node_modules`. A slot with changes that no finished job explains is never used and never cleaned: you get its path and the changed files. A slot with a branch whose commits your main branch does not have (a failed or abandoned job's work) is not used either, and the branch is never reset or deleted. Dependencies are installed by the lockfile (`npm ci`, `pnpm install --frozen-lockfile` or `yarn install --immutable`, in each directory of `test.full`, through `bash -c`; `lanes.install` replaces the command) only when the lockfile changed since that slot's last install. The command runs through bash: on Windows Git Bash, found by its absolute path in `PATH`; when WSL's `C:\Windows\System32\bash.exe` comes first in `PATH`, the install is refused with that message (put Git's `bin` directory ahead of `System32`). A failed install leaves the slot on the new branch with no job recorded: it stays free, and the next job starts over. A `node_modules` that is a link is refused before anything in the slot changes: a slot never uses another checkout's dependencies.

turbo's state stays in your checkout (the control root): `.planning/turbo/run/`, `logs/`, `locks/` and your answers. The commands a lane runs in its slot find it through `TURBO_CONTROL_ROOT`, which the lane's session gets, or else through the slot's `origin`; a slot whose control root cannot be confirmed stops those commands with an error instead of keeping state itself. GSD's gate switches (`.planning/turbo/gates/`) belong to the slot. Your answers are committed in your checkout under the merge lock (`.planning/turbo/locks/merge`); when the lock stays busy, the answer is recorded and committed with the next merge.

`turbo-run lanes remove [<k>]` removes free slots (all, or slot k) and their trust; a slot with a job, with changes, or with work your main branch does not have (a branch of any name with commits it lacks, a stash, a detached HEAD commit) is kept. Links inside a slot that lead outside it are removed as links first, so nothing outside the slot is deleted. A slot is first renamed to `lane-<k>.removing-<time>`: when a program holds a file in it the rename fails and nothing is removed; when Windows stops the delete halfway, the renamed directory is left and the next `lanes setup` or `lanes remove` deletes it. `turbo-run doctor` checks the slots (`lane-slots`), their trust (`lane-trust`) and dependencies (`lane-deps`), and GSD's `git.branching_strategy` (`git-branching`, which must be `none`); none of these changes the mode. `lanes.mode: "checkout"` keeps v0.3's single lane in your checkout, without slots.

### Several packages in `test.full`

A project with nested packages that have their own test scripts (and CI that runs each of them) needs all of them in the full run. A nested package is a tracked `package.json` below the project root, outside `node_modules/` and outside `fixtures/` or `__fixtures__/` directories (test data), whose `test` script is not npm's default `echo "Error: no test specified" && exit 1`. List them in `test.full`:

```json
{
  "test": {
    "full": [
      "npm test",
      { "dir": "server", "command": "npm test" },
      { "dir": "app", "command": "pnpm test" }
    ]
  }
}
```

- A string entry runs at the project root; `{ "dir", "command" }` runs in `dir`. `dir` is relative to the project root, an existing directory, without `..`, and each directory appears once (the root, `""` or `"."`, included). Directories are compared by their real path: a link that leads outside the project root is refused, and another spelling of a listed directory (a link inside the project, other letter case on a case-insensitive file system such as Windows') counts as listed twice. A list that breaks these rules stops `turbo-run test-changed`, `turbo-run init` and `turbo-run start` with a config error; `turbo-run doctor` prints it as a warning.
- A full run runs every entry in order, through `bash -c`, in its own directory. A red entry does not stop the others: each red one is named (`server: failed (exit code 1)`, or `server: failed (its directory server is missing)` when the directory disappeared during the run), and the run exits with the first red entry's code. The last-green marker is written only when every entry is green.
- A targeted run plans each entry on its own. A changed file belongs to the entry with the deepest matching `dir`; the root entry takes the rest. The rules of [Targeted tests](#what-happens) apply inside the entry's directory: its own `package.json` test script and `pretest`/`posttest` hooks, its runner config, the packages nested below it. An entry's tests that reach its changed file through files of other entries are selected too. Each entry counts its changes and its targeted runs from its own last full green run; an entry with no change that concerns it is skipped. Each entry logs its own line, for example `server: targeted: 2 related test file(s)`.
- A dependency or config file changed anywhere (a `package.json`, a lockfile, a `tsconfig*.json`, a `*.config.js`, `.planning/turbo/config.json`) runs every entry in full: another entry may load that package's code.
- Any other change outside an entry makes that entry run in full when the entry may depend on it:
  - a file in another entry that the entry's command may also run: `node --test` without path arguments, or with a path or glob that covers that directory; `jest` and `vitest` search nested directories too. So a root script `node --test` (node's default patterns) also runs the nested entries' tests, and a change in a nested entry runs the root entry in full as well. Give the root script explicit paths or globs (`node --test "test/**/*.test.mjs"`) to avoid that;
  - a file the entry's files mention or import, directly or through other files of the project. A relative import of a package directory (`'../server'`) reaches every file of that package;
  - a package the entry's files import by name (`'@scope/server'`) that contains the file or reaches it.
- Across entries, an import is seen only through a relative path, a file name in a quoted string, a package directory or a package name. An alias that names none of them (for example a tsconfig `paths` alias `'@core'` for another package's `src/index.ts`) is not: a change behind such an alias does not make the importing entry run in full. Run with `TURBO_FULL=1`, or import through the package name.
- `TURBO_FULL=1` runs every entry in full. At the phase end (see [Inside a phase](#inside-a-phase-turbo-phase)) every entry with a code change since its own last full green run runs in full.
- The import graph (`test.import_graph`) is recorded and used for the root entry only; nested entries use the mention rule.
- `turbo-run init` writes the list when it creates `.planning/turbo/config.json` and nested packages exist, and prints it: the root command first (none when the root has no `package.json` or its `package.json` has no real test script, such as a workspaces root), then one entry per package, with `npm test`, `pnpm test` or `yarn test` from the package's lockfile or the nearest one above it. With an existing config, init changes nothing: it prints `warn: nested package <dir> has its own test script that test.full does not run` for each package and the entries to add.
- `turbo-run doctor` prints `warn nested package <dir> has its own test script that test.full does not run` for each nested package no entry runs. When such a package changes, `test-changed` logs a warning and runs as with a single command (the entry that contains the package runs in full).
- Each record of the last-green marker names the command of its full run; when an entry's command changes (also in a config git does not track), that entry runs in full. After an upgrade, an older last-green marker counts as the root entry's until its next full run; a nested entry without a record of its own runs in full once.

## Safety

- **Permissions.** Background sessions run with `--permission-mode bypassPermissions` by default, so nobody has to approve tool calls. Set `lane_permission_mode` to another Claude Code permission mode to change that. Your existing Claude Code hooks still apply in every session.
- **No questions.** `AskUserQuestion` is disabled in background sessions (`--disallowedTools AskUserQuestion`). At each decision point a session takes the recommended option and records the decision where GSD records it. The checkpoints of the plans are your questions (see [Owner questions](#owner-questions)); sessions never answer them, and `turbo-run answer` refuses to run inside a session.
- **Owner-only steps.** A session does everything else in the phase first, then stops and you are notified for steps only you can do:
  - signatures and decisions reserved for the project owner;
  - live sessions with your own third-party accounts;
  - physical devices;
  - offline keys;
  - your 2FA;
  - money.

  Verification items GSD marks `human_needed` are checked without you where possible: in full mode by the `turbo-uat` agent (see [Automated UAT](#automated-uat-turbo-uat)), in safe mode by the session itself (browser checks with Playwright against a locally started app, HTTP and socket checks, test accounts in the app under test); only owner-only items are left to you. Only with `autonomy: "max"` are sessions told to deploy themselves.
- **Closed phases stay closed.** A phase checked off in the ROADMAP and fully implemented is never rescheduled, even if GSD later reports its verification stale. Re-verifying it is up to you: `/gsd-execute-phase <N>`.
- **Git and data.** Sessions are told never to force-push, never to rewrite published history and never to delete data without a dry run first. They never push either: with `push.mode` set, the supervisor does (see [Push and CI](#push-and-ci-optional)).
- **Agent worktrees.** A Claude Code agent that works in a worktree leaves `.claude/worktrees/agent-<id>` on a branch `worktree-agent-<id>`, locked while the session that made it runs. Run `turbo-run worktrees prune --dry-run` first: it lists `would remove <path>` for each clean one whose commits your current branch already has, and `kept <path>: <why>` for the others (uncommitted changes, commits not merged, a link inside it that leads outside it, such as a junction to another checkout's `node_modules`, or a lock of a process that still runs). `turbo-run worktrees prune` then removes those with `git worktree remove` and `git branch -d`, never forced; a Claude Code lock is released only when its process is gone. Files git ignores in such a worktree (an installed `node_modules`, a copied `.env`, a local database) go with it, as with any `git worktree remove`. It runs in your main checkout only. When a program holds a file, git may give the worktree up and leave part of its folder: `partly removed <path>` says so; delete that folder once nothing holds it. `turbo-run worktrees prune <path>` takes one worktree; the fan-out runs it (dry run first) for the merged Nyquist worktree, where the lock of the lane's own session is released too, since its agent has returned.
- **Files outside the lane.** A lane's file tools (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`) cannot write outside its checkout, its temporary directory and the control root's `.planning/turbo` (`lanes.write_guard`). Bash can: the guard sees only the file tools, so a redirect or a script still writes anywhere the session's user may. The supervisor then reports new entries next to the project in its log, and scratch-looking ones to you, and never deletes them (see [Use](#use)).
- **Releases.** Sessions never overwrite a running executable: a build goes into a new directory named after the UTC time under the release directory (`release/2026-10-11T12-00-00Z/`, for example). A file that a running process holds is never freed by killing the process: the session stops for you with the file, the process and the exact step (for example, quit the app). Making the app quit on request (an IPC call, or `--quit` sent to a second instance) is the project's own work; the stop reason recommends it. The same rule goes into every executor prompt, also in your own `attend` sitting (see [Live sittings](#live-sittings)).
- **Leftover hook processes.** A live run on Windows found GSD hook processes of lane sessions (`gsd-graphify-update.sh`, `gsd-statusline.js`) still running about two hours after their sessions had ended. They belong to Claude Code and GSD, and turbo does not stop them, because nothing proves which lane, or which of your own sessions, started one: the hooks run from the same `hooks/` folder for every session; on Linux and macOS a process whose parent ended is handed to init (or a subreaper), so its parent no longer names the session; on Windows turbo cannot read another process's environment or working directory; and whether the process id that `claude agents` reports is the parent of a session's hooks is not established. turbo never kills a process by name or command line. To check by hand on Windows (PowerShell), list the GSD hooks whose parent process is gone and that started more than an hour ago: `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'gsd-(graphify-update|statusline)' -and $_.CreationDate -lt (Get-Date).AddHours(-1) -and -not (Get-Process -Id $_.ParentProcessId -ErrorAction SilentlyContinue) } | Select-Object ProcessId, CreationDate, CommandLine`. The age matters: the graphify hook detaches a rebuild of the knowledge graph on purpose, and under Git Bash that rebuild may run under a process that still shows the hook's command line and has no parent; while `.planning/graphs/.last-build-status.json` of a project says `running`, its rebuild is not finished. An hour-old hook without a parent serves no session; stop it with its children by `taskkill /PID <ProcessId> /T /F` in PowerShell or `taskkill //PID <ProcessId> //T //F` in Git Bash. On Linux and macOS, `ps -eo pid,ppid,lstart,args | grep -E 'gsd-(graphify-update|statusline)'` lists them; a parent of 1 (or of your session manager) means its session is gone.
- **GSD stays untouched.** turbo never modifies GSD files and writes to the GSD config only the keys in [GSD settings turbo writes](#gsd-settings-turbo-writes), through `gsd-tools config-set` (a restore may then check out the file's committed bytes when they mean the same configuration). It changes STATE.md only through GSD's own state commands (`turbo-run state-sync`, see [Context and the resume position](#context-and-the-resume-position)).
- **Supervisor files.** State, logs and locks live in `.planning/turbo/run/`, `logs/` and `locks/`, which `init` adds to a `.gitignore` there. `run/` also holds the `/turbo-phase` progress, the owner requests, the UAT stand and its evidence, and the push requests, push results and lane inboxes. Each lane's temporary directory lives outside the project, in `~/.claude/turbo/tmp/<project key>/p<N>/` (see [Use](#use)). Versions before 0.3.2 kept it in the git directory: a leftover `.git/turbo/tmp/` is no longer used and can be deleted while no lane runs. `.planning/turbo/gates/` holds a file only while a phase has GSD's gates off, committed when git tracks `.planning/config.json`. The targeted-test runner keeps its last-green marker (one record per `test.full` entry) outside the working tree, in the git directory (`git rev-parse --git-path turbo-last-green`, usually `.git/turbo-last-green`).

## Push and CI (optional)

Off by default (`push.mode: "off"`). Needs git 2.31 or newer (`turbo-run doctor` checks it). Lanes never push. With `push.mode` set, a lane asks for a push, and the supervisor, the only process that pushes, makes it at its next check:

- **When.** `after-wave`: after each wave of GSD's execution, and once at the end of the phase. `after-phase`: once at the end of the phase. A lane also asks after each CI fix, and for a plan of the phase whose task pushes or waits for CI (the lane runs that task itself after the plan's wave).
- **Checks before a push.** The supervisor fetches the remote branch, which must already exist and be an ancestor of HEAD; otherwise nothing is pushed and you are notified. A requested commit that the remote branch already contains (you pushed it by hand since the request) is answered `already pushed`: nothing is scanned or pushed, you are not notified, and the lane goes on (exit 0). turbo does not watch the CI of that commit: you pushed it, and turbo checks nothing new. It then scans every commit it would push, merges included: each added line against the secret patterns turbo also uses for UAT records, and each added or changed file name against `.env*`, `*.session`, `*.db`, `*.sqlite`, `*.log`, `accounts.json`, `*.pem` and `*.key`. Files git treats as binary are scanned as text. A range that adds or changes a Git LFS pointer is refused (`lfs-content-not-scanned`): the content it stands for is not in the commits, so turbo cannot scan it; push such a range yourself. A finding stops the push; the notification names the file and the kind of finding, never the value. The patterns also match ordinary code now and then (an assignment to a variable named `token` or `password`, a test fixture); prose such as a test verdict `PASS: 14/14` or "the tests pass: ..." is no finding (a bare `pass` counts as a key where config puts it: quoted, before `=`, after `_` as in `DB_PASS:`, lowercase after indentation, `.`, `{` or `,` as in `smtp.pass:`, or `pass:x1y2z3`). Check the named files. When a finding is a false alarm in text, run `turbo-run push-allow <N>`: it lists the refusal's id and where each secret-pattern line is (commit, file, line; never the value) and writes nothing. After checking those lines, run `turbo-run push-allow <N> <refusal>` with that id (the notification names it too): the fingerprints of exactly those lines go into `~/.claude/turbo/allow/<project key>.txt`, outside the checkout (a fingerprint stands for one exact line of one file, so a new secret in the same file is still refused; the id of an older refusal allows nothing), and the supervisor scans the same request again at its next check and tells you how many lines were allowed. A lane never runs it. A forbidden file name or an LFS pointer cannot be allowed: when those are clean, push that range once yourself (`git push <remote> <branch>`), and turbo goes on from there. The same findings and lines are not notified twice.
- **The push.** `git push <remote> <sha>:refs/heads/<branch>` for exactly the commit the lane asked for and the branch it asked from, and only while the checkout is still on that branch and the commit still on it (otherwise the request fails and you are notified): never forced, never with `--no-verify`, so your pre-push hooks run (one that takes longer than 5 minutes fails the push). git runs with credential prompts off, so its credentials must work without a prompt.
- **CI.** With `push.ci: "github"`, the supervisor watches the runs of the pushed commit with `gh run list --commit` in the GitHub repository of `push.remote` (install the GitHub CLI and log in with `gh auth login`). The repository comes from the remote's push URL: `owner/repo` on github.com, `host/owner/repo` on a GitHub Enterprise host, which turbo asks only after `gh auth status --hostname <host>` succeeds (log in with `gh auth login --hostname <host>`), so no token goes to a server gh was not set up for. Without gh, without a login for that host, or with a remote that is not a GitHub repository, pushes go on without CI results and you are told once. A run that ends in `failure`, `timed_out` or `startup_failure` is red: the last 200 lines of its failed log, secrets masked, go into the lane's inbox (`turbo-run inbox <N>`) and you are notified. The lane finds the cause, fixes it in one commit and asks for a new push, at most `push.ci_fix_rounds` times in a phase; after that it stops for you. A commit with no run after 5 minutes counts as having no CI. Runs that do not finish within `push.ci_timeout_minutes` notify you; the lane goes on.
- **End of a phase.** The lane waits for its last push and that CI result before it records the phase done.

The requests, results and inboxes live in `.planning/turbo/run/` (`p<N>-push-request.json`, `p<N>-push.json`, `p<N>-inbox.jsonl`); the allowed fingerprints in `~/.claude/turbo/allow/<project key>.txt`. The supervisor reads the push settings when it starts: after changing them, stop it and start it again.

## Telegram (optional)

1. Set two environment variables where Claude Code starts, before `/turbo-autonomous` (the supervisor inherits them):
   - `TURBO_TELEGRAM_TOKEN`: your bot token;
   - `TURBO_TELEGRAM_CHAT`: the chat id to send to (to answer questions there too: your private chat with the bot, see below).
2. Enable it in `.planning/turbo/config.json`:

   ```json
   { "notify": { "telegram": true } }
   ```

The messages are the same short texts as the desktop notifications: phase number, status and what to do next.

To answer the owner questions in Telegram too (see [Owner questions](#owner-questions)), also set `"answer": { "telegram": true }`. `TURBO_TELEGRAM_CHAT` must then be your private chat with the bot, whose id is your user id: turbo takes button presses only from you, and replies only from you in that chat; it drops everything else (it logs how many, never the content).

- Each open question comes as one plain-text message in `lang`, in the same words as the live view: the phase, plan and task, the question, its context, its options with their descriptions (the recommended one marked ★), and a button for each of the first four, with its number and text, plus "Your own answer…" where your own words count; the text counts the further options, answered through "Your own answer…". A button works once. Times are your local time.
- "Your own answer…" asks for your answer as a reply to its message, up to 2000 characters. An answer that looks like a secret is refused; delete it from the chat.
- A question answered anywhere loses its buttons and shows the answer that stands. When a question changes (re-planned, or reopened when the lane stopped at it), its old message says so and a new one comes; a button of the old one records nothing.
- While questions are open, the supervisor asks Telegram for presses and replies at each check, waiting up to `poll_seconds` (at most 50 seconds). Use a bot of its own for each project: a bot with a webhook, or one that another program or another turbo run also reads, loses presses. turbo's state (the update offset and the one-time buttons) is in `.planning/turbo/run/telegram.json`; after a change of bot or chat, the open questions are sent again. The bot token never appears in a log or in that file.
