# gsd-turbo — дизайн

Дата: 2026-10-06 · Статус: черновик на ревью владельца · Основа: GSD (`@opengsd/gsd-core`) 1.16.0, Claude Code 2.1.291

## 1. Цель

Сократить календарное время от открытия майлстоуна до его закрытия **в 2–4 раза** за счёт большего расхода токенов. Качество гейтов не снижается: TDD, ревью, верификация, security и Nyquist остаются. Меняется только то, **когда** и **сколько параллельно** они идут, и **кто** закрывает проверки, которые можно закрыть без человека.

Мерило — время критического пути майлстоуна, без ожидания действий, которые физически требуют владельца.

Пакет должен быть переносимым: отдельный репозиторий, установка одной командой, без путей и секретов конкретного пользователя. Им можно поделиться.

## 3. Архитектура: три уровня

```
Уровень M — майлстоун
  turbo-run (Node-супервизор, без LLM, отсоединённый процесс)
    ├─ планирует полосы по графу фаз (Depends on + Areas + Gates)
    ├─ полоса = git worktree + фоновая сессия  claude --bg "/turbo-phase N"
    ├─ перезапускает сессию, остановившуюся по контексту (авто-продолжение)
    ├─ сливает полосу в main; STATE/ROADMAP пишет только он (единственный писатель)
    ├─ держит мьютексы общих ресурсов (prod-деплой, живая сессия владельца)
    └─ шлёт уведомление, когда нужен владелец, и продолжает другие полосы

Уровень P — фаза (внутри фоновой сессии полосы)
  /turbo-phase N
    свежесть → план (параллельный пролог и планировщик) → turbo-exec (DAG)
    → гейты веером → fix → verifier → turbo-uat → завершение

Уровень 0 — заранее
  /turbo-new-milestone, /turbo-plan-milestone, /turbo-adopt
    discuss + research + VALIDATION для всех будущих фаз параллельно;
    разметка ROADMAP: Areas / Gates / Parallel with; проверка свежести по base_sha
```

Фаза запускается как **верхнеуровневая** сессия, а не как вложенный агент. Поэтому её исполнители — обычные субагенты уровня 1, и форк не зависит ни от неверного флага GSD (F1), ни от лимита глубины.

## 4. Компоненты

### 4.1 `turbo-run` — супервизор майлстоуна (`bin/turbo-run.mjs`)
- **Вход:** `.planning/ROADMAP.md`, `.planning/state.json`, `.planning/turbo/lanes.json` (разметка от adopt / plan-milestone), `.planning/config.json` → блок `turbo`.
- **Цикл (раз в 20–30 с):**
  1. Готовые фазы: зависимости закрыты; `Areas` не пересекаются с работающими полосами; свободны требуемые `Gates`; есть место по `turbo.max_lanes` (по умолчанию 3).
  2. Для готовой фазы:
     - `git worktree add ../<repo>.turbo/p<N> -b turbo/p<N>` от текущего `main`;
     - зависимости ставятся копией или `npm ci`. Junction не используется: очистка worktree через junction стирает `node_modules` основного дерева;
     - `claude --bg --name turbo-p<N> --permission-mode <turbo.lane_permission_mode> "/turbo-phase <N>"` с `cwd` полосы.
  3. Опрос `claude agents --json` и файла статуса полосы `.planning/turbo/run/p<N>.json`. Его пишет `/turbo-phase`, значения: `running | paused-context | needs-owner | done | failed`.
  4. Реакции:
     - `paused-context` → новая сессия `"/turbo-phase <N> --resume"` (авто-продолжение);
     - `needs-owner` → уведомление, полоса ждёт, остальные идут;
     - `done` → слияние (§5.3) → `gsd-tools` завершает фазу в `main` → следующая.
  5. `failed` или 3 перезапуска без прогресса → полоса останавливается, уведомление с логом.
- **Подкоманды:** `turbo-run start|status|stop|lock <gate>|unlock <gate>|notify <msg>`. `start` отсоединяется сам (`spawn detached` + `unref`) и пишет pid-файл. Повторный `start` при живом pid ничего не делает.
- **Без LLM.** Решения детерминированные и покрыты unit-тестами. LLM вызывается только для разрешения конфликта слияния (отдельная `claude -p` сессия).

### 4.2 `/turbo-autonomous` — точка входа
1. Проверить совместимость (`turbo doctor`).
2. Если проект не размечен, запустить `/turbo-adopt`.
3. `turbo-run start`.
4. Показать таблицу полос и как смотреть ход: `turbo-run status`, `claude attach turbo-p<N>`.

Сессию можно закрыть: супервизор и полосы живут сами.

### 4.3 `/turbo-phase N` — конвейер фазы
1. **Свежесть.** Для CONTEXT, RESEARCH, PATTERNS и PLAN с `base_sha` выполняется `git diff --name-only <base_sha> HEAD -- <files_modified ∪ read_first ∪ упомянутые пути>`. Затронутые артефакты пересобираются точечно: удалён или переименован файл → перепланировать этот план; изменён файл, на строку которого ссылается план → повторить source-grounding для этого плана.
2. **Discuss.** Пропускается, если CONTEXT.md есть (сделан заранее). Иначе — режим assumptions с рекомендованными ответами, без вопросов.
3. **План.** `gsd-plan-phase` с `workflow.plan_chunked` + `planning.chunked_parallel`. Пролог (research ∥ ui-phase ∥ ai-integration ∥ intel) запускается веером. Каждый артефакт получает `base_sha`.
4. **Исполнение: `turbo-exec`** (§4.5) вместо цикла волн.
5. **Гейты веером** (§4.6).
6. **turbo-uat** (§6), если verifier вернул `human_needed`.
7. **Завершение.** Пишется `run/p<N>.json` `done`. STATE/ROADMAP сама полоса не завершает, это делает супервизор после слияния.
8. **Контекст.** На ~55% сессия доводит текущий шаг, пишет `HANDOFF.json` и `paused-context`, затем выходит. Возобновление идёт с того же шага.

### 4.4 `/turbo-plan-milestone`, `/turbo-new-milestone`
- `/turbo-new-milestone` = `/gsd-new-milestone`, затем `/turbo-plan-milestone`. У new-milestone нет точки расширения, поэтому это обёртка.
- `/turbo-plan-milestone`: для **каждой** будущей фазы параллельно идёт discuss (assumptions, рекомендованные ответы), доменное исследование и стратегия VALIDATION. Каждая фаза готовится в своём временном worktree отдельной фоновой сессией `turbo-prep`. Супервизор переносит в `main` только `.planning/phases/<N>-*` и делает один коммит.
- **Разметка ROADMAP** (агент `turbo-lane-analyst`) — по каждой фазе:
  - `**Areas**:` маски путей; источник — цель, требования, research и реальный код;
  - `**Gates**:` общие ресурсы: `prod-deploy`, `owner-live`, `owner-signature`, `packaged-build`;
  - `**Parallel with**:` вместо прозы в `Depends on`. Проза «runs in parallel with Phase N» парсер GSD читает как зависимость, отсюда ложный цикл.
- **Матрица конфликтов → `lanes.json`.** Если ослабление зависимостей меняет порядок, объявленный в ROADMAP, пишется ADR в `.planning/decisions/` (если каталог есть) или в `.planning/turbo/DECISIONS.md`. При `turbo.autonomy: max` оно применяется сразу, владелец может откатить.
- **Детальные планы** (pattern map, ссылки на строки) заранее **не пишутся** (F10). Их строит `/turbo-phase` в момент, когда предшественники влиты. Для следующей фазы той же полосы супервизор запускает планирование, пока текущая фаза проходит гейты.

### 4.5 `turbo-exec` — исполнение графом, а не волнами
- **Готовые планы:** `phase-plan-index` → `ready_plans` минус запущенные (GSD уже считает `ready` по SUMMARY зависимостей, `phase.cjs:940-967`).
- **Пересечения файлов:** план не запускается, пока работает другой план с общим файлом (`file-overlap-partitioner.cjs`). Вся волна в последовательный режим не уходит.
- **Запуск:** логика `per-plan-worktree-gate` → `worktree.create` → `gsd-executor` с `isolation: worktree` (агенты по одному на сообщение — из-за `.git/config.lock`).
- **Слияние:** сразу по завершении плана, под мьютексом слияния, через `worktree.cleanup-wave --manifest <plan>`. После каждого слияния запускается **целевой** тест (§4.7). Полный набор идёт один раз в конце фазы.
- **Ёмкость:** `dispatch-capacity` (20) или `turbo.max_executors`.

### 4.6 Гейты веером
- **Встроенные хуки выключаются в конфиге фазы** (`workflow.nyquist_validation`, `security_enforcement`, `ui_review`, `code_review` = false), turbo запускает их сам:
  - **параллельно**, только чтение: security-audit, ui-review (если UI-фаза), code-review без fix;
  - nyquist идёт в своём worktree (пишет и коммитит тесты), затем вливается;
  - затем code-fix, по одной находке на коммит, последовательно; после каждой итерации — тесты, покрывающие прошлые фиксы;
  - затем verifier.
- **Коммиты артефактов сериализует оркестратор:** `phase_commit_docs.<N>=false` на время веера, затем один коммит. Это обходит отсутствие повтора при `index.lock` (F9).

### 4.7 Целевые тесты — `turbo-test-changed`
- Скрипт кладётся в проект при adopt и прописывается в `workflow.test_command`.
- По `git diff --name-only <base>` выбирает затронутые тесты. Адаптеры:
  - `node --test` (по соседству и импортам);
  - jest/vitest `--findRelatedTests` / `related`;
  - pytest по модулям.
- Если ничего не выбрано или тест непонятен, запускается полный набор.
- `TURBO_FULL=1` даёт полный прогон; так его вызывают регрессия и финальный гейт фазы.

### 4.8 `/turbo-adopt` — перевод уже идущего майлстоуна на turbo
Для проектов, где майлстоун открыт и работает на обычном GSD. Идемпотентна: повторный запуск ничего не ломает, только досчитывает.

1. **Проверка.** `turbo doctor`: версия GSD, нужные команды `gsd-tools`, git чист, нет живых полос.
2. **Где проект сейчас.** Текущая фаза и её стадия по `state.json` и STATE.md: план, исполнение, гейты, UAT. Незакрытые human_needed и UAT, отложенные проверки.
3. **Конфиг.**
   - Блок `turbo` (§7) с профилем автономии.
   - `workflow.test_command` → `turbo-test-changed` (адаптер выбирается по проекту).
   - `plan_chunked`/`chunked_parallel`, `worktree.baseRef: head`, пороги контекста.
   - Разделы, которые GSD хочет вопросом, заполняются рекомендованными значениями.
4. **Аудит ROADMAP.**
   - Ложные циклы из прозы в `Depends on` переносятся в `Parallel with`.
   - Разметка `Areas`/`Gates` для всех незавершённых фаз. Источник — цели, требования, уже написанные планы (`files_modified`) и код.
   - Матрица конфликтов, `lanes.json`.
   - ADR, если меняется объявленный порядок. Предложения разрезать фазу, когда жёсткий стык касается только её части (пример: «C-код» отдельно от «C-ротации», §10), — тоже через ADR.
5. **Заранее.** `/turbo-plan-milestone` для фаз, у которых ещё нет CONTEXT/RESEARCH. Уже существующие артефакты получают `base_sha`, считанный по их коммиту, и проверку свежести.
6. **Старые human_needed.** `turbo-uat` проходит открытые A/B-пункты прошлых фаз. Остальное сводится в один запрос владельцу.
7. **Отчёт.**
   - Полосы и критический путь до и после, прогноз ускорения, что осталось владельцу.
   - Команда запуска `/turbo-autonomous`.
   - Все изменения одним коммитом `chore(turbo): adopt`, откат — `git revert`.

## 5. Параллельность и безопасность

### 5.1 Изоляция полос
- У каждой полосы свой worktree и ветка `turbo/p<N>`. Имена `agent-*` запрещены: GSD отказывается работать на таких ветках, `execute-phase.md:443`.
- `GSD_SESSION_KEY` уникален на полосу, иначе `milestone.lock` склеит сессии.
- Номера фаз (`phase add/insert`) меняются только в `main`, только супервизором.

### 5.2 Единственный писатель
- STATE.md, ROADMAP.md и REQUIREMENTS.md в `main` пишет только супервизор, через `gsd-tools`.
- Правки этих файлов внутри полосы при слиянии отбрасываются, затем повторяются командами `gsd-tools` в `main`.

### 5.3 Слияние полосы
1. `git merge --no-ff turbo/p<N>`.
2. STATE/ROADMAP/REQUIREMENTS берутся из `main`.
3. При конфликте кода — отдельная `claude -p` сессия-разрешатель, после неё целевые и полные тесты.
4. Если разрешить не удалось — полоса в `needs-owner`.
5. После слияния: `gsd-tools phase complete N`, `state sync`, пуш по правилам владельца.

### 5.4 Мьютексы ресурсов
`prod-deploy`, `owner-live` и т.п. — файловые блокировки в `.planning/turbo/locks/`. Их держит супервизор, полоса берёт через `turbo-run lock`.

### 5.5 Сбой и откат
- Каждая полоса изолирована. Остановка полосы не трогает `main`.
- `turbo-run stop` останавливает сессии (`claude stop`) и оставляет worktree для разбора.

## 6. Автономия и human_needed — `turbo-uat`

### 6.1 Политика `turbo.autonomy`
| Профиль | Что делает агент сам |
|---|---|
| `standard` | браузерные и HTTP-проверки на локальном стенде, тестовые учётки в тестируемом приложении |
| `max` (у владельца) | то же + деплой со страховкой (снапшот → деплой → health-check → авто-откат), проверки прода только на чтение тестовыми учётками проекта, ротации и операции, у которых есть dry-run |

**Всегда за человеком:**
- подписи и решения «на правах владельца»;
- живые сессии на сторонних платформах с его аккаунтами;
- физические устройства;
- офлайн-ключи;
- его 2FA;
- деньги.

### 6.2 Классификатор пунктов
Первое совпадение побеждает:
- **D (владелец):** подпись, юридическое, ключи, деньги. При `standard` сюда же деплой.
- **C (живое):** сторонняя платформа, устройство, внешнее десктоп-приложение, прод на запись.
- **B:** нужны засеянные аутентифицированные состояния.
- **A:** наблюдаемо через браузер, HTTP или сокет.

Пункт с герметичной и живой половинами делится на два.

### 6.3 Исполнение
- **A/B:** Playwright (MCP или скрипт) против стенда из `turbo.uat`: `boot`, `base_url` (только loopback), `seed`, `forbidden_hosts`.
- **Страховочные правила:**
  - allowlist сети;
  - временный DATA_DIR;
  - одноразовые креды, значения никогда не печатаются;
  - уборка после прогона;
  - secret-scan доказательств.
- Если блока `turbo.uat` нет, агент пытается вывести стенд из проекта (тестовые хелперы запуска, `npm run dev`). Не вышло — пункт остаётся владельцу.
- **Запись в UAT.md:**
  - `result: pass|issue`, `source: turbo-uat`, `class`, `checks`, `harness`, `head`;
  - `evidence` — манифест sha256 скриншотов, сами PNG в gitignore;
  - провал → `issue` и обычный gap closure.
- **Владельцу — один пакетный запрос на русском:** что прошло, что упало, что осталось. C-пункты одним чек-листом, D-пункты одним вопросом на подпись. Отложенные C пишутся как `skipped` с `reason: "Deferred follow-up: …"`, чтобы не блокировать закрытие фазы. Полоса при этом идёт дальше.

## 7. Конфиг (`.planning/turbo/config.json`)

Конфиг лежит в отдельном файле, а не блоком внутри `.planning/config.json`: так GSD-валидация схемы не спотыкается о чужие ключи. В конфиг GSD turbo пишет только документированные ключи (`workflow.test_command` и т.п.) через `gsd-tools config-set`. `run/`, `logs/` и `locks/` не попадают в git: для этого в `.planning/turbo/` лежит свой `.gitignore`.


## 8. Совместимость с GSD
- **Только чтение + свои команды.** Файлы `gsd-core` не правятся. Turbo пользуется `gsd-tools` (state, phase, worktree.*, phase-plan-index, commit), агентами GSD (`gsd-executor`, `gsd-verifier`, `gsd-security-auditor`, …) и ключами конфига.
- **Версии.** `turbo doctor` проверяет `gsd-core/VERSION` против `engines.gsd` (стартовый диапазон `>=1.16.0 <1.17`) и наличие нужных `gsd-tools` команд. Если что-то не так — режим `safe`: супервизор + авто-продолжение + целевые тесты, без turbo-exec и веера гейтов.
- **Upstream.** Отдельный PR в `open-gsd/gsd-core` с исправлением `backgroundDispatch` для Claude (F1). На работу turbo он не влияет.

## 9. Распространение
- Репозиторий `gsd-turbo`, лицензия MIT с атрибуцией GSD, если используются его фрагменты.
- Установка: `node install.mjs` (Windows / macOS / Linux, Node ≥ 20). Копирует `skills/turbo-*`, `agents/turbo-*`, `bin/` в `~/.claude/` и пишет манифест. Удаление — `node install.mjs --uninstall`.
- Никаких путей, имён, секретов и правил конкретного владельца. Его профиль автономии живёт в его конфиге проекта.
- Уведомления: Windows toast, macOS `osascript`, Linux `notify-send`; опционально Telegram (`TURBO_TELEGRAM_TOKEN`, `TURBO_TELEGRAM_CHAT` из env).

## 10. Оценка ускорения

Основа — фаза эталонного проекта (F3). Цифры прогнозные, пересчитываются по первым двум фазам на turbo.

| Этап фазы | Сейчас | turbo | За счёт чего |
|---|---|---|---|
| discuss + research | 1,05 ч | ~0,1 ч на критическом пути | сделаны заранее, параллельно; остаётся проверка свежести |
| pattern + plan | 1,2 ч | 0,2–0,5 ч | параллельный пролог и планировщик; план следующей фазы идёт во время гейтов текущей |
| execute | 4,0 ч | 2,0–2,4 ч | простой 1,4 ч → 0 (авто-продолжение); граф вместо волн; целевые тесты вместо 10 полных прогонов |
| гейты | 1,3 ч | ~0,5 ч | веер вместо цепочки |
| UAT | 0,5 ч владельца | ~0,2 ч агента | turbo-uat; подписи пакетом, не блокируют полосу |
| **Фаза** | **~7,5 ч** | **~3–3,7 ч** | **≈ 2–2,5×** |

**Майлстоун.**
- Остаток текущего майлстоуна эталонного проекта: 6 фаз × ~7,5 ч ≈ 45 ч конвейера. Обозначим их так: стартовая, A, B, C, D, финальная.
- С turbo: стартовая (~3,5 ч) → две полосы {A → B} ∥ {C-код → D} (~7 ч) → стык ротации (~1 ч) → финальная (~3 ч). Итого **≈ 14–15 ч, то есть ≈ 3×**.
- В новом майлстоуне, где разметка Areas есть с самого начала, полос может быть больше: **3–5×**.
- Сверх этого исчезают ночные и дневные простои между сессиями: сейчас каждая пауза ждёт, пока владелец перезапустит.

**Токены:** примерно +25–50%. Это работа на проверку свежести, перепланирование устаревшего, параллельные гейты и разрешение слияний.

**Не ускоряется:** живые сессии владельца, церемонии, подписи, единственный прод-сервер для деплоев (мьютекс).

## 11. Риски и что проверить первым
1. **Права в фоне.** `--bg` + `--permission-mode` у полос: без присоединённого терминала запрос прав висит до `dialogExpiry` (5 мин), потом отказ. Проверить `auto` и `bypassPermissions`, хуки-стражи остаются.
2. **`gsd-executor` из turbo-exec:** `isolation: worktree`, хук `gsd-agent-isolation-guard`, спасение SUMMARY.
3. **Конфликты слияния полос** при неточных Areas. Митигируется консервативными масками и разрешателем; при провале полоса уходит в `needs-owner`.
4. **Дрейф GSD:** внутренние команды `gsd-tools` могут меняться. Митигируется проверкой `doctor` и режимом `safe`.
5. **Лимиты фоновых сессий** не документированы: сколько параллельно, сколько живут. Проверить на 3 полосах.
6. **Стоимость** контролируется через `max_lanes` / `max_executors`.

## 12. Вне рамок
- `/fast`: решение владельца, слишком дорого.
- Правка файлов `gsd-core`, кроме отдельного PR в upstream.
- Workflow-бэкенд GSD (`claude_orchestration`): не подключён в GSD и не нужен.

## 13. Этапы реализации (детальный план — после одобрения)
1. **Каркас и безопасный режим:** репозиторий, `install.mjs`, `turbo doctor`, `turbo-run` (одна полоса, авто-продолжение, статус, уведомления), `turbo-test-changed`, `/turbo-autonomous`. Сразу убирает простои и полные прогоны.
2. **Фаза быстрее:** `/turbo-phase` с параллельным прологом, веером гейтов и `turbo-uat`.
3. **Заранее и полосы:** `/turbo-plan-milestone`, `/turbo-new-milestone`, разметка ROADMAP, `lanes.json`, несколько полос, мьютексы, слияние.
4. **Граф исполнения:** `turbo-exec`.
5. **`/turbo-adopt`** для существующих майлстоунов, обкатка на эталонном проекте (со стартовой фазы, §10), README для друга, PR в upstream.

Каждый этап — отдельный релиз. Ускорение растёт с каждым.
