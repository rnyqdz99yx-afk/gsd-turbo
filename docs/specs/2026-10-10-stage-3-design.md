# gsd-turbo — Stage 3: владелец в цикле, тот же агент, push/CI, живой вид

Дата: 2026-10-10. Основа: журнал первого боевого прогона (v0.2.0–v0.2.1, один реальный GSD-проект, одна фаза
на 24 плана). v0.2.2 закрывает мелкие дефекты лейна и многопакетный `test.full`. Здесь — всё остальное из журнала.

Исходный этап 3 из основной спеки (§13: `/turbo-plan-milestone`, несколько полос, слияние) сдвигается на Stage 4
и дальше.

## 1. Цель и критерии

turbo проходит майлстоун без владельца. Когда владелец всё-таки нужен, turbo спрашивает его один раз,
кликабельными вариантами, и ответ доходит до того самого агента, который ждёт. Работа не переделывается.
Владелец видит прогон вживую в своей сессии Claude Code. Регрессии, которые видит только CI, ловятся внутри фазы.
Хвост фазы с участием владельца не обрывает лейн.

Готово, когда:
1. Лейн дошёл до чекпоинта плана → владелец получает кликабельные вопросы (сессия, панель или Telegram) → после
   ответа продолжает **тот же** исполнитель, если он доступен. Если нет, запускается агент-продолжение, и лейн
   сообщает, какой путь сработал.
2. Чекпоинты, на которые ответили заранее, лейн не останавливают: ответ уходит исполнителю с условием, и лейн
   встаёт, только если условие не выполнено.
3. Перезапуск Claude Code или ПК посреди работы субагента → лейн продолжает того же агента.
4. При включённом push голова лейна уходит в remote после волны или фазы, CI отслеживается, красный CI лейн
   чинит сам (не больше 2 раундов).
5. В сессии владельца видно: лейн → шаг `/turbo-phase` → субагенты (тип, план, текущее действие, время,
   токены), вопросы с кнопками ответа, последние коммиты.
6. Фазу с хвостом, где нужен владелец, ведёт `/turbo-autonomous attend N` в его сессии, а затем возвращает
   лейну. Ручной прогон plain GSD не нужен.

## 2. Решения владельца (2026-10-10)

| Вопрос | Решение |
|---|---|
| Канал ответа | Сессия (`/turbo-autonomous`) + кнопки в панели мода + inline-кнопки Telegram |
| Когда спрашивать | Заранее (после планирования фазы, ответы условные) и при стопе |
| Доставка ответа | Тот же разговор лейна (`claude --bg --resume`) → `SendMessage` тому же исполнителю; запасной путь — агент-продолжение |
| Красный CI | Лейн чинит сам, после 2 неудачных раундов — стоп «нужен владелец» |
| Хвост с владельцем | Режим `attend` в сессии владельца |
| Живой вид | Мод Claude Code: панель + полоса над промптом + тосты + кнопки ответа |
| Хранение ответов | В git: `.planning/turbo/answers/p<N>.json` |

## 4. S0 — слой данных по транскриптам

Без этого слоя turbo ничего не знает о субагентах лейна. Его используют S1 (найти остановленного исполнителя), S3
(живой вид) и проверка живости.

- **Где лежит.** Транскрипт сессии: `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<key>/<sessionId>.jsonl`. Субагенты:
  `<key>/<sessionId>/subagents/agent-<id>.jsonl` + `agent-<id>.meta.json` (`agentType`, `description`, `model`,
  `worktreeBranch`). Форк сессии переносит транскрипт субагента в каталог новой сессии, поэтому субагент ищется по
  `agentId` во всех каталогах сессий проекта, и берётся самый свежий файл. Фиксированный путь `output_file` не
  используется никогда.
- **Состояние субагента.**
  - `completed` / `stopped` / `failed`: только по `<task-notification>` с его `<task-id>` в **user**-записи
    транскрипта лейна, которую сгенерировал харнес. Текст внутри `tool_use` (например, цитата в промпте
    диспатча) не считается.
  - `running`: завершения нет, а транскрипт писался не позже `stall_minutes` назад (по умолчанию 15).
  - `quiet`: завершения нет, и записей не было дольше этого порога. Это только пометка: turbo ничего не
    убивает и не перезапускает по ней.
- **Поля.** Текущее действие = последний `tool_use` (имя + короткое описание входа: путь файла или начало
  команды, до 80 символов, с маскировкой по шаблонам секретов из `lib/uat.mjs`). Время = от первой записи до
  последней или до сейчас. Токены = контекст последнего ответа (`input + cache_creation + cache_read`).
- **`turbo-run view [--json]`.** Выводит: супервизор, диапазон, лейны (фаза, шаг из `phase-step`, статус лейна,
  `sessionId`, время), субагенты лейна, открытые вопросы, последние 5 коммитов. Читает только хвосты файлов
  (≤ 256 КБ на файл) с кешем по `mtime`; ответ за ≤ 300 мс на прогоне из 3 лейнов и 20 субагентов.
- **Смена `sessionId`.** Если `claude --bg --resume` создал копию сессии (строка `note:` с новым id), супервизор
  записывает новый `lane.sessionId`. Слой данных ищет субагентов во всех сессиях, где они встречались.

## 5. S1 — канал владельца и тот же агент

### 5.1 Вопросы

- **Источник.** Задачи `checkpoint:*` в планах фазы, в формате GSD (`<gsd-core>/references/checkpoints.md`;
  формат перед реализацией сверить с установленной версией):
  - `checkpoint:decision` с `<decision>`, `<options>`, `<resume-signal>`;
  - `checkpoint:human-verify` с `<what-built>`, `<how-to-verify>`;
  - `checkpoint:human-action` с `<action>`, `<instructions>`.
- **`turbo-run questions N [--json]`.** Детерминированно строит набор вопросов и пишет его в
  `.planning/turbo/run/p<N>-questions.json`:
  `{ id, phase, plan, task, kind, header (≤ 12 символов), question, context (≤ 600 символов),
  options[{ label, description, recommended, signal }], allowOther, condition, agentId|null, state }`.
  - `signal` — точный текст `resume-signal`, который получит исполнитель.
  - `decision`: варианты из плана; `recommended` только там, где план сам его отметил.
  - `human-verify`: «Принять, если проверки прошли» (условие = автоматические проверки из `how-to-verify` прошли, лейн
    прикладывает доказательства), «Остановиться и показать мне», «Другое».
  - `human-action`: заранее отвечается только «Сделаю, когда фаза попросит». Такой чекпоинт всегда остаётся
    стопом или уходит в `attend`.
- **Классификация лейном.** После шага `plan` лейн один раз размечает каждый вопрос: `owner-only` (физическое
  действие, 2FA, деньги, живые аккаунты владельца), `consent` (деплой, публикация), `decision`, `verify`. Пишет это
  командой `turbo-run questions N --class <id>=<class>[,<id>=<class>…]` в поле `class`; без разметки класс
  `decision`, а `human-action` — `owner-only`. Детерминированный разбор плана остаётся источником вариантов:
  лейн не придумывает варианты и не меняет `signal`.

### 5.2 Ответы заранее

- После шага `plan` лейн вызывает `turbo-run questions N`, и супервизор шлёт уведомление `questionsReady`
  (рабочий стол + Telegram с кнопками). Лейн при этом не останавливается и идёт дальше.
- `/turbo-autonomous` при старте и `/turbo-autonomous answer` показывают все открытые вопросы пачками по 4
  через `AskUserQuestion`: рекомендованный вариант первым, рядом краткий контекст.
- Когда лейн отправляет исполнителю план с чекпоинтом, у которого есть ответ, он добавляет в промпт исполнителя
  **условный пред-ответ**: «на чекпоинте <task> ответ владельца — <signal>; он действует, только если <condition>;
  если условие не выполнено, верни чекпоинт как обычно». Так уже работало вручную на реальных фазах.
- **Постоянное правило.** При `autonomy: max` и заданном `deploy.*` вопрос класса `consent` про деплой
  отвечается автоматически с условием-гейтом: сборочные проверки зелёные, CI зелёный (если `push` включён),
  процедура `deploy.*` со снапшотом, health-check и откатом. Такой ответ пишется с `by: "standing-rule"`. Всё
  остальное спрашивается у владельца.

### 5.3 Ответ при стопе

- Исполнитель вернул чекпоинт без ответа (или условие не выполнено) → лейн дописывает в вопрос `agentId`
  исполнителя (из `<task-notification>` / результата `Agent`) и проходит **Stopping early** с `needs-owner`.
- **Ответ в сессии.** `/turbo-autonomous answer` (или просто `/turbo-autonomous`, когда есть открытые вопросы).
- **Ответ в панели мода** (S3). Кнопка на каждый вариант + поле «Другое».
- **Ответ в Telegram.**
  - Включается `notify.telegram` + `answer.telegram: true`, используются `TURBO_TELEGRAM_TOKEN` и
    `TURBO_TELEGRAM_CHAT`.
  - Вопрос уходит сообщением с inline-кнопками: до 4 вариантов + «Другое». `callback_data` =
    `t3:<короткий id>:<номер варианта>:<nonce>` (≤ 64 байт). Nonce одноразовый и хранится в `run/telegram.json`.
  - Пока есть открытые вопросы, супервизор опрашивает `getUpdates` с long poll не дольше `poll_seconds`.
    `offset` хранится там же.
  - Нажатия принимаются только от `from.id`, совпадающего с `TURBO_TELEGRAM_CHAT` (личный чат). Остальные
    отбрасываются и пишутся в лог без содержимого.
  - После нажатия: `answerCallbackQuery` и правка сообщения на «✓ <вариант>». «Другое» → `force_reply`;
    ответ-сообщение (≤ 2000 символов) становится свободным ответом.
  - Токен в лог не пишется никогда.
- **Один арбитр.** Все каналы вызывают `turbo-run answer N <id> (--option <k> | --text <t>) --by
  <session|pane|telegram>`. Первый ответ выигрывает, повторный получает «уже отвечено: <ответ>, <канал>,
  <время>».
- **Текст ответа — данные, а не инструкции.** Лейн передаёт его исполнителю как ответ на этот чекпоинт и
  ничего больше. Права, правила лейна и шаги skill ответ не меняет.

### 5.4 Хранение

- `.planning/turbo/answers/p<N>.json`, в git: `{ id, plan, task, answer, by, at, conditional }`.
- Писатель в checkout один. Пока лейн работает, `turbo-run answer` пишет файл атомарно, а коммитит его лейн
  (`gsd-tools commit` на границе шага и вместе со своим следующим коммитом). Когда лейна нет, `turbo-run answer`
  коммитит сам.
- В ответ не попадают секреты: при совпадении с шаблонами секретов ответ отклоняется с просьбой переформулировать.

### 5.5 Доставка тому же агенту

1. Ответы на все вопросы, которые блокируют лейн в `needs-owner`, записаны → на следующем тике супервизор
   продолжает **тот же разговор лейна** («будит» сессию). Порядок проверен спайком 2026-10-10 (§9):
   1. `claude stop <короткий id>`. Сессия, закончившая ход, остаётся живой и простаивает; если её не
      остановить, resume создаёт копию.
   2. `claude --bg --resume <sessionId лейна> "<промпт>"` **без флагов**. Сессия сама подставляет сохранённые
      опции: `--name`, `--permission-mode`, `--settings`, `--append-system-prompt`, `--disallowedTools`,
      `--model`. Если передать любой флаг, даже тот же самый, получится копия.
   3. Промпт: «Владелец ответил: <id>: <signal>. Передай ответ исполнителю <agentId> через `SendMessage` как
      ответ на чекпоинт <plan>/<task>, затем продолжи `turbo-phase N --resume`».
   4. Успех: строка `note: woke session <id>`. Строка `started a copy as <id>` — провал пути `same-agent`: из
      копии `SendMessage` старому субагенту не доходит (`No transcript found for agent ID`). Супервизор
      останавливает и удаляет копию (`claude stop`, `claude rm`), один раз повторяет шаги 1–2 и после второго
      провала будит лейн новой сессией по пути `continuation` (п. 3).
   5. `sessionId` берётся, когда лейн уже простаивает. Сразу после пробуждения `claude agents --json`
      ненадолго показывает другой `sessionId` задачи; его не записывают.
2. Лейн шлёт `SendMessage(to=<agentId>)`. Агент продолжил работу (`resumedAgentId`, тот же файл
   `agent-<id>.jsonl` растёт) → путь `same-agent`.
3. Агент недоступен → **агент-продолжение**: GSD `continuation-prompt` + таблица выполненных задач, сверенная с
   git, + хвост транскрипта старого агента (`turbo-run agent-tail <agentId>`: последние 40 записей, текст без
   `tool_result`, ≤ 20 КБ, секреты замаскированы). Путь `continuation`.
4. Лейн пишет путь (`same-agent | continuation`) в `phase-step --note`, и `view` его показывает.
5. Лейн остановился по контексту (`paused-context`) → новая сессия, как сейчас (старый разговор полон). Из
   новой сессии старые исполнители недоступны (спайк: `No transcript found`), поэтому правило лейна: не уходить
   в `paused-context`, пока работают его фоновые субагенты. Сначала дождаться их завершения, потом
   останавливаться. Недоделанное старым агентом продолжает агент-продолжение (п. 3).
6. **Падение сессии, перезапуск Claude Code или ПК.** Демон Claude Code сам поднимает упавшую фоновую сессию
   (`crashed` → `running`, новый pid); она простаивает, и её ход не продолжается. Супервизор видит лейн живым, но
   без прогресса и без записи `done`, `needs-owner` или `paused-context` дольше `stall_minutes`, → будит его
   по п. 1 (stop, затем resume без флагов) с промптом «сессия прервалась; проверь своих фоновых субагентов
   (`turbo-run view --json`): незавершённым пошли `SendMessage` с текущим состоянием диска и git и просьбой
   продолжить с места остановки, перепроверив частичные записи». После падения процесса так работает (спайк).
   После перезагрузки ПК, когда умирает и демон, вручную это тоже работало; на лейне это проверяется вживую
   (§11).

## 6. S2 — push и CI

- **Конфиг.** `push: { mode: "off" | "after-wave" | "after-phase", remote: "origin", ci: "github" | "none",
  ci_timeout_minutes: 30, ci_fix_rounds: 2 }`, по умолчанию `mode: "off"`.
- **Запрос.** `after-wave`: лейн после каждой завершённой волны GSD вызывает `turbo-run push-request N`.
  `after-phase`: вызывает один раз на шаге `close`. Пушит только супервизор, лейны не пушат никогда.
- **Супервизор на следующем тике:**
  1. `git fetch <remote>`. Удалённая ветка должна быть предком `HEAD`; иначе пуша нет, уведомление
     `pushDiverged`.
  2. Скан секретов диапазона `<remote>/<branch>..HEAD`: шаблоны из `lib/uat.mjs` (вынести в общий модуль) +
     запрещённые имена (`.env*`, `*.session`, `*.db`, `*.sqlite`, `*.log`, `accounts.json`, `*.pem`, `*.key`).
     Есть находка → пуша нет, уведомление `pushRefused` (имя файла и тип находки, без значения).
  3. `git push <remote> HEAD:<branch>` без force и без `--no-verify`. Запись `run/p<N>-push.json { sha, at }`.
  4. `ci: "github"`: каждый тик `gh run list --commit <sha> --json databaseId,name,status,conclusion`, пока все
     прогоны не завершатся или не выйдет `ci_timeout_minutes` (тогда уведомление `ciTimeout`, лейн не
     трогается).
- **Красный CI.** `gh run view <id> --log-failed`, хвост 200 строк с маскировкой секретов → сообщение во входящие
  лейна `run/p<N>-inbox.jsonl` `{ kind: "ci-red", sha, run, job, step, tail }` + уведомление `ciRed`.
- **Входящие.** `turbo-run inbox N` печатает непрочитанное и помечает прочитанным. Правило лейна: проверять
  входящие после каждой волны и перед каждым шагом. На `ci-red` лейн:
  - `phase-step N --attempt ci`; номер больше `ci_fix_rounds` → стоп «нужен владелец»;
  - иначе находит причину (systematic debugging), исправляет одним коммитом, `turbo-run test-changed`, затем
    `push-request`.
- **План, который пушит сам.** Его задача «push и дождаться CI» выполняется как `turbo-run push-request N --wait`:
  команда ждёт пуша и результата CI (до `ci_timeout_minutes`) и печатает результат. Лейн больше не встаёт перед
  таким планом.

## 7. S3 — живой вид (мод Claude Code)

- **Что это.** Мод (плагин с `.claude-plugin/plugin.json` и `hooks/hooks.json` → `{"modules": ["./register.…"]}`,
  Claude Code ≥ 2.1.290) в каталоге `mod/` репозитория.
- **Установка (спайк §9.4).** `install.mjs` копирует мод в `~/.claude/skills/turbo-view/`. Claude Code сам грузит
  его в каждой сессии как `turbo-view@skills-dir`: без marketplace и без правки settings. Выключается записью
  `"turbo-view@skills-dir": false` в `enabledPlugins`. Пользовательская копия важнее проектной, а `--plugin-dir`
  важнее обеих. `doctor` проверяет версию Claude Code; на более старой версии мод не ставится, и работает запасной
  `turbo-run status --watch`.
- **Код.** Отрисовка — чистая функция `render(view)` в `.mjs` (тесты `node --test`, работают в CI). Модуль мода —
  тонкая обвязка: `$.clock.every`, `$.process.run`, `$.ui.open`, обработчики кнопок. Её проверяют `claude plugin
  validate` и `claude plugin test` локально; в CI этих команд нет.
- **Когда активен.** Только в проекте с `.planning/turbo/`. Данные: `$.process.run(node turbo-run.mjs view --json)`
  раз в 3 с через `$.clock.every`; в фоне — раз в 15 с. Сама панель открывается при ширине терминала от 144
  колонок (или от 110, если её уже открывали); в узком терминале её открывает команда `/turbo-view`. Полоса над
  промптом видна всегда.
- **Панель (`Pane`, сайдбар).**
  Простыми словами (v0.3.1), вердикт первым и в цвете (зелёный — всё в порядке, янтарный — ждёт ответ или
  тишина, красный — остановка или CI, которому нужен владелец):

## 8. S4 — живые сессии

- **`/turbo-autonomous attend N`** — хвост фазы ведётся в сессии владельца.
  1. `turbo-run attend N` помечает лейн `attended` и останавливает его сессию (`claude stop`, разговор
     сохраняется). Пока стоит пометка, супервизор этот лейн не перезапускает.
  2. Skill показывает оставшиеся планы (без SUMMARY) и все их вопросы и спрашивает согласия заранее, одной
     пачкой.
  3. Запускает GSD `execute-phase N` в основном checkout последовательно: перед каждым диспатчем `gsd-tools
     dispatch-isolation --force-isolation none`, условные пред-ответы идут в промпты исполнителей. Физические
     действия владелец делает, когда до них доходит.
  4. `turbo-run attend N --done` снимает пометку и делает `resume N --start`. Лейн продолжает шаги
     `/turbo-phase` (verifier, гейты, UAT, закрытие).
- **Правила релиза** (правило лейна и `attend`):
  - Работающий исполняемый файл не перезаписывается; сборку копировать в новый путь (`<release>/<время>/`).
  - Файл заблокирован процессом → процесс не убивать, а остановиться (`owner-only`) с точной инструкцией.
  - Программный выход из приложения (IPC или `--quit` второго экземпляра) — задача самого проекта: turbo пишет
    это в причину остановки как рекомендацию.
- **Бюджет кругов.** Новый ключ `gap_rounds`, по умолчанию 1. Он заменяет жёсткую «одну итерацию закрытия
  гэпов» в шагах `execute` и `uat`. Исправление часто открывает следующий сбой на шаг позже, поэтому владелец
  может поставить 3. Каждый круг должен давать новые доказательства (новая проверка прошла или упала иначе);
  круг без нового результата — стоп.
- **Правило для планов закрытия гэпов.** План гэпа перезапускает только проверки упавших пунктов, а не весь
  живой прогон. Это правило лейна для `gsd-plan-phase --gaps`.

## 11. Тесты

- Unit: разбор чекпоинтов (фикстуры на каждый из трёх видов), арбитр ответов (первый выигрывает), Telegram
  (фиктивный `fetch`: чужой `from.id`, повтор nonce, `force_reply`), слой данных (фикстуры транскриптов: форк,
  цитата маркера в промпте, `quiet`), push (расхождение, находка секрета, без force), CI (фиктивный `gh`),
  входящие, `attend`, `gap_rounds`.
- Supervisor: resume того же разговора, обработка `note:` с новым id, `attended` не перезапускается.
- Мод: рендер дерева из фиксированного `view --json` (чистая функция `render(view)` вне мода).
- Живые проверки (вне CI, с доказательствами в журнале): чекпоинт → ответ в Telegram → тот же агент;
  перезапуск Claude Code посреди работы исполнителя; красный CI → исправление лейном.
