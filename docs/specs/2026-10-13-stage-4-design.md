# gsd-turbo — Stage 4: несколько фаз одновременно и подготовка заранее

Дата: 2026-10-13. Основа: основная спека (§4.1, §4.4, §5), журнал трёх боевых прогонов (v0.2–v0.3.3) и два
исследования 2026-10-13: внутренности GSD 1.16 для параллельных полос и правила доверия к папкам в Claude Code.
Релиз: **v0.4.0**, одним релизом (решение владельца).

## 1. Цель и критерии

Майлстоун идёт не фаза за фазой, а **несколькими полосами**: независимые фазы выполняются одновременно, каждая в
своём локальном клоне репозитория. Будущие фазы заранее проходят discuss и research. Супервизор вливает готовые
фазы в `main` сам, без LLM, и вливает ровно то дерево, которое полоса проверила тестами. Целевое ускорение
майлстоуна — ≈3× против plain GSD (основная спека §10), против v0.3 — до `max_lanes`× на независимых фазах.

Готово, когда:
1. `/turbo-autonomous` в майлстоуне без разметки сам готовит фазы (prep), размечает ROADMAP и запускает до
   `max_lanes` независимых фаз одновременно.
2. Фазы с пересекающимися `Areas`, общим `Gates` или зависимостью друг от друга никогда не идут одновременно.
3. Полоса в конце фазы вливает свежий `main`, сама разрешает конфликты в коде, гоняет полный набор тестов, и
   супервизор вливает её в `main` только если `main` с тех пор не сдвинулся. Иначе полоса повторяет интеграцию;
   после `merge_rounds` неудач — карточка владельцу.
4. `STATE.md`, `ROADMAP.md`, `REQUIREMENTS.md` в `main` меняет только супервизор, через `gsd-tools`.
5. Всё, что умела v0.3 (авто-продолжение, вопросы владельцу заранее и при стопе, будильник тихой полосы, push/CI,
   attend, gap rounds, панель, Telegram), работает **на каждую полосу**.
6. `lanes.mode: "checkout"` возвращает поведение v0.3 (одна полоса в основной рабочей копии) — аварийный режим.

## 2. Решения

Владелец (2026-10-13):
- один релиз; работа как в Stage 3 (подпроекты параллельно: Opus-исполнитель в своём worktree + независимый
  Opus-ревьюер + раунды фиксов, ветка → CI → `merge --no-ff`);
- конфликт слияния разрешает Claude, не вышло — карточка владельцу;
- порядок фаз turbo меняет сам и пишет ADR (`autonomy: max`), при `standard` — одна карточка;
- архитектура «изолированная копия на полосу, сливает супервизор» и единственный писатель — одобрены;
- дальше дизайн решает Claude сам («ты сам придумай самую лучшую идею… выбирай сам»).

## 4. Слоты: где живут полосы

**Слот** — постоянный локальный клон основного репозитория: `<parent>/<repo>.turbo/lane-<k>`, `k = 1..max_lanes`
(каталог настраивается: `lanes.dir`). Для GSD это обычный репозиторий (G1, G2 не срабатывают).

- **Создание** (`turbo-run lanes setup`, его же зовёт `start`, когда слотов не хватает):
  1. `git clone --local --no-checkout <main> <slot>`; remote `origin` слота = основная рабочая копия.
  2. Копирование gitignored-файлов, без которых проект не работает: `.claude/settings.local.json` и маски из
     `lanes.copy` (по умолчанию: `.env`, `*/.env`, `.env.local`, `*/.env.local`). Копии никогда не коммитятся
     (они в `.gitignore` проекта; если файл из `lanes.copy` не игнорируется — отказ с объяснением).
  3. В `.claude/settings.local.json` слота turbo ставит `worktree.baseRef: "head"` (G8). Файл проекта не трогает.
  4. Доверие (§4.1).
- **Подготовка к задаче** (каждая полоса, prep, аналитик): `git fetch origin`, `git checkout -B turbo/<job>
  origin/<main_branch>`, `git clean -fdx -e <скопированные файлы> -e node_modules` только если слот чист
  от незавершённой работы (запись `lane.json` слота пуста или `done`); иначе — отказ и уведомление, никогда
  `--force` по чужой работе.
- **Зависимости:** установка по lockfile (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --immutable`,
  по каждому каталогу из `test.full`) **только если хеш lockfile изменился** с прошлой установки в этом слоте
  (`.git/turbo-deps.json` слота). Ссылки на `node_modules` основной копии запрещены (известная беда: очистка через
  junction стирает основное дерево). Команду можно задать: `lanes.install`.
- **Удаление:** `turbo-run lanes remove [k]` — только чистые слоты без записи работы; доверие снимается из
  `~/.claude.json` теми же правилами, что ставилось.

### 4.1 Доверие
`turbo-run lanes trust` для каждого слота:
1. Если Claude Code уже доверяет каталогу (`projects[<path>].hasTrustDialogAccepted === true`) — ничего.
2. Иначе, когда формат `~/.claude.json` узнаётся (объект `projects`, ключи — абсолютные пути в том виде, в каком
   их пишет Claude Code на этой ОС): бэкап `~/.claude.json.turbo-bak-<UTC>`, атомарная запись одного ключа, повторное
   чтение и проверка. Пишется только `hasTrustDialogAccepted: true` для каталога слота; больше ничего.
3. Формат не узнан или запись не удалась → строка владельцу: «откройте `claude` в `<slot>` один раз и примите
   доверие» (по одной на слот), запуск полос ждёт.
`doctor` проверяет доверие каждого слота (`lane-trust`). `--no-trust-write` (и ключ `lanes.trust_write: false`)
отключает пункт 2 для тех, кто не хочет, чтобы turbo трогал `~/.claude.json`.

### 4.2 Управляющий корень
Состояние turbo живёт в **основной рабочей копии** (управляющий корень), а не в слоте: `run/`, `logs/`,
`locks/`, вопросы и ответы владельца. Исключение — `gates/`: он описывает конфиг GSD самого слота (гейты
выключаются в слоте), поэтому живёт и коммитится в слоте, как сейчас в основной копии. Супервизор передаёт полосе `TURBO_CONTROL_ROOT` через `--settings`
`env` (как сейчас `TMP`); без переменной `turbo-run` в клоне находит корень по `remote.origin.url` слота, если
он указывает на локальную копию с `.planning/turbo/`. Все команды `turbo-run`, которые полоса зовёт
(`phase-step`, `lane-status`, `ask`, `questions`, `push-request`, `inbox`, `context`, `gates`, `state-sync`),
читают и пишут состояние в управляющем корне, а код и `.planning` фазы — в слоте.
Ответы владельца (`answers/`, отслеживаются git) коммитит `turbo-run answer` в `main` сам, под блокировкой слияния
(`main` принадлежит супервизору, полоса там не работает). Полоса читает их из управляющего корня.

## 5. Планировщик и супервизор

Состояние `supervisor.json`: `lanes: { "<phase>": { slot, sessionId, job: "phase"|"prep"|"annotate", … } }`
вместо одного `lane`. Всё, что сейчас делается для `s.lane` (запуск, переподъём после контекста, будильник,
доставка ответов, `attend`, лимит перезапусков), делается по каждой записи.

**Готова к запуску** фаза, если:
1. все её `Depends on` завершены (как сейчас: `isFinished`), и она в диапазоне прогона;
2. её `Areas` не пересекаются с `Areas` идущих фаз (§6.3; фаза без разметки = `**`, пересекается со всеми);
3. ни один её `Gates` не занят идущей фазой;
4. есть свободный доверенный слот; идущих полос < `max_lanes`.
Порядок выбора — как сейчас (`comparePhase`), затем по длине цепочки зависящих от неё фаз (критический путь
первым). Без `lanes.json` или при устаревшем (§6.4) — не больше одной полосы фазы, пока идёт разметка.

**Блокировки ресурсов.** `Gates` фазы занимаются на всё время фазы. Дополнительно `turbo-run lock <gate> <N>` /
`unlock` — файловые мьютексы в `locks/` для разовых действий (деплой, упаковка), которые полоса берёт на шаге;
ожидание — с таймаутом и уведомлением.

**Порядок записи в `main`.** Одна файловая блокировка слияния (`locks/merge`): слияние полосы, коммит ответа
владельца, перенос prep и разметки берут её по очереди.

`lanes.mode: "checkout"` — одна полоса в основной копии, без слотов, без интеграции: ровно v0.3.

## 6. Заранее: prep и разметка

### 6.1 Prep
Для каждой незавершённой фазы диапазона без `CONTEXT.md` супервизор ставит задачу `prep`: фоновая сессия
`/turbo-prep N` в свободном слоте на ветке `turbo/prep-<N>`. Она делает шаги `freshness`, `discuss` (assumptions,
рекомендованные ответы) и `prologue` из `/turbo-phase` (общий код шагов, тот же `phase-step`) и останавливается
**до** `plan`. Готово → `lane-status N prepped` → супервизор вливает ветку (§7.2, без тестов: меняется только
`.planning/phases/<N>-*`; если ветка тронула что-то ещё — отказ, задача `failed`). Одновременно не больше
`max_prep` (по умолчанию = `max_lanes`); фазы полос всегда имеют приоритет над prep.
Планы (`PLAN.md`) заранее не пишутся (основная спека F10): их строит полоса, когда предшественники влиты;
`base_sha` и шаг `freshness` точечно обновляют устаревшее.

### 6.2 Разметка (агент `turbo-lane-analyst`)
Задача `annotate`: одна фоновая сессия в слоте на ветке `turbo/annotate`, после prep (или сразу, если prep нечего
делать). На входе ROADMAP, CONTEXT/RESEARCH всех незавершённых фаз, уже написанные планы (`files_modified`) и код.
По каждой незавершённой фазе — строки в её секции ROADMAP, сразу после `**Depends on**:`:
- `**Areas**:` маски путей через запятую (миниматч, от корня репозитория), которые фаза может тронуть; включая
  тесты и конфиги; `.planning/**` не указывается (у каждой фазы свой каталог);
- `**Gates**:` из словаря `prod-deploy`, `owner-live`, `owner-signature`, `packaged-build`, плюс свои из
  `lanes.gates` проекта; пусто — строки нет;
- `**Parallel with**:` фазы, с которыми она может идти одновременно (информативно, для людей).
Плюс `.planning/turbo/lanes.json`: `{ roadmap_sha256, phases: { N: { areas, gates, confidence } }, pairs: [[a,b,
"conflict"|"ok", reason]] }`. `confidence: low` → фаза считается `**`.
Ослабить объявленную зависимость (`Depends on`) аналитик может, только если она прозаическая или мнимая (фазы
не делят ни файлов, ни данных, ни поведения): пишет ADR в `.planning/decisions/` (если каталог есть) или в
`.planning/turbo/DECISIONS.md` — что было, что стало, почему, как откатить. При `autonomy: max` правка
применяется; при `standard` она идёт владельцу одной карточкой (`turbo-run ask`: принять всё / принять выборочно /
не менять). Зависимости аналитик пишет только в форме `Phase 3, Phase 4` (G4). Результат вливается как prep
(§7.2), меняются только ROADMAP, `lanes.json` и файлы решений.

### 6.3 Пересечение `Areas`
Две маски пересекаются, если одна может совпасть с путём, который совпадает с другой. Проверка консервативная:
сравниваются статические префиксы до первого `*`/`?`/`[`/`{`; если один префикс — префикс другого (по сегментам
пути), считается пересечением. Ложное «пересекаются» стоит только параллельности; ложное «не пересекаются»
невозможно для масок без метасимволов внутри сегментов, а остальное ловит интеграция (§7).

### 6.4 Свежесть разметки
`lanes.json` хранит sha256 ROADMAP. Изменился (добавили или удалили фазу, правили зависимости) → фазы, которых
нет в `lanes.json` или у которых поменялась секция, становятся `**`, и ставится задача `annotate` только для них.

### 6.5 Команды
- `/turbo-plan-milestone` — prep + разметка для всего майлстоуна, без запуска фаз (то же, что первые шаги `start`).
- `/turbo-new-milestone` — `/gsd-new-milestone`, затем `/turbo-plan-milestone`.
- `/turbo-autonomous` (start) — если `lanes.mode: "slots"` и разметки нет, сам ставит prep и annotate первыми.

## 7. Конец фазы: интеграция и слияние

### 7.1 Шаг `integrate` полосы (новый, после `close`)
1. `git fetch origin && git merge origin/<main_branch>` в слоте. Для `.planning/STATE.md`, `.planning/ROADMAP.md`,
   `.planning/REQUIREMENTS.md` берётся версия `origin` (`git checkout --theirs` при конфликте и всегда после
   слияния): отметки своей фазы сделает супервизор.
2. Конфликты в коде полоса разрешает сама, в рамках своей фазы; не может — `turbo-run ask` с вариантами (что
   конфликтует, чья правка, что предлагает) → стоп для владельца.
3. Полный прогон тестов (`TURBO_FULL=1 turbo-run test-changed`). Красный → исправление в полосе (это её код
   после слияния), до `ci_fix_rounds` попыток, затем стоп для владельца.
4. Коммит слияния, `turbo-run lane-status N ready --base <sha origin/main, который влит>`.

### 7.2 Слияние (супервизор, без LLM, под `locks/merge`)
1. Основная копия чиста и на `<main_branch>`; иначе — ждать и уведомить (владелец что-то делает в ней).
2. `HEAD == base` полосы → `git fetch <slot> turbo/<job>` и `git merge --no-ff FETCH_HEAD -m "Merge phase N
   (turbo lane k)"`. Дерево слияния совпадает с проверенным в полосе (кроме трёх файлов из 7.1 п.1, которые
   берутся из `main`).
3. `HEAD != base` → запрос полосе «интегрируйся снова» (inbox `reintegrate`, будильник как для ответа владельца).
   Подряд больше `merge_rounds` (3) → карточка владельцу: «фаза N не успевает влиться: main меняется быстрее» с
   вариантами (подождать, остановив запуск новых фаз / разобрать самому).
4. После слияния: `gsd-tools query phase.complete N`, `turbo-run state-sync`, один коммит
   `docs(phase-N): complete phase (turbo merge)` с ROADMAP/STATE/REQUIREMENTS (G6). `phase.complete` упал
   (например, VERIFICATION не `passed`) → `git reset --hard ORIG_HEAD` **не делается**; слияние остаётся,
   фаза → `needs-owner` с текстом ошибки.
5. Push (если `push.mode` не `off`): `main` → remote, CI отслеживается как сейчас. Красный CI → лог в inbox
   полосы; полоса (её слот ещё держит ветку) чинит, проходит 7.1 заново, супервизор вливает исправление. Слот
   освобождается только после зелёного CI (или сразу при `push.mode: off`).
6. Слот освобождён → задача `done`, ветка `turbo/<job>` в слоте удаляется при следующей подготовке.
Prep и annotate вливаются по 7.2 п.1–2 без п.4–5 (только `.planning`; push вместе со следующим слиянием фазы).

### 7.3 Push полос
Полосы не пушат. `push-request` полосы в режиме слотов: `--at wave` — ничего; `--at phase` — заменяется
интеграцией и пушем `main` (п.5). Ветки полос в remote не попадают (`push.lane_branches` — вне рамок).

## 8. Владелец

- **Вопросы** — без изменений, по фазе; в карточке видно, какая полоса (`фаза 34, полоса 2`).
- **attend N** — останавливает только полосу N; остальные идут. Сессия владельца открывается в слоте полосы:
  команда печатает `cd <slot> && claude`, а скилл `attend` работает в том каталоге (там доверие уже есть).
  `attend N --done` возвращает фазу полосе. `main` при этом не трогается.
- **stop** — все полосы, prep и annotate; слоты и ветки остаются для разбора.
- **status / панель / Telegram** — список полос: фаза, слот, шаг, помощники, вопросы; общая строка
  «3 полосы · 1 вопрос · следующая: фаза 36 ждёт фазу 34». Панель: по блоку на полосу, свёрнутые до одной строки,
  когда полос больше двух; раскрыта та, где вопрос или предупреждение.

## 9. Сбои

- Полоса упала или исчерпала перезапуски → только она `failed`/`needs-owner`; остальные идут; новые фазы, которые
  от неё зависят, ждут.
- Супервизор упал → при старте читает `lanes`, находит сессии по слотам и продолжает (как сейчас одну полосу).
- Слот грязный без записи работы → не используется, уведомление «слот k: незавершённые изменения» (ничего не
  удаляется).
- `~/.claude.json` поменялся и доверие слота пропало → `Workspace not trusted` → полоса ждёт, владельцу строка
  из §4.1 п.3.
- Основная копия грязная → слияния ждут, полосы работают дальше.

## 11. Подпроекты и порядок

Сначала спайки (§12), затем:

| Подпроект | Что | Зависит от |
|---|---|---|
| **L0 Слоты и корень** | `lib/slots.mjs` (setup, prepare, deps, copy, remove), `lib/trust.mjs`, управляющий корень (`paths.mjs` + все команды полосы), `TURBO_CONTROL_ROOT` в настройках сессии, doctor | — |
| **L1 Полосы** | `supervisor.json` `lanes`, планировщик (`Areas`/`Gates`/слоты/критический путь), запуск/переподъём/будильник/ответы/attend/stop по полосе, блокировки `lock/unlock` | L0 (интерфейс) |
| **L2 Интеграция** | шаг `integrate` в `/turbo-phase`, `lane-status ready --base`, слияние §7.2, `phase.complete` + коммит, push `main` → CI → inbox полосы, освобождение слота | L0 (интерфейс) |
| **L3 Заранее** | `/turbo-prep`, задачи prep/annotate в супервизоре, агент `turbo-lane-analyst`, разметка ROADMAP, `lanes.json`, ADR, свежесть, `/turbo-plan-milestone`, `/turbo-new-milestone` | L0, L1 (интерфейс задач) |
| **L4 Вид** | `view`/панель/`status --watch`/Telegram для нескольких полос | L1 (формат `supervisor.json`) |

L0 идёт первым и фиксирует интерфейсы (`controlRoot()`, `slotFor()`, формат `supervisor.json.lanes`). L1–L4 —
параллельно, каждый в своём worktree репозитория turbo, со своим ревьюером. Слияние подпроектов в ветку
`stage-4`, затем общий интеграционный прогон и релиз v0.4.0.

## 12. Спайки — первыми

1. **Доверие слота:** `git clone --local` во временный каталог, запись `hasTrustDialogAccepted` с бэкапом,
   `claude --bg` в нём стартует; снятие ключа возвращает `Workspace not trusted`.
2. **GSD в клоне:** в клоне эталонного мини-проекта на ветке `turbo/p1`: `gsd-execute-phase` с двумя планами
   одной волны — исполнители коммитят, волна параллельна (`baseRef: head` в settings.local слота), STATE/ROADMAP
   обновляются по планам (G1, G2, G8 не срабатывают).
3. **Слияние:** после фазы в клоне — `git fetch`/`merge --no-ff` в основную, затем `phase.complete N` в основной
   проходит (VERIFICATION `passed` пришёл со слиянием).
4. **Две полосы:** две фоновые сессии в двух слотах одновременно не мешают друг другу (lock-файлы, транскрипты,
   `claude agents --json` различает их по `cwd`).
Любой спайк провалился → эта спека правится до реализации.

## 13. Тесты

- Юнит: пересечение масок (§6.3), выбор готовых фаз (зависимости, `Areas`, `Gates`, слоты, критический путь),
  `lanes.json` и свежесть, разбор разметки ROADMAP, формат `~/.claude.json` и запись доверия (на копии во временном
  каталоге), управляющий корень.
- С настоящим git во временных каталогах: setup/prepare/remove слота, копирование ignored-файлов, установка
  зависимостей только при смене lockfile, интеграция с конфликтом и без, слияние с `HEAD == base` и `!=`, отказ
  prep, который тронул что-то кроме `.planning/phases/<N>-*`.
- E2E супервизора с фальшивым `claude` (как `e2e-supervisor`): три фазы, две независимые идут вместе, третья
  ждёт; падение одной полосы не останавливает другие; рестарт супервизора подхватывает полосы.
- Живой прогон: эталонный проект, оставшиеся фазы его майлстоуна, с журналом, как в Stage 3.

## 14. Совместимость и обновление

- v0.3 → v0.4: первый `start` создаёт слоты и (если нет разметки) ставит prep/annotate. Идущий прогон v0.3
  останавливается до обновления (README, Upgrade).
- `lanes.mode: "checkout"` — без слотов, одна полоса, как v0.3; на случай, когда клон невозможен.
